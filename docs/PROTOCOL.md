# Протокол агента: бэкенд ↔ агент ↔ воркер

Агент на узле держит воркеры и связь с бэкендом. Связь на обоих уровнях устроена одинаково:
вниз — поток SSE (желаемое состояние и команды), вверх — обычные `POST` (итоги, события,
состояние). Связь с бэкендом — по HTTPS, агент входит своим ключом (§4, §5).
Библиотек не нужно: бэкенд и воркер реализуют протокол сами, стандартными средствами своего
языка. Типы и константы на Go — пакет `github.com/epifanovmd/agent/protocol`, клиент воркера на
Go — `github.com/epifanovmd/agent/worker`; примеры на Python — `examples/`.

## 1. Принципы

1. **Узел автономен.** Агент держит воркеры по своему `agent.yaml` и последнему полученному
   желаемому состоянию; без бэкенда узел работает дальше.
2. **Желаемое состояние вместо команд**, где это возможно: бэкенд сообщает, каким всё должно
   быть (настройки воркеров, наблюдение), агент и воркеры сами к нему сходятся и переживают обрывы
   и перезапуски.
3. **Команды асинхронны.** Команда — `{id, type, args}`; итог приходит отдельно, с `re = id`.
   Ждать итог или нет — решает тот, кто отправил.
4. **Доставка «как минимум один раз», обработка идемпотентна.** У каждой команды, итога и события
   свой `id`; повтор безопасен; неподтверждённое хранится на диске.
5. **Защищено по умолчанию.** Связь с бэкендом — только HTTPS (`http://` — по явной настройке);
   бэкенд хранит не ключи агентов, а их хеши.
6. **Соединение всегда открывает нижний уровень:** агент — к бэкенду, воркер — к агенту. Входящих
   портов на узле нет.
7. **Агент не знает предметной области.** Всё, что касается дела (сеть, отчёты, обработка данных), —
   в воркерах и бэкенде.

## 2. Термины

| Термин               | Что                                                                                    |
| -------------------- | -------------------------------------------------------------------------------------- |
| **узел**             | машина с агентом                                                                       |
| **воркер**           | процесс на узле, который делает дело; запускает и держит его агент                     |
| **желаемое**         | документ «каким всё должно быть» с номером `rev`; новый `rev` целиком заменяет прежний |
| **команда**          | разовое поручение с `id`, `type`, `args` и сроком                                      |
| **итог**             | ответ на команду: `{re, ok, result?, error?}`                                          |
| **событие**          | сообщение о случившемся с `id`, `type`, `data`, `at`                                   |
| **очередь на диске** | неподтверждённые итоги и события агента; запись удаляется после подтверждения          |

**Имена.** Воркер и ключ настроек — `^[a-z][a-z0-9-]{0,31}$`; тип команды, события и запроса
воркера — `^[a-z][a-z0-9._-]{0,63}$`; имя агента — непустое, до 128 символов; меток — до 64, ключ и
значение — до 256 символов.

Ошибка везде — `{ code, message }`; `code` — `[A-Z_]+`. Время — мс Unix. Base64 — стандартный,
с дополнением (`=`).

## Часть I. Бэкенд ↔ агент

## 3. Адреса и ответы

Базовый адрес — `server.url` агента, маршруты — под `/agent/v1`.

| Ответ бэкенда                | Что делает агент                                                                                     |
| ---------------------------- | ---------------------------------------------------------------------------------------------------- |
| `2xx`                        | успех                                                                                                |
| `401 AGENT_UNKNOWN`          | ключ агента не известен: регистрация заново, если в настройках есть токен; иначе — ожидание и журнал |
| `403 AGENT_REVOKED`          | агент отозван (`revoked`, §4): связь прекращается, воркеры останавливаются и выполняют `cleanup`     |
| `429`, `5xx`, обрыв, таймаут | повтор с паузой 1 с → 60 с (×2, ±20 %); `Retry-After` — не раньше                                    |
| другой `4xx`                 | ошибка протокола: запись в журнал, данные не повторяются                                             |

## 4. Регистрация и ключ

```http
POST /agent/v1/enroll
{ "token": "…", "name": "node-01", "labels": { "zone": "eu" },
  "host": { "os": "linux", "arch": "amd64", "hostname": "…" } }
→ 200 { "agentId": "6f1c…", "secret": "…" }
→ 401 { "code": "ENROLL_DENIED" }
```

- **Ключ агента** — `agentId` и `secret`. Агент хранит их в `<dataDir>/credentials.json` (0600),
  бэкенд — только `sha256(secret)`.
- **Токен** — непрозрачная строка, правила у бэкенда. Рекомендуется одноразовый токен на узел со
  сроком действия (выдаётся с командой установки; регистрация сразу привязывает агента к узлу) и,
  для контейнеров и разработки, многоразовый токен проекта. Отказ — всегда `401 ENROLL_DENIED`;
  неудачные попытки с одного адреса бэкенд ограничивает (`429`).
- **Смена ключа** — команда `agent.rotateKey` (§8): агент создаёт новый секрет и отдаёт его хеш в
  итоге. Бэкенд принимает и старый, и новый секрет, пока не придёт первый запрос с новым; дальше —
  только новый. Запросы текущей сессии агент шлёт со старым секретом; доставив итог,
  переподключается с новым (не принят — снова со старым). Агент, не сумевший сохранить новый
  секрет, продолжает со старым.

**Состояние агента** хранится на узле рядом с ключом (`<dataDir>/status.json`) и переживает
перезапуски:

| Состояние | Воркеры                                  | Связь с бэкендом                         | Переход                                   |
| --------- | ---------------------------------------- | ---------------------------------------- | ----------------------------------------- |
| `pending` | не запускаются; сокет их не принимает    | регистрация, `hello`, поток              | → `active`: ответ на `hello` со `status: active` |
| `active`  | работают, и без связи (по последнему желаемому) | всё по протоколу                  | → `revoked`: ответ `403 AGENT_REVOKED`    |
| `revoked` | останавливаются, выполняют `cleanup` (§11); сокет не принимает | прекращена, на связь не выходит | → `pending`: новая установка с токеном (`agent install --token`) — прежний ключ забывается |

- Новый агент — `pending`. Бэкенд подтверждает его ответом на `hello`: `status: active` (нет
  поля — тоже `active`) или оставляет ждать: `status: pending` (например, до подтверждения
  человеком; ожидающего агента бэкенд переводит, закрыв его поток: агент переподключится и
  получит новый ответ на `hello`).
- Агент без бэкенда (`server.url` не задан) — сразу `active`.
- Ключ не известен бэкенду (`401 AGENT_UNKNOWN`) — регистрация заново; состояние не меняется.
  После любой регистрации агент начинает с новой записью с начала: забывает `seq` команд (поток —
  `after=0`) и неотправленные итоги прежней; события воркеров и желаемое сохраняются.
- Отзыв — навсегда: бэкенд отвечает отозванному ключу `403 AGENT_REVOKED` и после удаления
  агента. Удалить программу с узла — `agent uninstall --purge` (от того, кто ставил).

## 5. Транспорт и вход

- **HTTPS обязателен.** Агент соединяется только по `https://`; `http://` — только при
  `server.allowInsecure: true` (стенд, локальная сеть). Свой удостоверяющий центр —
  `server.caFile`.
- **Вход** — каждый запрос, кроме регистрации, с заголовком
  `Authorization: Agent <agentId>.<secret>`. Бэкенд сравнивает хеш секрета за постоянное время.
- **Журналы.** Заголовок `Authorization` и тело регистрации бэкенд в журнал не пишет.
- Тела запросов, ответов и событий потока — обычный JSON (`application/json`).

## 6. Поток вниз — `GET /agent/v1/stream`

Долгий ответ `text/event-stream`; агент держит его всегда, пока есть связь.

```text
: ok

id: 18
event: desired
data: {"rev":18,"workers":{"report":{"configs":{"settings":{"version":7,"data":{…}}}}},"watch":null}

id: c-1043
event: command
data: {"seq":1043,"id":"c-91","type":"worker.restart","args":{"worker":"report"},"deadline":1791900000000}

: ping
```

- **`desired`** — желаемое целиком (§7). Бэкенд присылает его первым при каждом подключении и
  затем при каждом изменении.
- **`command`** — команда агенту (§8). При подключении бэкенд присылает все незавершённые команды
  с `seq` больше `?after=<seq>` (агент передаёт `seq` последней полученной), затем новые.
- **Ping** — комментарий раз в 15 с; ничего не пришло 45 с — агент переподключается.
- Бэкенд может закрыть поток сам (балансировка копий) — агент переподключается сразу.
- **Длинный опрос** — запасной путь для прокси, которые буферизуют SSE:
  `GET /agent/v1/poll?after=<seq>&rev=<rev>&wait=30` → `200 { desired?, commands: […] }` (пусто —
  по истечении `wait`). Агент переходит на него сам, если поток не отдал `: ok` за 10 с.

## 7. Желаемое состояние

```jsonc
{
  "rev": 18,
  "workers": {
    "report": { "configs": { "settings": { "version": 7, "data": { … } } } }
  },
  "watch": { "metricsIntervalMs": 1000, "logLevel": "debug", "until": 1791… } // null — не наблюдают
}
```

- **Настройки воркеров** — по ключам с версиями; ключ, которого нет, у воркера удаляется. Какие
  воркеры работают на узле, решает `agent.yaml` узла, а не бэкенд.
- Агент хранит последнее желаемое в своём хранилище (§18) и передаёт воркерам их часть (§14); без связи — последнее
  сохранённое.
- **Наблюдение** (`watch`) — пока кто-то смотрит на узел: метрики чаще, журнал подробнее, до
  `until`.

## 8. Команды агенту

Команда: `{ seq, id, type, args, deadline? }`; итог — `POST /agent/v1/results` (§9) с `re = id`.

| `type`            | `args`                                                  | Итог `result`                                        |
| ----------------- | ------------------------------------------------------- | ---------------------------------------------------- |
| `worker.command`  | `{ worker, type, args?, timeoutMs? }`                   | итог воркера (§15) как есть, до 4 МБ                 |
| `worker.cancel`   | `{ worker, re }` — отменить идущую команду воркера `re` | `{}`                                                 |
| `worker.restart`  | `{ worker, force? }`                                    | `{}` — после запуска                                 |
| `worker.update`   | `{ worker, version, url, sha256, signature, force? }`   | `{ version, previous }`                              |
| `agent.update`    | `{ version }`                                           | `{ version, previous }` — присылает уже новая версия |
| `agent.rotateKey` | —                                                       | `{ secretHash }` — sha256 нового секрета, hex        |
| `agent.logs`      | `{ worker?, lines? }`                                   | `{ entries: [LogEntry] }`, до 4 МБ                   |

- **Повтор** команды с уже выполненным `id` агент не выполняет снова: шлёт сохранённый итог или,
  если команда ещё идёт, ничего (журнал `id` — в хранилище агента, §18, последние 10 000).
- **Срок.** Истёк `deadline` до начала — итог `EXPIRED`, команда не выполняется.
- **Занятый воркер.** `worker.restart` и `worker.update` ждут, пока воркер не `busy` (§16), не
  дольше 24 ч; `force` — сразу.
- Незнакомый `type` — итог `UNKNOWN_COMMAND`.
- **`worker.command`** передаётся воркеру с тем же `id`; срок — меньший из `deadline` и
  `timeoutMs` (нет обоих — без срока: долгая команда может идти часами). Истёк — агент отменяет
  команду у воркера и присылает итог `TIMEOUT`. Воркер не запущен или не на связи — команда ждёт
  его подключения.

## 9. Вверх: итоги, события, состояние

| Маршрут                   | Тело                                                             | Доставка                                            |
| ------------------------- | ---------------------------------------------------------------- | --------------------------------------------------- |
| `POST /agent/v1/hello`    | при подключении и изменении: версия, узел, воркеры с манифестами | последнее значение                                  |
| `POST /agent/v1/results`  | `[{ re, ok, result?, error? }]`                                  | очередь на диске, до `accepted`                     |
| `POST /agent/v1/events`   | `[{ id, worker, type, data?, at }]`                              | очередь на диске, до `accepted` или `rejected`      |
| `POST /agent/v1/state`    | состояние агента и воркеров, итоги настроек, применённый `rev`   | последнее значение, раз в `stateMs` и при изменении |
| `POST /agent/v1/metrics`  | точки метрик узла и воркеров                                     | последние 600 точек в памяти, досылаются            |
| `POST /agent/v1/logs`     | записи журнала с уровня `log.forward` или `watch.logLevel`       | пачками раз в 1–2 с, последние N в памяти           |
| `POST /agent/v1/requests` | запрос воркера к бэкенду (§17)                                   | ответ в том же запросе, без повторов                |

```http
POST /agent/v1/events
[ { "id": "e-1", "worker": "report", "type": "report.done", "data": { … }, "at": 1791… } ]
→ 200 { "accepted": ["e-1"], "rejected": [ { "id": "e-2", "reason": "…" } ] }
```

- Тела: `results`, `events`, `metrics`, `logs` — массивы записей; `hello`, `state`, `requests` —
  объекты.
- Записи — пачками до 500 или 1 МБ, отправка сразу при появлении; пачки по одной и по порядку.
- Бэкенд принимает идемпотентно: уникальный ключ (`agent_id`, `id`); повтор — снова в
  `accepted`. Подтверждать лучше после записи в свою базу, обрабатывать — потом.
- `rejected` (неверная запись) агент не повторяет, причину пишет в журнал.

**`hello`:**

```jsonc
{ "agent": { "version": "1.0.0", "bootId": "…", "startedAt": 1791…, "updateMode": "self", "install": "systemd" },
  "host": { "os": "linux", "arch": "amd64", "hostname": "…" },
  "name": "node-01", "labels": { "zone": "eu" },
  "workers": [ { "name": "report", "version": "1.2.0", "release": true, "manifest": { … } } ] }
→ 200 { "status": "active", "serverTime": 1791…, "stateMs": 30000, "metricsMs": 10000 }
```

**`state`:**

```jsonc
{ "desiredRev": 18, "outbox": 0, "update": { "latest": "1.1.0", "checkedAt": 1791… },
  "workers": [ { "name": "report", "state": "running", "version": "1.2.0", "restarts": 0,
                 "health": { "ok": true, "busy": false, "message": "" },
                 "configs": { "settings": { "version": 7, "ok": true } } } ] }
```

**На связи** агент для бэкенда, пока открыт поток или был запрос за последние `3 × stateMs`.

## 10. Сборки и обновление

**Каталог сборок** — `manifest.json` и сами сборки: `{ version, publicKey?, artifacts: [{ os, arch,
file, sha256, signature }], workers?: [{ name, version, os, arch, file, sha256, signature,
stopTimeout?, command? }] }` (`artifacts` — сборки агента, `workers` — сборки воркеров; их
`stopTimeout` и `command` берёт `agent install --worker` для записи в `agent.yaml`). `file` — имя
файла в каталоге или ссылка `https://…`; `publicKey` — справочно: агент проверяет подписи только
своими ключами. Каталог собирает `agent manifest`.

**Подпись** — Ed25519 (base64) над строкой `agent-release/1\n<имя>\n<версия>\n<os>\n<arch>\n<sha256>`
(имя — `agent` или имя воркера, sha256 — hex строчными). Агент собирает строку сам, поэтому подпись
не подходит к другой сборке. Ключи проверки — вшитый при сборке агента и `update.publicKey`,
`update.publicKeys`; подпись принимается, если сходится с любым. Ключей нет —
`UPDATE_NOT_VERIFIED`; подпись или sha256 не сходятся — `UPDATE_FAILED`; `update.mode: disabled` —
`UPDATE_NOT_SUPPORTED`.

- **Агент** обновляет себя по `agent.update {version}` из своего каталога сборок (`update.releases`:
  релизы на GitHub, зеркало или папка на узле; `<адрес>/latest/download/manifest.json` — последняя
  версия, `<адрес>/download/v<версия>/` — сборки версии): перечитать свой файл настроек (не
  читается — `UPDATE_FAILED`), проверить подпись и sha256, сохранить текущий файл как `.prev`,
  заменить, перезапуститься. Итог присылает новая версия после `hello`; не вышла на связь за три
  запуска — возвращается `.prev`, итог — `UPDATE_FAILED`. Агент в контейнере (`update.mode:
  external`) себя не обновляет — `UPDATE_NOT_SUPPORTED`. Раз в `update.checkInterval` (по
  умолчанию 6 ч, `0s` — не проверять) агент смотрит последнюю версию каталога и сообщает её в
  `state.update`; ставит — только по команде.
- **Воркер со сборкой** (`release: true` в `agent.yaml`): `worker.update {worker, version, url,
  sha256, signature}` — сборка с бэкенда (`url` — путь от корня бэкенда, запрос с ключом агента,
  или ссылка `https://`) — файл или архив `.tar.gz` (распаковывается) в
  `<dataDir>/workers/<имя>/current`; замена воркера (новая сборка перед запуском выполняет свой `setup`, §11) с
  возвратом прежней, если `setup` не удался или новая сборка не зарегистрировалась (§13) с пульсом
  `ok: true` за 60 с после запуска (`UPDATE_FAILED`). Воркер без
  `release: true` — `WORKER_NOT_RELEASED`; уже обновляется — `BUSY`.

Бэкенд может раздавать каталог сборок воркеров проекта (`GET /agent/v1/releases/manifest.json` и
`GET /agent/v1/releases/<file>`, вход ключом агента не нужен): из него `agent install --worker`
ставит воркер вместе с агентом.

Добавить или удалить воркер бэкенд не может: это решает `agent.yaml` узла.

## Часть II. Агент ↔ воркер

Связь только внутри узла, через unix-сокет агента (`<dataDir>/run/agent.sock`, права 0600:
воркеры работают от пользователя агента), а каждого воркера агент узнаёт по его токену.

## 11. Запуск воркера

Агент запускает воркер по `agent.yaml` (команда, каталог, переменные) и передаёт ему окружение:

| Переменная           | Что                                                            |
| -------------------- | -------------------------------------------------------------- |
| `AGENT_SOCKET`       | путь к unix-сокету агента                                      |
| `AGENT_WORKER_TOKEN` | токен этого воркера: `Authorization: Worker <token>`           |
| `AGENT_WORKER_NAME`  | имя воркера в `agent.yaml`                                     |
| `WORKER_STATE_DIR`   | каталог для своих данных воркера, переживает обновления сборки |

- stdout и stderr агент пишет в файлы журнала воркера и передаёт бэкенду (`info` и `warn`).
- **Зависимости** — исполняемый файл `setup` в рабочем каталоге воркера (каталог сборки-архива
  или папка воркера). Агент выполняет его перед запуском воркера с тем же окружением, один раз на
  его содержимое (отметка — `.agent-setup` с sha256 файла `setup` и файлов зависимостей рядом:
  `requirements*.txt`, `pyproject.toml`, `package.json`, `go.mod`, `*.lock` и подобные): у сборки — один раз на версию, у папки — после
  изменения `setup` или файла зависимостей. Вывод — в журнал воркера; срок — `lifecycle.setupTimeout` (по умолчанию
  10 мин). Ошибка или срок — воркер не запускается, повтор с паузой; при `worker.update` — возврат
  прежней сборки. Время `setup` не входит в сроки регистрации и обновления. `setup` работает от
  пользователя агента: системные пакеты ставит `agent install --packages`; долгую установку лучше
  кешировать в `WORKER_STATE_DIR` или класть зависимости в саму сборку.
- **Уборка** — исполняемый файл `cleanup` рядом с `setup`: после остановки воркера, с его
  окружением, — убрать созданное воркером на узле (интерфейсы, правила, файлы). Его выполняют
  `agent uninstall` (`agent stop-workers --cleanup`), отзыв агента (§4) и удаление воркера из
  `agent.yaml` (новая установка с другим набором воркеров, правка настроек): тогда удаляется и его
  сборка с бэкенда; данные (`WORKER_STATE_DIR`) остаются до `agent uninstall --purge`. Нет файла —
  воркер ничего не убирает.
- **Остановка** — `SIGTERM` всей группе процессов воркера, через `stopTimeout` — `SIGKILL`.
- **Воркер переживает перезапуск и обновление агента:** процесс продолжает работать, после
  запуска агент находит его и ждёт переподключения (§13).

## 12. Маршруты сокета агента

Все — HTTP по `AGENT_SOCKET`, с `Authorization: Worker <token>`. Ответ с ошибкой — `{ code,
message }`: `401 UNAUTHORIZED` (токен), `403 AGENT_NOT_ACTIVE` (агент не `active`, §4 — воркер
не принимается), `409 WORKER_INVALID` (воркер не зарегистрирован — нужен `POST /register`),
`400 MESSAGE_INVALID`, `413 BODY_TOO_LARGE`, `422 COMMAND_UNDECLARED` /
`EVENT_UNDECLARED` / `REQUEST_UNDECLARED`, `503 OUTBOX_FULL`.

| Маршрут          | Что                                                         |
| ---------------- | ----------------------------------------------------------- |
| `POST /register` | манифест и версия воркера (§13)                             |
| `GET /stream`    | SSE вниз: `desired`, `command`, `cancel`, `watch` (§14–§16) |
| `POST /applied`  | итог применения настроек                                    |
| `POST /results`  | итог команды                                                |
| `POST /progress` | ход долгой команды                                          |
| `POST /events`   | события воркера                                             |
| `POST /health`   | пульс: самочувствие, занятость, метрики                     |
| `POST /requests` | запрос к бэкенду, ответ в том же запросе                    |

## 13. Регистрация воркера

```http
POST /register
{ "version": "1.2.0", "manifest": {
    "description": "Отчёты: сборка и выгрузка",
    "configs":  [ { "key": "settings", "schema": { … }, "description": "…" } ],
    "commands": [ { "type": "interface.restart", "schema": { … }, "description": "…" } ],
    "events":   [ { "type": "report.done", "schema": { … } } ],
    "requests": [ { "type": "report.lookup", "schema": { … } } ] } }
→ 200 {}
```

- Воркер регистрируется при каждом запуске и после переподключения (агент перезапущен); до
  регистрации агент считает его запускающимся и не принимает от него пульс, события и поток, не
  зарегистрировался за 60 с — `invalid` с причиной (процесс работает дальше).
- Манифест — что воркер умеет; агент сверяет по нему команды, события, запросы и ключи настроек и
  передаёт его бэкенду в `hello`. Схемы агент не проверяет — это делает бэкенд.

## 14. Настройки воркера — желаемое

Поток у воркера один: новый `GET /stream` закрывает прежний. В нём воркер получает
`event: desired`:

```text
event: desired
data: {"configs":{"settings":{"version":7,"data":{…}}}}
```

- Первым — сразу после подключения, затем при каждом изменении его части желаемого; всегда
  целиком. Ключи — только объявленные в `manifest.configs`.
- Воркер сходится к нему и сообщает итог по каждому изменённому ключу:

```http
POST /applied
[ { "key": "settings", "version": 7, "ok": true },
  { "key": "limits", "version": 2, "ok": false, "error": { "code": "CONFIG_REJECTED", "message": "…" } } ]
→ 200 {}
```

## 15. Команды воркеру

```text
event: command
data: {"id":"c-91","type":"report.build","args":{"period":"2026-01"},"deadline":1791…}
```

- Типы — только объявленные в `manifest.commands`; другое агент отклоняет сам
  (`COMMAND_UNDECLARED`).
- **Итог** — `POST /results [{ re, ok, result?, error? }]`, когда команда выполнена; долгая
  команда может идти часами.
- **Ход** — `POST /progress { re, progress, message? }` (0…1); агент передаёт его бэкенду событием
  `command.progress`.
- **Отмена** — `event: cancel` с `{ re }`; воркер прерывает команду и присылает итог `CANCELLED`.
- **Повтор** команды с тем же `id` (например, после переподключения) воркер не начинает заново,
  если она уже идёт или выполнена: присылает итог, когда он есть.
- Итог агент сразу пишет в очередь на диске и передаёт бэкенду с `re` команды бэкенда. Итог до
  4 МБ; больше — итог `BODY_TOO_LARGE`.
- Команды, ждущие итога, агент присылает снова при каждом подключении потока воркера.

## 16. Пульс и события

**Пульс** — раз в 10 с, а пока бэкенд наблюдает за узлом — с частотой метрик наблюдения (не
чаще раза в секунду), чтобы метрики воркеров в точках были свежими.

**Наблюдение** — агент передаёт воркерам наблюдение бэкенда (`watch`, §7) при открытии потока и
при каждом его изменении:

```text
event: watch
data: {"metricsIntervalMs":1000,"logLevel":"debug"}
```

`metricsIntervalMs` — частота точек метрик агента, `logLevel` — уровень журнала, который агент
передаёт бэкенду; наблюдения нет — `{}`. Кроме частоты пульса воркер может ответить своим:
подробнее писать журнал, чаще проверять своё.

```http
POST /health
{ "ok": true, "busy": false, "message": "", "metrics": { "peers": 12, "rxBytes": 1048576 } }
```

- `ok: false` — воркер нездоров (сообщение — в `message`).
- `busy: true` — идёт работа, которую нельзя прерывать: плановые перезапуск и обновление ждут.
- Пульса нет 30 с — агент считает воркер нездоровым; ещё 60 с — перезапускает его.
- `metrics` агент передаёт бэкенду в точках метрик узла.

**События:**

```http
POST /events
[ { "id": "…", "type": "report.done", "data": { … } } ]
→ 202 {}
```

Агент проверяет тип по манифесту, записывает события в очередь на диске и только потом отвечает;
очередь полна — `503 OUTBOX_FULL`. В пачке до 500 событий, `data` до 64 КБ, `id` — до 128
символов.

## 17. Запросы воркера к бэкенду

```http
POST /requests
{ "type": "report.lookup", "data": { … }, "timeoutMs": 10000 }
→ 200 { "ok": true, "data": { … } }   |   200 { "ok": false, "error": { … } }
```

Агент передаёт запрос `POST /agent/v1/requests` и возвращает ответ; связи нет или срок истёк —
ошибка `AGENT_OFFLINE` или `TIMEOUT`. Без повторов: решает воркер.

## Часть III. Агент на узле

## 18. Работа без бэкенда, локальный API, хранилище

- **Без бэкенда** (`server.url` не задан): воркеры работают, желаемое — из файлов
  `desired/<worker>/<key>.json` рядом с `agent.yaml` (версия ключа — время изменения файла;
  перечитываются по `SIGHUP`), события воркеров не хранятся, запросы к бэкенду — `AGENT_OFFLINE`.
- **Локальный API** — сокет `<dataDir>/run/admin.sock` (только владелец агента): `GET /status`,
  `GET /workers`, `POST /workers/{name}/restart`, `POST /workers/{name}/command`, `GET /logs`.
  Команды `agent status`, `agent logs --worker`, `agent restart --worker`, `agent command` ходят
  в него. Команда из локального API ждёт итога воркера и бэкенду не передаётся.
- **Сторож systemd:** `WatchdogSec=60`, `sd_notify` — зависший агент перезапускается.

**Хранилище агента** — один файл `<dataDir>/agent.db` (bbolt: транзакции, переживает падение,
ключи упорядочены). Разделы:

| Раздел     | Что                                                                                      |
| ---------- | ---------------------------------------------------------------------------------------- |
| `outbox`   | итоги и события для бэкенда по порядковому номеру; удаляются после `accepted`/`rejected` |
| `commands` | идущие и выполненные команды по `id`: от кого, итог, время; последние 10 000             |
| `desired`  | последнее желаемое состояние и его `rev`                                                 |
| `applied`  | итоги применения настроек воркерами по ключам                                            |

Приём события от воркера и запись в `outbox` — одна транзакция (воркер получает ответ после неё);
отметка «команда выполнена» и запись её итога в `outbox` — тоже одна. Размер очереди ограничен
`outbox.maxMessages`; освободившееся место файл переиспользует. Ключ агента —
`<dataDir>/credentials.json` (0600), отдельно от хранилища.

## 21. Бэкенд: минимальная реализация

```sql
agents          (id, name, secret_hash, pending_secret_hash, revoked, labels jsonb,
                 hello jsonb, state jsonb, last_seen_at)
agent_desired   (agent_id, rev, doc jsonb)
agent_commands  (seq bigserial, id uuid, agent_id, type, args jsonb, deadline_at,
                 status queued|done|failed|expired, result jsonb, created_at, finished_at)
agent_events    (agent_id, id, worker, type, data jsonb, at, received_at,
                 PRIMARY KEY (agent_id, id))
```

- **Состояние агента:** ответ на `hello` — `status: active` (или `pending`, пока агент не
  подтверждён); отозванному и удалённому агенту на любой запрос — `403 AGENT_REVOKED`: запись
  удалённого агента остаётся отозванной, иначе агент со старым ключом зарегистрируется заново.
- **Изменить желаемое / поставить команду:** запись в таблицу и `NOTIFY agents, '<agentId>'`;
  копия бэкенда, у которой открыт поток агента, отправляет новое.
- **Дождаться итога** (короткие команды из интерфейса): `NOTIFY agent_results` или опрос записи до
  N секунд; не дождались — `202 { commandId }`, итог — по сокету интерфейса.
- **Несколько копий:** любой `POST` принимает любая копия; поток держит одна; команды и желаемое
  доходят через NOTIFY.
