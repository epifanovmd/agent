# Как устроен агент

Агент — одна программа на узле. Она подключается к бэкенду, выполняет задачи и команды через
воркеры, применяет состояние, присылает метрики и обновляет себя. Своей предметной области у
агента нет: всё, что нужно проекту, — в воркерах. Формат сообщений — [sdk/spec](../sdk/spec/README.md),
как подключить агента к своему бэкенду и писать воркеры — [sdk/docs](../sdk/docs/README.md).

```
cmd/agent/          команды: run | cleanup | version | keygen | boot-guard | release-manifest
internal/
├── app/            сборка агента из частей ниже, перечитывание настроек, прокси
├── link/           связь с сервером: WebSocket, запасной HTTP, переподключение
├── outbox/         очередь важных сообщений на диске — хранятся, пока сервер не подтвердит
├── stream/         обычные сообщения: нумерация и короткий буфер в памяти
├── runtime/        главный цикл: статус, метрики, сведения об узле, остановка
├── worker/         запуск воркеров, обмен с ними, перезапуск, замена, уборка, воркеры из выпуска
├── cgroup/         ограничения ресурсов воркеров (cgroup v2)
├── jobs/           задачи: свободные места, выдача воркерам
├── commands/       команды: список разрешённых, вывод по мере работы, итог
├── state/          состояние: хранение на диске, повтор при ошибке
├── telemetry/      метрики узла, видеокарты (nvidia-smi), сведения об узле, показатели воркеров
├── update/         самообновление: проверка подписи, запасная копия, откат
├── identity/       регистрация по токену, ключ агента, смена ключа, ключ шифрования
├── config/         настройки: YAML и переменные окружения
└── logx/, backoff/ лог (и отправка его на сервер), паузы между повторами
sdk/go/message/     типы сообщений — общие для агента и Go-SDK
sdk/go/sealed/      запечатанные секреты в состоянии
```

Команды программы:

| Команда                                          | Что делает                                                            |
| ------------------------------------------------ | --------------------------------------------------------------------- |
| `agent [run] [-config agent.yaml]`               | работа (по умолчанию); SIGHUP — перечитать настройки                  |
| `agent cleanup [-config agent.yaml]`             | уборка воркеров перед удалением агента с узла, без сервера            |
| `agent version`                                  | версия                                                                |
| `agent keygen`                                   | пара ключей подписи выпуска                                           |
| `agent boot-guard ФАЙЛ`                          | откат версии, которая не вышла на связь (вызывает служба systemd)     |
| `agent release-manifest DIR VERSION [--worker…]` | `manifest.json` для сборок в каталоге (подпись — `AGENT_SIGNING_KEY`) |

## Как это работает

**Связь.** Соединение всегда открывает агент, поэтому входящие порты на узле не нужны: агент
работает за NAT. Сначала он пробует WebSocket (`/api/v1/agent-link`). Если WebSocket не проходит,
агент переходит на обычные HTTP-запросы, а раз в 10 минут снова пробует WebSocket. Сервер может
закрыть соединение с кодом-причиной, и агент поступает по нему:

- сервер перезапускается — переподключиться сразу;
- ключ агента отозван — зарегистрироваться заново, если есть токен;
- после смены ключа (`agent.rotateKey`) — подключиться с новым секретом, а если он не подошёл,
  с прежним;
- нужна более новая версия агента или сервера — ждать с растущей паузой;
- подключилась другая копия агента — подождать.

**Три вида сообщений.**

- **Обычные** — статус, метрики, прогресс, вывод команд. Их не страшно потерять: следующее
  всё равно придёт. Они нумеруются и недолго хранятся в памяти на случай обрыва.
- **Важные** — итоги задач, итоги команд, события, отчёт о применении состояния. Они
  записываются на диск и лежат там, пока сервер не подтвердит получение. Переживают и обрыв
  связи, и перезапуск агента.
- **Запросы с ответом** — например, свежие ссылки на файлы задачи.

**Без связи.** Задачи продолжают выполняться, итоги копятся на диске. После переподключения
агент сначала сообщает, какие задачи у него есть, включая завершённые без связи, а потом
досылает их итоги.

**Воркеры.** Воркер — дочерний процесс агента на любом языке из списка `workers` в настройках.
Агент говорит с ним строками JSON через отдельный канал (дескриптор 3). При запуске воркер
сообщает, что он умеет: очереди задач, команды, разделы состояния, показатели. Агент
подключает это к себе и сообщает серверу, что у него появились новые возможности. Дальше:

- задачи из этих очередей агент отдаёт воркеру;
- команды пересылает ему, а итог отправляет серверу как важное сообщение;
- состояние хранит у себя на диске и передаёт воркеру — после каждого запуска воркера и
  ещё раз в `state.resyncInterval` (по умолчанию 10 минут). Так воркер исправляет то, что на
  узле поменяли руками, даже если сервер ничего нового не присылал;
- показатели воркера добавляет к метрикам узла;
- события воркера отправляет серверу как важные сообщения.

Если два воркера назовут одинаковое имя, его получит первый. Имена на `agent.` и `worker.`
занимает сам агент.

Какие воркеры работают на узле, решают только настройки агента: сервер не может запустить
на узле свою программу.

**Перезапуск и замена воркера.**

- **Упал** — его задачи завершаются ошибкой `WORKER_CRASHED` (сервер повторит их), а агент
  перезапускает процесс с растущей паузой.
- **Замена** — по команде `worker.restart` (например, после того как файлы воркера обновили на
  диске) или по просьбе самого воркера. По умолчанию (`restart: rolling`) новая копия запускается рядом, а старая
  дорабатывает задачи и уходит: без простоя. `restart: stop-first` — сначала уходит старая,
  потом запускается новая. Это для воркеров, которые держат то, что не делится: порт,
  сетевой интерфейс, файл.
- **Остановка** — всё, что воркер создал на узле, остаётся; следующий запуск это подхватит.

**Метрики узла.** Агент присылает их раз в `metricsIntervalMs` (его задаёт сервер). Метрики
собираются группами, список групп — `telemetry.metrics`:

| Группа         | Что                                                                   | По умолчанию |
| -------------- | --------------------------------------------------------------------- | ------------ |
| `cpu`          | загрузка процессора                                                   | да           |
| `cpu.cores`    | загрузка по ядрам                                                     |              |
| `load`         | средняя нагрузка за 1, 5 и 15 минут                                   | да           |
| `memory`       | память: занято, всего, доступно                                       | да           |
| `swap`         | swap                                                                  | да           |
| `disk`         | корневая файловая система `/` и файловые системы из `telemetry.disks` | да           |
| `diskio`       | чтение и запись дисков: байт/с и операций/с                           |              |
| `network`      | сеть всего: приём, отдача, ошибки, отброшенные пакеты                 | да           |
| `interfaces`   | сеть по каждому интерфейсу                                            | да           |
| `conntrack`    | число отслеживаемых сетевых соединений и предел (Linux)               | да           |
| `sockets`      | TCP-соединения по состояниям                                          |              |
| `processes`    | число процессов и потоков                                             |              |
| `fds`          | открытые файлы и предел (Linux)                                       |              |
| `uptime`       | сколько узел работает                                                 | да           |
| `temperatures` | датчики температуры (где доступны)                                    |              |

Точные поля — [sdk/spec §6.2](../sdk/spec/README.md#62-статус-и-метрики). Кроме групп, агент
присылает видеокарты (через `nvidia-smi`, если он есть; `telemetry.gpu`) и показатели воркеров.

Без связи точки копятся (до `telemetry.backlog`, по умолчанию 720) и досылаются после
подключения с пометкой «досланная». Часы узла могут расходиться с часами сервера, поэтому агент
сообщает разницу, и сервер ставит каждой точке правильное время.

**Подписки сервера.** Пока кто-то смотрит на узел (например, открыта карточка агента в
интерфейсе), бэкенд подписывается на агента: «присылай это, так часто, столько времени».
Подписок может быть несколько, у каждой свой срок; сервер сводит их в одну и присылает агенту.
Подписка только добавляет, но не убирает:

- статус и метрики приходят чаще — с самой частой из настроек сервера и подписки;
- подписка на показатели воркера тоже ускоряет метрики — показатели едут в них;
- к группам из `telemetry.metrics` добавляются группы подписки (например, `diskio`, `sockets`);
- лог уходит подробнее — с более подробного из `log.forward` и уровня подписки.

Когда подписки истекают или их снимают, агент возвращается к своим настройкам. Подробно —
[sdk/spec §6.9](../sdk/spec/README.md#69-подписка-сервера).

**Сведения об узле.** ОС, процессор, диски, сетевые адреса, видеокарты, открытые порты. Агент
присылает их после каждого подключения и при изменении; проверяет раз в
`telemetry.inventoryInterval` (по умолчанию 10 минут).

**Несколько адресов и прокси.** В `server.urls` можно перечислить несколько адресов одного
бэкенда: агент подключается к первому доступному, а при отказе (сеть, нет ответа, ошибка 5xx)
переходит к следующему. Ключ агента один на все адреса. Запросы агента идут через HTTP-прокси
из `HTTPS_PROXY` / `HTTP_PROXY` (кроме адресов из `NO_PROXY`, localhost и петлевых адресов).

**Лог на сервер.** Агент отправляет на сервер записи своего лога и вывод воркеров — от уровня
`log.forward` (по умолчанию предупреждения и ошибки). Подписка сервера может на время попросить
подробнее. Без связи записи не копятся.

**Секреты в состоянии.** При первом запуске агент создаёт ключ шифрования
(`<dataDir>/encryption.key`) и сообщает открытую часть серверу. Бэкенд может запечатать секреты
в снимке для конкретного агента (`agents.seal`): в БД и на диске узла они лежат
зашифрованными, а агент раскрывает их только в памяти, перед передачей воркеру.

**Ограничения воркеров.** У воркера в `agent.yaml` можно задать `limits` (память, процессор,
число процессов) и `user`. Агент ставит ограничения через cgroup v2 — для этого установщик
пишет в службу `Delegate=yes`. Если cgroup недоступны, агент предупреждает в логе и запускает
воркер без ограничений.

**Связь без шифрования.** Если адрес сервера начинается с `http://` и это не localhost, агент
при старте пишет предупреждение: ключ агента и состояние (в нём бывают секреты) идут открытым
текстом.

**Остановка агента** (SIGTERM). Агент перестаёт брать задачи и даёт воркерам доработать
текущие (не дольше их `stopTimeout`). Потом отправляет последний статус и итоги и выходит.
Остановка ничего на узле не убирает.

**Удаление агента с узла — уборка.** `agent cleanup` по очереди запускает каждый воркер из
настроек и просит убрать за собой всё, что он создал: интерфейсы, правила, файлы. Потом
останавливает воркер. Связь с сервером для этого не нужна, и сервер запустить уборку не может.
`install.sh --uninstall` вызывает её сам.

## Кто чем управляет

**Узел** (`agent.yaml`) решает, что на нём работает: какие воркеры, с какими ограничениями, какие
встроенные команды доступны, какие метрики собирать. Сервер это поменять не может.

**Сервер** раздаёт задачи и команды, присылает состояние, задаёт частоту статуса и метрик,
подписывается на агента и обновляет агента и воркеры из выпуска.

**Агент → воркеру: контекст.** Сразу после регистрации и при каждом изменении агент сообщает
воркеру (`worker.context`):

- режим: обычная работа или только уборка (`agent cleanup`);
- сведения об агенте: id, имя, версия, метки;
- есть ли сейчас связь с сервером;
- действующую частоту метрик и подписки на показатели этого воркера — чтобы воркер готовил
  показатели не чаще и не реже, чем их ждут;
- с какого уровня лог сейчас уходит на сервер.

**Воркер управляет собой сам:**

- **здоровье** — сообщает «в порядке» или «не в порядке, потому что…». Агент показывает это в
  статусе воркера, а если воркер не в порядке, весь агент получает состояние `degraded`;
- **пауза** — просит не давать ему новых задач (всех или отдельных очередей) и потом снова
  давать. Начатые задачи он доделывает;
- **просьба о перезапуске** — агент заменяет воркер новой копией его обычным способом (`restart`),
  без статуса сбоя.

**Сервер управляет воркером:**

- `worker.pause` и `worker.resume` — та же пауза очередей, но со стороны сервера. Паузы сервера
  и воркера независимы: очередь работает, только когда её не держит ни один из них;
- `worker.restart` — заменить воркер новой копией; `worker.update` — обновить воркер из выпуска;
- **настройки воркера** — через его раздел состояния: воркер объявляет раздел (например,
  `example.node.config`), сервер присылает снимок с настройками, агент хранит его на диске и
  отдаёт воркеру после каждого запуска. Отдельного механизма настроек нет.

Встроенные команды агента — все, кроме выключенных в `commands.disabled`:

| Команда           | Что делает                                                                     |
| ----------------- | ------------------------------------------------------------------------------ |
| `agent.logs`      | последние строки лога агента и воркеров                                        |
| `agent.drain`     | не брать новые задачи, доделать текущие                                        |
| `agent.resume`    | снова брать задачи                                                             |
| `agent.restart`   | перезапустить агента, когда задачи доделаны                                    |
| `agent.update`    | обновить программу агента (только при `update.mode: self`)                     |
| `agent.rotateKey` | сменить секрет агента                                                          |
| `worker.restart`  | заменить воркер (или все) новой копией                                         |
| `worker.update`   | обновить воркер из выпуска (есть, только если такие воркеры есть в настройках) |
| `worker.pause`    | не давать воркеру новых задач (всех или отдельных очередей)                    |
| `worker.resume`   | снять паузу сервера                                                            |

Аргументы и итоги — [sdk/spec §6.4](../sdk/spec/README.md#64-команды-capabilitiescommands).

## Настройки

Файл YAML: `agent run -config agent.yaml` или переменная `AGENT_CONFIG`. В файле можно писать
`${ПЕРЕМЕННАЯ}` — подставится из окружения. Переменные окружения важнее файла. Длительности
пишутся как `30s`, `10m`.

| Ключ                          | Переменная                                           | По умолчанию                                                                            | Что                                                                                                                                                                                                                             |
| ----------------------------- | ---------------------------------------------------- | --------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `server.url`                  | `AGENT_SERVER_URL`                                   | —                                                                                       | адрес бэкенда (`https://…`); нужен он или `server.urls`                                                                                                                                                                         |
| `server.urls`                 | `AGENT_SERVER_URLS` (через запятую)                  | —                                                                                       | несколько адресов одного бэкенда: агент подключается к первому доступному, при отказе — к следующему                                                                                                                            |
| `server.transport`            | `AGENT_TRANSPORT`                                    | `auto`                                                                                  | `auto` (WebSocket, при неудаче HTTP) \| `ws` \| `http`                                                                                                                                                                          |
| `server.caFile`               | `AGENT_SERVER_CA_FILE`                               | —                                                                                       | свой корневой сертификат сервера (PEM), в дополнение к системным; воркеры получают путь в `AGENT_SERVER_CA_FILE` (Node — ещё в `NODE_EXTRA_CA_CERTS`) для загрузки файлов задач                                                 |
| `server.certFile`             | `AGENT_SERVER_CERT_FILE`                             | —                                                                                       | клиентский сертификат агента, если сервер его требует; задаётся вместе с `server.keyFile`                                                                                                                                       |

| `telemetry.inventoryInterval` | `AGENT_INVENTORY_INTERVAL`                           | `10m`                                                                                   | как часто проверять сведения об узле; `0` — не присылать их вовсе                                                                                                                                                               |
| `telemetry.excludeInterfaces` | `AGENT_TELEMETRY_EXCLUDE_INTERFACES` (через запятую) | `lo`, `veth`, `docker`, `br-`, …                                                        | какие сетевые интерфейсы не показывать (префиксы имён); заданный список заменяет стандартный                                                                                                                                    |
| `telemetry.backlog`           | `AGENT_TELEMETRY_BACKLOG`                            | `720`                                                                                   | сколько точек метрик копить без связи; `0` — не копить                                                                                                                                                                          |
| `commands.disabled`           | `AGENT_COMMANDS_DISABLED` (через запятую)            | —                                                                                       | встроенные команды, которые агент не объявит и не выполнит: `agent.logs`, `agent.drain`, `agent.resume`, `agent.restart`, `agent.update`, `agent.rotateKey`, `worker.restart`, `worker.update`, `worker.pause`, `worker.resume` |
| `update.mode`                 | `AGENT_UPDATE_MODE`                                  | `self`                                                                                  | `self` — обновляет себя сам (systemd); `external` — обновляют снаружи (контейнер); `disabled`                                                                                                                                   |
| `update.publicKey`            | `AGENT_UPDATE_PUBLIC_KEY`                            | —                                                                                       | открытый ключ проверки подписи выпуска (base64)                                                                                                                                                                                 |
| `state.resyncInterval`        | `AGENT_STATE_RESYNC`                                 | `10m`                                                                                   | как часто заново отдавать воркерам последнее состояние; `0` — не отдавать                                                                                                                                                       |
| `workers`                     | —                                                    | —                                                                                       | список воркеров, поля — в таблице ниже                                                                                                                                                                                          |

Прочие переменные окружения:

| Переменная                              | Что                                                                                   |
| --------------------------------------- | ------------------------------------------------------------------------------------- |
| `AGENT_CONFIG`                          | путь к файлу настроек, если не задан `-config`                                        |
| `HTTPS_PROXY`, `HTTP_PROXY`, `NO_PROXY` | HTTP-прокси для запросов агента к серверу (читаются при запуске; строчные имена тоже) |
| `AGENT_SIGNING_KEY`                     | закрытый ключ подписи для `agent release-manifest` (и `make release`)                 |
| `AGENT_BOOT_GUARD`                      | `external` — откат проверяет служба до запуска (`boot-guard`); ставит установщик      |

Поля воркера (`workers[]`):

| Поле          | По умолчанию | Что                                                                                                                                                                 |
| ------------- | ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `name`        | —            | имя воркера (обязательно)                                                                                                                                           |
| `command`     | —            | команда запуска списком, например `["python3", "report.py"]` (обязательно, кроме воркеров из выпуска)                                                               |
| `args`        | —            | аргументы, которые дописываются к `command` (или к файлу воркера из выпуска)                                                                                        |
| `dir`         | —            | рабочий каталог                                                                                                                                                     |
| `env`         | —            | переменные окружения воркера                                                                                                                                        |
| `replicas`    | `1`          | сколько копий процесса запускать                                                                                                                                    |
| `queues`      | все          | ограничить очереди, которые воркер обслуживает на этом узле                                                                                                         |
| `stopTimeout` | `30s`        | сколько ждать доработки задач при остановке                                                                                                                         |
| `restart`     | `rolling`    | способ замены: `rolling` (новая копия рядом, без простоя) \| `stop-first` (сначала уходит старая)                                                                   |
| `release`     | `false`      | `true` — воркер из выпуска: исполняемый файл ведёт агент (`<dataDir>/workers/<name>/current`), сервер обновляет его командой `worker.update`; `command` не задаётся |
| `limits`      | —            | ограничения на все копии вместе (cgroup v2): `memory` (`512M`, `2G`), `cpu` (`50%` — половина ядра, `200%` или `2` — два ядра), `pids`                              |
| `user`        | —            | запустить воркер от другого пользователя (агент должен работать от root)                                                                                            |

Пример:

```yaml
server:
  url: https://api.example.com
dataDir: /var/lib/agent
labels:
  zone: eu
workers:
  - name: report
    command: ["/opt/workers/report/report-worker"]
    restart: stop-first
    limits: { memory: 512M, cpu: "50%", pids: 256 }
  - name: sysinfo
    release: true
```

### Изменить настройки, не останавливая агента

Поправьте `agent.yaml` и выполните `systemctl reload agent` (агент получает SIGHUP): он
перечитает файл, не теряя очередь важных сообщений.

- **Сразу, без разрыва связи:** воркеры (новые запускаются, убранные доделывают задачи и
  уходят, изменённые заменяются, число копий меняется), лог, телеметрия, `state.resyncInterval`.
- **С переподключением:** имя, метки, `commands.disabled`, а также удалённый воркер или
  отключённые возможности — всё это входит в приветствие `hello`, поэтому агент подключается
  заново. Очередь важных сообщений и начатые задачи сохраняются. Добавленные воркеры и копии
  связь не рвут.
- **Только перезапуском** (`systemctl restart agent`): `server.*`, `dataDir`, `update.*`,
  `enroll.token`. Агент напишет в лог, какие ключи требуют перезапуска, а остальное применит.
- Если в файле ошибка, агент пишет её в лог и продолжает работать с прежними настройками.

Сервер `agent.yaml` менять не может: что работает на узле, решает только сам узел.

## Установка

**В контейнере.** Образ `ghcr.io/epifanovmd/agent:<версия>-python` (`deploy/Dockerfile`): агент,
Python и `agent_sdk`, `update.mode: external`, воркеров нет. Свой образ проекта строится
`FROM` него:

```dockerfile
FROM ghcr.io/epifanovmd/agent:<версия>-python
COPY workers/ /app/
COPY agent.yaml /etc/agent/agent.yaml
```

Адрес сервера — `AGENT_SERVER_URL`, токен — `AGENT_ENROLL_TOKEN`. Ключ агента и очередь сообщений
храните в томе `/var/lib/agent`. Обновление — новым образом.

**На сервер без Docker** — одной командой. Бэкенд отдаёт установщик сразу со своим адресом и
ключом проверки подписи:

```bash
curl -fsSL https://api.example.com/api/v1/agent-link/install.sh | sudo sh -s -- --token <токен>
```

Бэкенд на SDK собирает эту строку сам — `installCommand`, см. [sdk/docs](../sdk/docs/README.md).
Установщик скачивает с сервера сборку под эту машину и сверяет контрольную сумму. Можно и из
файла:

```bash
sudo sh deploy/install/install.sh --binary ./agent-linux-amd64 --server https://api.example.com --token <токен>
```

Нужны root, systemd и `curl` (если сборка берётся с сервера). Повторный запуск обновляет
программу и службу, не трогая ключ агента. Что получается:

| Что              | Где                                                   |
| ---------------- | ----------------------------------------------------- |
| программа        | `/opt/agent/bin/agent`                                |
| настройки        | `/etc/agent/agent.yaml` (создаётся, если его нет)     |
| токен и ключ     | `/etc/agent/agent.env`, доступ только владельцу       |
| данные           | `/var/lib/agent`                                      |
| служба           | `agent` (сама перезапускается при сбое)               |
| журнал установки | `/etc/agent/install-state`                            |
| настройки ядра   | `/etc/sysctl.d/90-agent.conf` (если задан `--sysctl`) |

В журнал установки записывается, что поставлено (пакеты, которых не было, настройки ядра с их
прежними значениями, режим остановки), чтобы при удалении точно вернуть как было.

Флаги установщика:

| Флаг                                                                                              | Что                                                                                                                                                                                                                                                      |
| ------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `--server URL`                                                                                    | адрес бэкенда; в установщик, который отдаёт бэкенд, он уже вписан                                                                                                                                                                                        |
| `--token ТОКЕН`                                                                                   | токен регистрации; сохраняется в `agent.env`                                                                                                                                                                                                             |
| `--token-file ПУТЬ`                                                                               | взять токен из файла, а не из командной строки (его не видно в списке процессов); вместо `--token`                                                                                                                                                       |
| `--public-key КЛЮЧ`                                                                               | открытый ключ проверки подписи выпуска; в установщик от бэкенда он уже вписан                                                                                                                                                                            |
| `--binary ПУТЬ`                                                                                   | поставить сборку из файла, а не скачивать с сервера                                                                                                                                                                                                      |
| `--name ИМЯ`                                                                                      | имя агента (по умолчанию — имя машины)                                                                                                                                                                                                                   |
| `--config ФАЙЛ`                                                                                   | свой `agent.yaml` вместо создаваемого                                                                                                                                                                                                                    |
| `--ca-file ПУТЬ`                                                                                  | свой корневой сертификат сервера: копируется в `/etc/agent/ca.pem` и прописывается в `server.caFile`                                                                                                                                                     |
| `--worker ИМЯ`                                                                                    | поставить воркер из выпуска сервера (контрольная сумма сверяется) и прописать его в создаваемый `agent.yaml` с `release: true`; можно несколько раз                                                                                                      |
| `--user ИМЯ`                                                                                      | от какого пользователя работает служба (по умолчанию `agent`, создаётся сам)                                                                                                                                                                             |
| _(без `--privileged`)_                                                                            | система для службы только для чтения, писать можно лишь в `/var/lib/agent`, `/opt/agent` и каталоги `--rw-path`                                                                                                                                          |
| `--rw-path ПУТЬ`                                                                                  | разрешить запись ещё в этот каталог (можно несколько раз)                                                                                                                                                                                                |
| `--privileged`                                                                                    | агент и воркеры — от root и без ограничений. Нужно воркерам, которые настраивают сам узел: сеть, firewall, системные файлы. Включайте, только если это действительно нужно                                                                               |
| `--packages "…"`                                                                                  | поставить системные пакеты для воркеров (apt, dnf, yum, apk, zypper), например `"jq curl"`                                                                                                                                                               |
| `--packages-apt`, `--packages-dnf`, `--packages-yum`, `--packages-apk`, `--packages-zypper` `"…"` | свои имена пакетов для этого менеджера — на узле с ним заменяют `--packages`                                                                                                                                                                             |
| `--sysctl КЛЮЧ=ЗНАЧЕНИЕ`                                                                          | настройка ядра для воркеров, например `vm.max_map_count=262144` (можно несколько раз)                                                                                                                                                                    |
| `--kill-mode process\|mixed`                                                                      | `mixed` (по умолчанию) — при остановке systemd по истечении срока завершает все процессы службы; `process` — только агента, а он сам останавливает воркеры: фоновые процессы воркеров переживают перезапуск агента. Запоминается для повторной установки |
| `--stop-timeout СРОК`                                                                             | сколько systemd ждёт остановки службы (по умолчанию `15min`)                                                                                                                                                                                             |
| `--uninstall [--purge]`                                                                           | удалить: сначала уборка воркеров (`agent cleanup`), потом служба, программа и настройки ядра из `--sysctl` с возвратом прежних значений; с `--purge` — ещё настройки, данные и пакеты, которые поставила эта установка                                   |

## Обновление

1. **Ключи.** `agent keygen` выдаёт пару ключей. Закрытый (`AGENT_SIGNING_KEY`) нужен только при
   сборке выпуска — держите его в секретах CI, не на бэкенде. Открытый
   (`AGENT_UPDATE_PUBLIC_KEY`) прописывается агентам и бэкенду (опция `publicKey`).
2. **Сборка.** `AGENT_SIGNING_KEY=… make release` кладёт в `dist/<VERSION>/` сборки
   linux/darwin × amd64/arm64, подписанный `manifest.json` и `install.sh`
   (`scripts/release.sh`). Сборки воркеров добавляются так: положите файлы
   `<name>-<version>-<os>-<arch>` в тот же каталог и выполните
   `scripts/go.sh release --worker NAME=VERSION[,restart=…][,stopTimeout=…]`. В CI выпуск попадает
   в образ `ghcr.io/epifanovmd/agent-dist:<версия>` (каталог `/dist/<версия>/`), который бэкенд
   может взять к себе `COPY --from=…`. Бэкенд раздаёт эти файлы агентам (опция `releasesDir`).
3. **Обновление узла.** Бэкенд отправляет агенту команду `agent.update` со ссылкой на сборку.
   Агент проверяет подпись и контрольную сумму, сохраняет текущую версию как запасную (`.prev`),
   ставит новую и перезапускается, когда задачи доработаны.
4. **Воркеры из выпуска.** Если в выпуске есть сборки воркеров, бэкенд обновляет их командой
   `worker.update` — с той же проверкой подписи. Агент ставит новую сборку, заменяет воркер и,
   если тот не поднялся, возвращает прежнюю. Обновить можно только воркер с `release: true` в
   `agent.yaml`; добавить или удалить воркер с сервера нельзя.
5. **Откат.** Если новая версия за три запуска так и не подключилась к серверу, агент возвращает
   прежнюю. Под systemd это делает прежняя версия ещё до запуска новой (`agent.prev boot-guard`),
   поэтому откат срабатывает, даже если новая версия падает сразу.
