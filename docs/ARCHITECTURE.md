# Как устроен агент

Агент — одна программа на узле. Она запускает воркеры и следит за ними, держит связь с бэкендом,
передаёт воркерам желаемое состояние и команды, собирает метрики узла и обновляет себя. Своей
предметной области у агента нет: всё, что нужно проекту, — в воркерах. Воркер — процесс на любом
языке, который сам подключается к сокету агента. Протокол бэкенд ↔ агент ↔ воркер —
[PROTOCOL.md](PROTOCOL.md); здесь — как он устроен в агенте, настройки, установка и обновление.

```
cmd/agent/        команды: run | install | uninstall | config | status | logs | restart | command |
                  stop-workers | pack | manifest | upgrade | version | boot-guard
protocol/         типы и константы протокола — публичный пакет (агент, клиент воркера, бэкенды на Go)
worker/           клиент воркера на Go — публичный пакет: регистрация, поток, итоги, пульс, события, запросы
internal/
├── app/          оркестратор: желаемое и команды воркерам, команды агенту, состояние, метрики, журнал,
│                 работа без бэкенда, локальный API, сигналы, сторож systemd
├── backend/      клиент бэкенда: hello, поток SSE (запасной путь — длинный опрос), отправка вверх, запросы
├── store/        хранилище agent.db (bbolt): очередь итогов и событий, журнал команд, желаемое, итоги настроек
├── workerapi/    сокет агента для воркеров: вход по токену, поток вниз, POST вверх, коды ошибок
├── worker/       процессы воркеров: запуск, подхват, регистрация и пульс, перезапуск, замена, сборки
├── sse/          поток Server-Sent Events: запись и чтение
├── identity/     регистрация по токену, ключ агента, смена секрета
├── config/       настройки агента: YAML (extends, envFiles), переменные AGENT_*, разница при перечитывании
├── sysmetrics/   метрики узла — в процессе агента
├── update/       самообновление: подпись, копия .prev, откат (boot guard); загрузка сборок воркеров
├── releases/     каталог сборок (manifest.json): каталог агента, бэкенд, папка; проверка новой версии
├── install/      agent install и agent uninstall: службы systemd, экземпляры, журнал установки
├── bundle/       архив папки агента (agent pack) и установка из него
├── logx/         лог агента: stderr, журнал по источникам, отправка бэкенду
└── backoff/, fsutil/   паузы между повторами, запись файлов через временный
test/e2e/         сквозные тесты (тег e2e): настоящий агент, воркеры-примеры, бэкенд в процессе теста
```

Команды программы:

| Команда | Что делает |
| --- | --- |
| `agent [run] [-config ФАЙЛ \| --env ИМЯ]` | работа (по умолчанию); SIGHUP — перечитать настройки, SIGUSR1 — перезапуск, SIGTERM и SIGINT — остановка |
| `agent install [--env ИМЯ] [флаги]` | поставить или обновить службу systemd (Linux; root или `--rootless` — служба пользователя): из архива, из папки агента или по флагам — раздел «Установка» |
| `agent pack [--env ИМЯ] [--platform …] [--with-env]` | архив папки агента для узла — раздел «Установка» |
| `agent upgrade [--check] [--version X] [--force]` | поставить новую версию агента из каталога сборок — раздел «Обновление» |
| `agent manifest DIR VERSION [--worker…]` | `manifest.json` для сборок в каталоге (подпись — `AGENT_SIGNING_KEY`) |
| `agent uninstall [--purge]` | удалить службу (Linux; root или службу пользователя); `--purge` — ещё настройки, данные и то, что ставила установка |
| `agent config check [-config ФАЙЛ \| --env ИМЯ]` | проверить настройки и показать итоговые значения |
| `agent status [--json]` | работает ли агент, связь, воркеры, последняя ошибка — через локальный API (код выхода 0 — работает) |
| `agent logs [-f] [-n N] [--worker ИМЯ]` | лог службы (`journalctl -u agent`): последние `N` записей (по умолчанию 100), `-f` — следить; `--worker` — журнал воркера из памяти агента |
| `agent restart [--worker ИМЯ] [--force]` | перезапустить работающего агента (SIGUSR1; службу запускает systemd снова; воркеры работают дальше) или воркер через локальный API |
| `agent command ВОРКЕР ТИП [JSON] [--timeout 30s]` | команда воркеру через локальный API; вывод — итог |
| `agent stop-workers [--cleanup]` | остановить воркеры, оставшиеся работать после остановки агента (агент не должен работать); `--cleanup` — затем их `./cleanup` |
| `agent version`, `agent help` | версия, список команд |
| `agent boot-guard ФАЙЛ` | откат версии, которая не вышла на связь (вызывает служба systemd) |

У `status`, `logs`, `restart`, `command`, `stop-workers` и `config check` есть `-config`, `--env` и
`--instance` — чей агент (раздел «Настройки»).

## Как это работает

`internal/app` собирает агента из частей: открывает хранилище, поднимает сокет агента для воркеров
и локальный API, запускает воркеры (`internal/worker`), связь с бэкендом (`internal/backend`) и
циклы состояния, метрик, журнала и проверки новой версии. Без связи и без бэкенда воркеры
работают по последнему желаемому.

### Связь с бэкендом

Соединение всегда открывает агент, поэтому входящие порты на узле не нужны: агент работает за NAT,
через HTTP-прокси и TLS. Маршруты, ответы и пределы — [PROTOCOL.md §3–§9](PROTOCOL.md#3-адреса-и-ответы).

- **Состояние агента** (`internal/lifecycle`, `<dataDir>/status.json`, [PROTOCOL.md
  §4](PROTOCOL.md#4-регистрация-и-ключ)): `pending` — ждёт регистрации и подтверждения бэкендом,
  воркеры не запускаются, сокет агента их не принимает (`403 AGENT_NOT_ACTIVE`); `active` — бэкенд
  подтвердил агента ответом на `hello`, воркеры работают и без связи; `revoked` — бэкенд ответил
  `403 AGENT_REVOKED`: воркеры останавливаются и выполняют `./cleanup`, связь прекращается и после
  перезапуска не возобновляется. Вернуть отозванного — новая установка с токеном (`agent install
  --token`): прежний ключ и состояние забываются. Без бэкенда агент сразу `active`. Состояние — в
  `agent status`.
- **Регистрация.** Ключа агента (`<dataDir>/credentials.json`) нет — агент регистрируется по
  `enroll.token`, повторяя, пока бэкенд недоступен. Отклонённый токен или его отсутствие — ошибка в
  журнал и `agent status`.
- **Сессия** — `POST /hello` (версия, узел, имя, метки, воркеры с манифестами), затем поток вниз
  `GET /stream?after=<seq>`: желаемое и команды. Поток не отдал `: ok` за 10 с (прокси буферизует
  ответ) — агент переходит на длинный опрос `GET /poll`. Тишина в потоке дольше 45 с — обрыв.
  Ответ на `hello` задаёт частоты состояния (`stateMs`) и метрик (`metricsMs`).
- **Вверх** (uplink) отправляется всё, что ждёт, пока есть связь, по порядку: новый `hello`, если
  он изменился (настройки, регистрация воркера), итоги, события, последнее состояние, метрики,
  журнал. Итоги и события берутся из очереди на диске пачками до 500 записей или 1 МБ и удаляются
  после `accepted` или `rejected`. Новое в очереди будит отправку сразу.
- **Повторы** — пауза 1 с → 60 с (×2, ±20 %), `Retry-After` — не раньше. Сессия продержалась
  минуту — пауза снова с начала. Другой `4xx` — ошибка протокола: запись в журнал, данные не
  повторяются.
- **`401`** — сначала повтор с прежним секретом, если идёт смена ключа (ниже); иначе регистрация
  заново, если есть токен; иначе ожидание с паузой и журнал.
- **`403 AGENT_REVOKED`** — агент `revoked` (выше): воркеры останавливаются с уборкой, связь
  прекращается насовсем.
- **Смена ключа** (`agent.rotateKey`) — `internal/identity` создаёт ожидающий секрет и сохраняет его
  в `credentials.json`, итог — его хеш. Запросы текущей сессии идут с заголовком, принятым при её
  `hello`; доставив итоги, агент переподключается с новым секретом. Бэкенд принял его в `hello` —
  он становится основным; не принял (`401`) — агент возвращается к прежнему.
- **На связи** агент, пока открыт поток или идёт длинный опрос; это видно в `agent status`.
- **Запросы воркеров к бэкенду** — `POST /requests` в той же сессии, без повторов; связи нет —
  сразу `AGENT_OFFLINE`, срок истёк — `TIMEOUT` (по умолчанию 30 с, не больше 5 минут).

### Хранилище

Всё, что должно пережить обрыв связи и перезапуск, — в одном файле `<dataDir>/agent.db`
(`internal/store`, bbolt: транзакции, переживает падение). Повреждённый файл (сбой диска)
агент откладывает как `agent.db.broken-<время>` и начинает с чистого — с ошибкой в журнале:
желаемое придёт от бэкенда снова.

| Раздел | Что |
| --- | --- |
| `outbox` | итоги команд и события воркеров по порядку, с индексом по `id`: повтор того же `id` не записывается второй раз |
| `commands` | журнал команд бэкенда по `id`: идущие и выполненные с итогом; последние 10 000 |
| `desired` | последнее желаемое состояние и его `rev` |
| `applied` | итоги применения настроек воркерами по ключам |
| `meta` | `seq` последней полученной команды — его агент передаёт в `?after=` |

Приём события от воркера и запись его в очередь — одна транзакция: воркер получает ответ после
неё. Отметка «команда выполнена» и запись её итога в очередь — тоже одна. В очереди не больше
`outbox.maxMessages` (10 000) событий: когда она полна, воркер получает `503 OUTBOX_FULL`; итоги
команд принимаются всегда.

### Желаемое и настройки воркеров

Желаемое (`desired`) агент сохраняет в хранилище и передаёт каждому воркеру его часть — только
ключи из `manifest.configs` воркера — событием `desired` в его поток: при открытии потока и при
изменении части ([PROTOCOL.md §14](PROTOCOL.md#14-настройки-воркера--желаемое)). Итоги
`POST /applied` записываются в раздел `applied` и уходят бэкенду в состоянии
(`workers[].configs`): у каждого ключа — версия и `ok` (нет `ok` — ещё применяется). Ключ, которого
нет в манифесте воркера, в состоянии — `CONFIG_REJECTED`. Наблюдение (`watch`) из желаемого
применяется сразу и снимается само в `until`.

### Команды агенту

Команда бэкенда сначала записывается в журнал команд (`internal/app/commands.go`): новая
выполняется, выполненная — её итог снова в очередь, идущая — ничего. Истёк `deadline` до начала —
итог `EXPIRED`. Идущие команды переживают перезапуск агента: при запуске он продолжает их по
журналу (`agent.update` — завершает итогом новой версии или `UPDATE_FAILED`).

| Команда | Что делает |
| --- | --- |
| `worker.command` | команда воркеру с тем же `id`; итог — от воркера |
| `worker.cancel` | отменить идущую команду воркера (`event: cancel` в его поток) |
| `worker.restart` | заменить процесс воркера; итог — после регистрации нового |
| `worker.update` | новая сборка воркера с возвратом прежней (только `release: true`) |
| `agent.update` | новая версия агента из его каталога сборок — раздел «Обновление» |
| `agent.rotateKey` | новый секрет агента |
| `agent.logs` | последние записи журнала агента или воркера (по умолчанию 200, не больше 5000) |

Аргументы, итоги и коды — [PROTOCOL.md §8](PROTOCOL.md#8-команды-агенту).

**Команды воркерам** (`internal/app/workers.go`). Тип не из `manifest.commands` — итог
`COMMAND_UNDECLARED` без передачи воркеру. Воркер не запущен или не на связи — команда ждёт в памяти
и уходит, когда он откроет поток; при каждом открытии потока агент присылает все команды, ждущие
итога. Срок — меньший из `deadline` и `timeoutMs`; истёк — агент отправляет воркеру `cancel` и
пишет итог `TIMEOUT`. Итог больше 4 МБ — `BODY_TOO_LARGE`. Ход (`POST /progress`) уходит бэкенду
событием `command.progress`.

### Воркеры

Воркер — процесс из списка `workers` в настройках. Какие воркеры работают на узле, решает только
`agent.yaml`: бэкенд не может запустить на узле свою программу, добавить или удалить воркер.

**Запуск.** Агент запускает воркер в его каталоге со своим сеансом и группой процессов и передаёт
`AGENT_SOCKET` (сокет агента), `AGENT_WORKER_TOKEN` (токен этого запуска), `AGENT_WORKER_NAME` и
`WORKER_STATE_DIR` (`<dataDir>/state/<имя>`, 0700 — данные воркера, переживают обновления сборки).
Копия воркера всегда одна.

**Сокет агента** (`internal/workerapi`) — HTTP по unix-сокету `<dataDir>/run/agent.sock` (0600;
слишком длинный путь для сокета — каталог во временном каталоге системы). Воркера агент узнаёт по
токену (`Authorization: Worker <token>`). Маршруты — [PROTOCOL.md §12](PROTOCOL.md#12-маршруты-сокета-агента).
Поток у воркера один: новый `GET /stream` закрывает прежний; не успевает читать (в очереди
256 событий) — поток закрывается, воркер переподключается и получает всё заново. Ошибки — `{code,
message}` с HTTP-кодом: `401 UNAUTHORIZED`, `400 MESSAGE_INVALID`, `413 BODY_TOO_LARGE`,
`404 WORKER_UNKNOWN`, `409 WORKER_INVALID` (нужен `POST /register`), `409 WORKER_UNAVAILABLE`,
`422 COMMAND_UNDECLARED` / `EVENT_UNDECLARED` / `REQUEST_UNDECLARED`, `503 OUTBOX_FULL`.

**Регистрация и пульс.** Воркер регистрируется (`POST /register`: версия и манифест) после каждого
запуска и переподключения; до этого `state: starting`, пульс, события и поток не принимаются. Новый
манифест — новый `hello`. Не зарегистрировался за 60 с — `state: invalid` с причиной: процесс
работает, но настроек и команд не получает. Пульс (`POST /health`) — раз в 10 с: самочувствие,
`busy` и метрики воркера. Наблюдение бэкенда агент передаёт воркерам в потоке (`event: watch`):
пока за узлом наблюдают, пульс идёт с частотой метрик, и метрики воркеров в точках свежие (пакет
`worker` делает это сам, свою реакцию воркер задаёт в `Options.Watch`). Пульса нет 30 с — воркер нездоров (`health.ok: false`), ещё 60 с —
завис: агент завершает его и перезапускает как упавший.

**Жизнь воркера.** Сроки — постоянные агента; в настройках воркера задаются только
`lifecycle.stopTimeout` и `lifecycle.setupTimeout`.

- **Зависимости** — `./setup` в рабочем каталоге воркера (каталог сборки-архива или папка),
  если такой исполняемый файл есть: перед запуском процесса, с окружением воркера, вывод — в его
  журнал. Отметка `.agent-setup` рядом — sha256 `setup` и файлов зависимостей (`requirements*.txt`, `pyproject.toml`, `package.json`, `go.mod`, `*.lock` и подобные):
  повторные запуски его не выполняют, у сборки он выполняется один раз на версию, у папки — после
  изменения `setup` или файла зависимостей. Не уложился в
  `setupTimeout` или вышел не с 0 — воркер не запускается (повтор с паузой), при `worker.update` —
  возврат прежней сборки. Выполняется на месте, а не до замены сборки: окружения вроде venv
  хранят абсолютные пути. Время `setup` в сроки регистрации и обновления не входит.
- **Уборка** — `./cleanup` рядом с `setup`: убрать созданное воркером на узле после его остановки.
  Выполняют `agent uninstall` (через `agent stop-workers --cleanup`), отзыв агента (`revoked`) и
  удаление воркера из настроек (`worker.Retire`: новая установка с другим набором воркеров, правка
  `agent.yaml` — сразу или при следующем запуске агента по файлу процесса воркера); у воркера со
  сборкой с бэкенда удаляется и сборка (`current`, `previous`). Данные воркера остаются до
  `agent uninstall --purge`.

- **Вышел** с кодом не 0, убит сигналом или завис — перезапуск с растущей паузой (1–30 с,
  `state: backoff`), без предела числа перезапусков; проработал минуту — пауза снова с начала.
  Вышел сам с кодом 0 — остаётся остановленным (`state: stopped`) до `worker.restart` или изменения
  его настроек.
- **Занят** — пульс с `busy: true`. Плановая замена (`worker.restart`, `worker.update`, изменённые
  настройки воркера) ждёт окончания работы, но не дольше 24 ч; в состоянии — `pending: restart` или
  `update`; итог команды — после замены. `force: true` — заменить сразу. От перезапуска зависшего
  `busy` не защищает.
- **Замена** — сначала уходит прежний процесс, потом запускается новый (с новым токеном).
- **Остановка** — SIGTERM всей группе процессов; не вышел за `stopTimeout` — SIGKILL. Потомков,
  переживших воркер, агент завершает. Остановка ничего на узле не убирает.

**Воркер переживает агента.** Перезапуск агента (`agent.update`, `agent restart`) и его остановка
(SIGTERM: `systemctl stop`, `systemctl restart`, Ctrl+C) воркер не трогают: долгая работа идёт
дальше. О каждом запущенном процессе агент пишет `<dataDir>/processes/<имя>.json` (pid, время
запуска процесса по данным системы, токен, версия сборки, отпечаток настроек, места чтения
вывода). Запускаясь, агент подхватывает живой процесс: pid жив и время его запуска то же (pid,
выданный системой другому процессу, не подходит). Подхваченный воркер переподключается к сокету
агента с прежним токеном и регистрируется заново; если его настройки или сборка с тех пор
изменились — плановая замена. Процесса нет или он чужой — обычный запуск; процесс воркера, которого
нет в настройках, агент останавливает. Воркеры агента в контейнере (`update.mode: external`) всегда
останавливаются вместе с ним. Воркеры, оставшиеся после остановки агента, останавливает
`agent stop-workers` (его вызывает и `agent uninstall`). Процесс воркера, который агент не может
ни подхватить, ни остановить (другого пользователя), агент второй раз не запускает: воркер —
`invalid` с причиной, попытка повторяется каждые 10 с.

**Окружение воркера.** Из окружения агента воркер получает только обычные переменные (`PATH`,
`HOME`, `USER`, `LOGNAME`, `SHELL`, `LANG`, `LANGUAGE`, `LC_*`, `TZ`, `TMPDIR`, `TERM`, переменные
прокси, `SSL_CERT_FILE`, `SSL_CERT_DIR`); переменные `AGENT_*` агента (например, токен
регистрации) — никогда. Воркер работает от того же пользователя, что и агент. `env` воркера
важнее всего.

**Вывод воркера.** stdout и stderr воркера — файлы `<dataDir>/logs/<имя>.log` и `<имя>.err.log`
(не каналы агента: воркер переживает его перезапуск). Агент читает их и пишет строки в свой лог и
журнал воркера (stdout — `info`, stderr — `warn`). Подхватив воркер, агент продолжает чтение с
места, где остановился прежний, — строки, написанные без агента, тоже попадают в журнал. Файл
больше 10 МБ агент копирует в `.1` (прежняя копия удаляется) и очищает. Строка длиннее 16 КБ
обрезается.

**Сборка воркера** (`release: true`) — в `<dataDir>/workers/<имя>/current` (файл или каталог
распакованного архива). `worker.update` скачивает сборку, сверяет sha256 и подпись, откладывает
текущую как `previous` и заменяет воркер; новая не зарегистрировалась с пульсом `ok: true` за 60 с —
возвращается прежняя, итог `UPDATE_FAILED` ([PROTOCOL.md §10](PROTOCOL.md#10-сборки-и-обновление)).

### Состояние, метрики, журнал

- **Состояние** (`POST /state`) — применённый `rev`, длина очереди, новая версия агента, воркеры:
  `state`, версия, перезапуски, пульс, `pending`, итоги настроек. Уходит раз в `stateMs` (по
  умолчанию 30 с) и при изменении — несколько изменений подряд одним.
- **Метрики** — точка раз в `metricsMs` (по умолчанию 10 с; при `watch` — чаще, не чаще раза в
  секунду): метрики узла и `metrics` из последнего пульса каждого воркера. Без связи в памяти
  держатся последние 600 точек.
- **Метрики узла** собирает `internal/sysmetrics` в процессе агента — в отдельной горутине со
  сроком 10 с: зависшее чтение системы не задерживает остальное, прошлый сбор не закончен — точка
  без метрик узла. Температуры на macOS читает дочерний процесс (служебная команда `agent sensors`).
  Группы: `cpu` (всего и по ядрам), `load` (1, 5, 15 минут), `memory`, `swap`, `disk` (корневая
  файловая система `/`), `network` (приём, отдача, ошибки, отброшенные пакеты), `interfaces` (по
  интерфейсам, без петли, контейнеров, мостов и служебных), `conntrack` (Linux), `uptime`. Поля —
  пакет `protocol` (`HostMetrics`).
- **Журнал** (`internal/logx`) — лог агента в stderr и в память: последние `log.buffer` (5000)
  записей агента и каждого воркера — для `agent.logs` и `agent logs --worker`. Бэкенду записи уходят
  пачками раз в секунду от уровня `log.forward` (по умолчанию предупреждения и ошибки) или
  `watch.logLevel`; без связи ждут последние 5000.

### Работа без бэкенда

`server.url` не задан (`internal/app/local.go`) — связи нет, воркеры работают. Желаемое — из файлов
`desired/<воркер>/<ключ>.json` рядом с файлом настроек (без файла настроек — в `dataDir`): значение
— JSON, версия ключа — время изменения файла; файлы перечитываются по SIGHUP. События воркеров не
хранятся, запросы к бэкенду — `AGENT_OFFLINE`, состояние и метрики не отправляются; управление —
через локальный API.

### Локальный API

Сокет `<dataDir>/run/admin.sock` (0600 — только пользователь агента; `internal/app/admin.go`):

| Маршрут | Что |
| --- | --- |
| `GET /status` | агент (pid, версия, имя, `agentId`, бэкенд, связь, отзыв, последняя ошибка) и состояние |
| `GET /workers` | состояние воркеров |
| `POST /workers/{name}/restart[?force=true]` | заменить воркер; ответ — после регистрации нового |
| `POST /workers/{name}/command` | `{type, args?, timeoutMs?}` — команда воркеру, ответ — итог (срок по умолчанию 30 с) |
| `GET /logs?worker=&lines=` | последние записи журнала агента или воркера |

Им пользуются `agent status`, `agent logs --worker`, `agent restart --worker` и `agent command`.
Команда из локального API бэкенду не передаётся и в журнал команд не пишется; разрыв соединения
клиентом отменяет её у воркера.

### Сигналы, служба, остановка

- **SIGHUP** (`systemctl reload`) — перечитать настройки (раздел «Изменить настройки»).
- **SIGUSR1** (`agent restart`) — выход для перезапуска менеджером службы; воркеры работают дальше.
- **SIGTERM, SIGINT** — остановка; воркеры работают дальше, следующий запуск их подхватывает (в
  контейнере — останавливаются вместе с агентом). Остановка ничего на узле не убирает.
- **Сторож systemd** (`internal/app/notify.go`) — служба `Type=notify`: агент сообщает `READY=1`,
  когда сокеты открыты, и `WATCHDOG=1` вдвое чаще `WatchdogSec` (60 с); зависший агент systemd
  перезапускает. Без `NOTIFY_SOCKET` (не под systemd) — ничего.
- **Один агент на каталог данных.** `agent run` и `agent stop-workers` держат блокировку
  `<dataDir>/agent.lock`: второй агент с тем же `dataDir` не запускается («агент с этим dataDir уже
  запущен»). По ней же `agent status` узнаёт, что агент запущен, и спрашивает `GET /status`
  (срок 10 с); код 0 — работает и отвечает, — так его использует `HEALTHCHECK` в Docker. Ошибка, с
  которой агент завершился в последний раз, — `<dataDir>/agent.error`: её показывает `agent status`.
- **Прокси.** Запросы к бэкенду идут через HTTP-прокси из `HTTPS_PROXY` / `HTTP_PROXY` (кроме адресов
  из `NO_PROXY`, localhost и петлевых адресов), прочитанных при запуске; к каталогу сборок агента —
  так же.
- **Связь без шифрования.** `http://` в `server.url` — только с `server.allowInsecure: true`; агент
  тогда при старте пишет предупреждение: ключ агента и данные идут открытым текстом.

## Кто чем управляет

**Узел** (`agent.yaml`) решает, что на нём работает: какие воркеры, можно ли обновляться. Бэкенд это
поменять не может.

**Бэкенд** задаёт частоты состояния и метрик (ответ на `hello`), присылает желаемое (настройки
воркеров, наблюдение) и команды (таблица в разделе «Команды агенту»).

## Настройки

Настройки — файл YAML и переменные окружения `AGENT_*`; переменные важнее файла. Обязательного
нет: без `server.url` агент работает без бэкенда, для первого подключения к бэкенду нужен токен
регистрации (`enroll.token`). Поэтому агента можно запустить вообще без файла:
`AGENT_SERVER_URL=… AGENT_ENROLL_TOKEN=… agent run`.

Где агент ищет файл:

1. флаг `-config ФАЙЛ`, или `--env ИМЯ` — файл `agent.ИМЯ.yaml` в папке агента (см. ниже);
2. `--instance ИМЯ` — настройки экземпляра на узле (`/etc/agent-ИМЯ/agent.yaml`);
3. переменная `AGENT_CONFIG`;
4. настройки экземпляра, чья это программа (`/opt/agent-ИМЯ/bin/agent`, `~/.agent/bin/agent`);
5. `agent.yaml` в папке агента — рядом с программой, затем в текущем каталоге;
6. `~/.agent/agent.yaml` агента пользователя, иначе файл по умолчанию, если он есть, —
   `/etc/agent/agent.yaml` на Linux и `~/.agent/agent.yaml` на macOS.

Папка агента — каталог, где рядом лежат программа и её настройки. У программы, поставленной
службой (`/opt/agent…/bin/agent`), папки нет: её настройки — в `/etc`. Каталог данных по умолчанию
— `/var/lib/agent` на Linux и `~/.agent/data` на macOS.

- `agent config check [-config ФАЙЛ | --env ИМЯ]` проверяет настройки так, как их прочитает агент:
  цепочку файлов (`extends`), файлы переменных (`envFiles`), `agent.env` рядом с файлом (его читает
  служба) и переменные окружения. Ошибки разметки и типов показывает с файлом и номером строки,
  ошибки значений — с именем ключа, неизвестные поля (опечатки) — замечаниями (о них агент пишет
  предупреждение в свой журнал при запуске и при перечитывании настроек), а если всё в порядке,
  печатает итоговые значения (токен скрыт). Если агент ещё не зарегистрирован, а токена нет, —
  тоже замечание.

В файле можно писать `${ПЕРЕМЕННАЯ}` — подставится из окружения или из файлов переменных.
Длительности пишутся как `30s`, `10m`.

### Папка агента

Папка агента — программа, её настройки и воркеры в одном месте; её можно положить в репозиторий
проекта (программа и секреты в git не попадают): программа `agent`, `agent.yaml` — настройки
для этой машины (`./agent run` читает его без флагов), `agent.<окружение>.yaml` поверх него
(`extends`, например `agent.prod.yaml` для боевых узлов), файлы переменных (`.env`, `envFiles`) и
воркеры проекта в `workers/`.

Воркер проекта — папка в `workers/` с исполняемым `run` и файлом `VERSION`, в `agent.yaml` —
`- path: workers/<имя>`. Как воркер устроен внутри, решает проект: агенту нужен только протокол
воркера ([PROTOCOL.md, часть II](PROTOCOL.md#часть-ii-агент--воркер)). Примеры воркеров на Python
(без библиотек) и на Go (пакет `worker`) — `examples/workers`.

### Несколько файлов: `extends` и `envFiles`

Настройки для разных окружений не повторяют друг друга: общий файл и поверх него — файл окружения.

```yaml
# agent.yaml — общее: воркеры, журнал
workers:
  - name: example
    command: ["./run"]
    dir: workers/example
```

```yaml
# agent.prod.yaml — поверх agent.yaml
extends: agent.yaml
envFiles: [.env.prod] # KEY=VALUE: AGENT_ENROLL_TOKEN=…, AGENT_SERVER_URL=…
server:
  url: ${AGENT_SERVER_URL}
workers:
  - name: example # тот же воркер: env дописывается к общему
    env: { EXAMPLE_MODE: prod }
```

`agent run --env prod` (или `-config agent.prod.yaml`) читает сначала `agent.yaml`, затем
`agent.prod.yaml`:

- словари сливаются по ключам, списки заменяются целиком, воркеры (`workers`) сливаются по имени:
  воркер с тем же `name` дополняется, новый добавляется в конец; цепочка — до 8 файлов;
- `envFiles` — файлы `KEY=VALUE` (как у `agent.env`): из них берутся `${ИМЯ}` и переменные `AGENT_*`;
  окружение процесса важнее их, более поздний файл (в списке и в цепочке) — важнее раннего; файла
  нет — замечание, не ошибка;
- относительные пути — от файла, в котором записаны: `extends`, `envFiles`, `dataDir`,
  `server.caFile`, `workers[].dir`, `workers[].path`.

| Ключ | Переменная | По умолчанию | Что |
| --- | --- | --- | --- |
| `server.url` | `AGENT_SERVER_URL` | — | адрес бэкенда (`https://…`); не задан — работа без бэкенда |
| `server.allowInsecure` | `AGENT_SERVER_ALLOW_INSECURE` | `false` | разрешить `http://` (стенд, локальная сеть) |
| `server.caFile` | `AGENT_SERVER_CA_FILE` | — | свой корневой сертификат сервера (PEM), в дополнение к системным |
| `outbox.maxMessages` | `AGENT_OUTBOX_MAX_MESSAGES` | `10000` | сколько событий воркеров очередь на диске держит без связи (1–1000000); полна — события отклоняются |
| `dataDir` | `AGENT_DATA_DIR` | `/var/lib/agent` (macOS — `~/.agent/data`) | ключ агента, хранилище, сокеты, процессы, вывод и данные воркеров, сборки воркеров |
| `name` | `AGENT_NAME` | имя машины | имя агента (до 128 символов) |
| `labels` | `AGENT_LABELS` (`k=v,…`) | — | метки агента (до 64; ключ и значение — до 256 символов); метки из переменной добавляются к меткам из файла |
| `enroll.token` | `AGENT_ENROLL_TOKEN` | — | токен регистрации; нужен только до первой регистрации |
| `log.level` | `AGENT_LOG_LEVEL` | `info` | уровень лога в stderr: `debug`, `info`, `warn`, `error` |
| `log.format` | `AGENT_LOG_FORMAT` | `text` | `text` \| `json` (для систем сбора логов) |
| `log.forward` | `AGENT_LOG_FORWARD` | `warn` | какие записи лога агента и воркеров отправлять бэкенду: `off`, `error`, `warn`, `info`, `debug` |
| `log.buffer` | `AGENT_LOG_BUFFER` | `5000` | сколько последних записей журнала агент помнит — у себя и у каждого воркера (100–5000) |
| `update.mode` | `AGENT_UPDATE_MODE` | `self` | `self` — обновляет себя сам (systemd); `external` — обновляют снаружи (контейнер); `disabled` — не обновляться |
| `update.publicKey` | `AGENT_UPDATE_PUBLIC_KEY` | — | открытый ключ проверки подписи сборок (base64); действует вместе с ключом, вшитым при сборке |
| `update.publicKeys` | `AGENT_UPDATE_PUBLIC_KEYS` (через запятую) | — | ещё ключи проверки (base64): подпись принимается, если сходится с любым — вшитым, `publicKey` или этими |
| `update.releases` | `AGENT_UPDATE_RELEASES` | релизы агента на GitHub | каталог сборок агента, устроенный как релизы GitHub: ссылка или абсолютный путь к папке |
| `update.checkInterval` | `AGENT_UPDATE_CHECK_INTERVAL` | `6h` | как часто проверять новую версию агента (раздел «Обновление»); `0s` — не проверять, иначе не меньше `1m` |
| `workers` | — | — | список воркеров, поля — в таблице ниже |
| `extends` | — | — | файл настроек, поверх которого читается этот (раздел «Несколько файлов») |
| `envFiles` | — | — | файлы переменных `KEY=VALUE` для `${ИМЯ}` и `AGENT_*` (раздел «Несколько файлов») |
| `instance` | — | — | экземпляр для `agent install`, если нет `--instance`; агенту на узле не нужен |
| `install` | — | — | параметры `agent install`, если нет флагов: `packages`, `packagesByManager`, `privileged`, `sysctl`; агенту без root (`--rootless`) то, что требует root, не ставится — с предупреждением |

Прочие переменные окружения:

| Переменная | Что |
| --- | --- |
| `AGENT_CONFIG` | путь к файлу настроек, если не заданы `-config`, `--env` и `--instance` |
| `HTTPS_PROXY`, `HTTP_PROXY`, `NO_PROXY` | HTTP-прокси для запросов агента (читаются при запуске; строчные имена тоже) |
| `AGENT_SIGNING_KEY` | закрытый ключ подписи для `agent manifest` и `agent pack` (и `make release`) |
| `AGENT_BOOT_GUARD` | `external` — откат проверяет служба до запуска (`boot-guard`); ставит установщик |
| `AGENT_NO_UPDATE_CHECK` | не проверять новую версию в командах `agent config check` и `agent upgrade` |

Поля воркера (`workers[]`):

| Поле | По умолчанию | Что |
| --- | --- | --- |
| `name` | — | имя воркера: строчная латиница, цифры и «-», начало — буква, до 32 символов (обязательно, кроме `path`) |
| `command` | — | команда запуска списком, например `["python3", "report.py"]` (обязательно, кроме воркеров со сборкой с сервера; у них — выполняется в каталоге сборки) |
| `args` | — | аргументы, которые дописываются к `command` (или к файлу сборки воркера) |
| `dir` | — | рабочий каталог |
| `env` | — | переменные окружения воркера |
| `release` | `false` | `true` — воркер со сборкой с сервера: сборку ведёт агент (`<dataDir>/workers/<name>/current`), бэкенд обновляет её командой `worker.update`; без `command` запускается сам файл сборки или `run` из архива |
| `path` | — | папка воркера (путь — от файла настроек): агент запускает в ней `command`, по умолчанию `./run`; имя по умолчанию — имя папки; вместо `dir`, не вместе с `release` |
| `lifecycle` | — | `stopTimeout` (по умолчанию `30s`): сколько ждать выхода после SIGTERM, потом SIGKILL; `setupTimeout` (по умолчанию `10m`): срок `./setup`; изменение применяется без замены воркера |

Постоянные — сроки потоков, регистрации и пульса, пределы размеров, ожидание занятого воркера —
задаёт протокол ([PROTOCOL.md §20](PROTOCOL.md#20-пределы-и-сроки)).

Пример:

```yaml
server:
  url: https://api.example.com
dataDir: /var/lib/agent
labels:
  zone: eu
workers:
  - name: report
    command: ["/opt/workers/report/report-worker"]
    lifecycle:
      stopTimeout: 1m # после SIGTERM отчёт успевает сохраниться
  - name: example
    release: true
```

### Изменить настройки, не останавливая агента

Поправьте `agent.yaml` и выполните `systemctl reload agent` (агент получает SIGHUP): он
перечитает файл; связь и очередь не прерываются.

- **Сразу:** `log.level`, `log.format`, `log.forward`.
- **С новым `hello`:** имя, метки, воркеры — новые запускаются, удалённые останавливаются,
  изменённые заменяются (замена ждёт, пока воркер занят); изменённый только `lifecycle`
  применяется без замены.
- **Только перезапуском** (`agent restart` или `systemctl restart agent`): `server.*`, `dataDir`,
  `update.*`, `enroll.token`, `outbox.maxMessages`, `log.buffer`. Агент напишет в лог, какие ключи
  требуют перезапуска, а остальное применит.
- Без бэкенда SIGHUP перечитывает и файлы желаемого (`desired/`).
- Если в файле ошибка, агент пишет её в лог и продолжает работать с прежними настройками.

Бэкенд `agent.yaml` менять не может: что работает на узле, решает только сам узел.

## Установка

Агента ставят службой systemd на Linux (нужен root), для пользователя без root (служба
пользователя systemd) или запускают без установки (`agent run`: в контейнере, под своим менеджером
процессов, в терминале). `<версия>` ниже — номер версии без `v`, например `1.0.0`. Адрес сервера и
токен регистрации даёт бэкенд.

На узле после установки всегда одно и то же: программа (`/opt/agent/bin/agent`), один файл
настроек (`/etc/agent/agent.yaml`) и переменные службы (`/etc/agent/agent.env`), каталог данных с
воркерами (`/var/lib/agent`) и служба systemd. У агента пользователя без root (`--rootless`) всё
это — в `~/.agent`. Откуда всё это приходит (`--rootless` — с любым источником):

| Откуда | Команда на узле | Настройки |
| --- | --- | --- |
| папка агента | `sudo ./agent install --env prod` в папке | `agent.yaml` + `agent.prod.yaml` одним файлом, воркеры папки |
| архив `agent pack` | `tar xzf agent-prod-….tar.gz && cd agent && sudo ./agent install` | то же, из архива |
| установщик `install.sh` | `curl -fsSL …/install.sh \| sudo sh -s -- --server https://api.example.com --token …` | из флагов, воркеры — `--worker` с каталога сборок |
| архив по ссылке | `curl -fsSL …/install.sh \| sudo sh -s -- --bundle 'https://files.example.com/agent-prod-linux-{arch}.tar.gz' --token …` | архив `agent pack` с любого хостинга |
| программа агента и флаги | `sudo ./agent install --server URL --token ТОКЕН [--worker …]` | из флагов, воркеры — `--worker` с каталога сборок |

`…/install.sh` — установщик из релиза агента (`deploy/install/install.sh`):
`https://github.com/epifanovmd/agent/releases/latest/download/install.sh` (или
`…/download/v<версия>/install.sh`; `make release` кладёт его в `dist/<версия>/`). Бэкенд может
раздавать его и архивы сам — любым статическим хостингом.

### Из папки агента и архива

`agent pack --env prod` упаковывает папку агента для узлов — по архиву на платформу
(`--platform`, по умолчанию `linux/amd64,linux/arm64`) в папку агента (`--out` — другой каталог):
`agent-prod-<версия>-linux-amd64.tar.gz`. В архиве — папка `agent/`:

| Что | Откуда |
| --- | --- |
| `agent` | программа под платформу узла: эта же или из каталога сборок агента той же версии (подпись сверяется) |
| `agent.yaml`, `agent.prod.yaml` | файлы цепочки `extends` как есть |
| `workers/<имя>/` | воркеры из папки (`path`) — для `agent run` прямо из архива |
| `release/manifest.json` и сборки | те же воркеры архивами `<имя>-<VERSION>-<os>-<arch>.tar.gz` (версия — файл `VERSION` воркера) |
| `bundle.json` | версия агента, файл настроек, окружение, платформа, открытые ключи подписи |
| `.env.prod` | только с `--with-env`: файлы переменных с секретами |

Воркер с исполняемым `build` (программа под платформу — например, на Go) собирается под каждую
платформу архива: `build` запускается в папке воркера с `GOOS` и `GOARCH` (и `AGENT_OS`,
`AGENT_ARCH`) и `OUT` — каталогом итога, где должен появиться исполняемый `run`; в архив и в
сборку воркера идёт итог сборки (и `VERSION`), а не исходники. У воркера без `build` в архив идёт
папка как есть, кроме служебных файлов (`__pycache__`, `*.pyc`, `.git`) и строк его `.packignore`
— шаблонов путей от папки воркера или имён (`tests/` — только каталоги, `*.tmp`, `#` — пояснение).

`--release-out КАТАЛОГ` — ещё и общий каталог сборок воркеров из папки под все платформы
(`manifest.json` и архивы): его раздаёт бэкенд, чтобы обновлять воркеры узлов командой
`worker.update`. Файлы настроек и воркеры должны лежать в папке агента. С `AGENT_SIGNING_KEY` в
окружении (раздел «Обновление», «Ключи подписи») сборки воркеров подписаны, открытый ключ — в
`bundle.json`; закрытый в архив не попадает. Без ключа воркеры поставить можно, а обновить с
бэкенда (`worker.update`) — нет.

`agent install` из распакованного архива (рядом с программой — `bundle.json`) или с `--env` в
папке агента (тогда архив собирается тут же, с файлами переменных):

1. сводит цепочку файлов в один `/etc/agent/agent.yaml`: без `extends` и `envFiles`, `dataDir` —
   каталог узла, воркеры из папки — воркеры со сборкой (`release: true`), `instance` и `install`
   убираются; `${ИМЯ}` остаются как есть, а значения из файлов переменных — только те, что
   нужны: из `${ИМЯ}` настроек и `AGENT_*` — уходят в `/etc/agent/agent.env`
   (`AGENT_ENROLL_TOKEN` — токен, `AGENT_UPDATE_PUBLIC_KEYS` — ключи; `--server` — в
   `AGENT_SERVER_URL`, он важнее файла; `AGENT_SIGNING_KEY` на узел не попадает);
2. ставит сборки воркеров из `release/` в `/var/lib/agent/workers/<имя>/current` (подпись
   сверяется ключами агента и ключом из `bundle.json`);
3. берёт `instance` и раздел `install` из настроек, если нет флагов (`--instance`, `--packages`,
   `--sysctl`, …): флаги важнее;
4. дальше — как обычная установка (ниже). Прежний `agent.yaml`, если он отличается, остаётся
   рядом как `agent.yaml.bak`.

Токен — `--token` или `AGENT_ENROLL_TOKEN` в файле переменных архива (`--with-env`). Удалить —
`sudo ./agent uninstall [--purge]` из того же архива: экземпляр берётся из его настроек.

**Архив по ссылке.** Установщик `install.sh` с `--bundle URL` скачивает архив `agent pack` и
запускает его `agent install` — распаковывать вручную не нужно. `{arch}` в ссылке заменяется на
`amd64` или `arm64` этой машины, так что одна команда подходит обеим платформам:

```bash
I=https://github.com/epifanovmd/agent/releases/latest/download/install.sh
B='https://files.example.com/agent-prod-linux-{arch}.tar.gz'
curl -fsSL $I | sudo sh -s -- --bundle "$B" --token <токен>              # служба systemd
curl -fsSL $I | sh -s -- --bundle "$B" --rootless --token <токен>        # агент пользователя
curl -fsSL $I | sh -s -- --bundle "$B" --run --token <токен>             # без установки
curl -fsSL $I | sudo sh -s -- --bundle "$B" --uninstall [--purge]        # удалить
```

Программа агента, настройки и воркеры — из архива; `--server` нужен, только если адреса сервера нет
в его настройках. Архивы раздаёт бэкенд или любой статический хостинг.

### Linux со systemd

Подходит любой Linux с systemd: Debian и Ubuntu, RHEL и Fedora, SUSE и т. п. Нужны права root. На
узлах без systemd (Alpine и другие) `agent install` сразу завершается с ошибкой и ничего не меняет —
там агента запускают в контейнере.

**Вручную — три команды.** Скачайте сборку из GitHub Release и поставьте ею службу:

```bash
v=<версия>; arch=amd64   # arm64 — для ARM
curl -fLo agent https://github.com/epifanovmd/agent/releases/download/v$v/agent-linux-$arch && chmod +x agent
sudo ./agent install --server https://api.example.com --token <токен>
```

Контрольная сумма сборки — в `manifest.json` той же версии (сравните с `sha256sum agent`). После
установки скачанный файл не нужен: программа лежит в `/opt/agent/bin/agent`, а команда `agent`
доступна из любого каталога. Проверить, что всё работает:

```bash
sudo agent status    # работает ли агент, есть ли связь, воркеры, последняя ошибка
sudo agent logs -f   # лог службы (то же, что journalctl -u agent -f)
```

Если `sudo agent` отвечает «command not found» (так бывает на RHEL, Rocky, Alma: у sudo свой список
каталогов без `/usr/local/bin`), вызывайте программу полным путём: `sudo /opt/agent/bin/agent status`.

Своя сборка ставится так же: `sudo dist/<версия>/agent-linux-amd64 install --server … --token …`
(`make release`).

**Одной командой — установщиком `install.sh`.** Установщик лежит в релизе агента рядом со
сборками; адрес сервера, токен и ключи проверки подписи сборок проекта ему передают флагами (строку
для узла собирает бэкенд):

```bash
curl -fsSL https://github.com/epifanovmd/agent/releases/latest/download/install.sh |
  sudo sh -s -- --server https://api.example.com --token <токен> [--update-key <ключ проекта>]
```

`install.sh` скачивает сборку под эту машину из последнего релиза агента на GitHub (или из
каталога `--releases`; `file` в `manifest.json` может быть и ссылкой `https://`), сверяет
контрольную сумму и запускает `agent install`, передав ему остальные флаги.
Свои флаги у него такие: `--server URL`, `--binary ПУТЬ` (поставить сборку из файла),
`--releases URL` (откуда скачать; передаётся и `agent install`), `--bundle URL` (архив
`agent pack` по ссылке — раздел «Из папки агента и архива»), `--ca-file ПУТЬ` (свой корневой
сертификат для загрузки; передаётся и `agent install`), `--instance ИМЯ` (экземпляр, см.
«Несколько агентов на одном узле»; передаётся и `agent install`), `--run` (без установки — раздел
«Без установки»), `--uninstall [--purge]`.

**Что делает `agent install`** (службой systemd; без root и в Docker — разделы ниже):

1. проверяет, что есть root и systemd;
2. создаёт пользователя службы `agent` (системный, без входа в систему), если его нет;
3. кладёт программу в `/opt/agent/bin/agent` и ссылку на неё в `/usr/local/bin/agent`;
4. создаёт `/etc/agent/agent.yaml` из флагов (`server.url` — с `server.allowInsecure`, если адрес
   `http://`; `name`, `dataDir`, воркеры `--worker`, `server.caFile`; журнал в JSON), если файла
   ещё нет; готовый файл не меняет;
5. сохраняет токен в `/etc/agent/agent.env` — читать его может только служба;
6. если заданы флаги — ставит системные пакеты, параметры ядра и сборки воркеров;
7. создаёт службу `agent` (`internal/install/agent.service.tmpl`), включает её и запускает.

Служба: `Type=notify`, `NotifyAccess=main`, `WatchdogSec=60` — зависший агент перезапускается;
`Restart=always`; `KillMode=process` — SIGTERM получает только агент, воркеры работают дальше;
`ExecReload` — SIGHUP; `ExecStartPre` — откат обновления прежней версией (`agent.prev boot-guard`).
Без `--privileged` — с ограничениями systemd (ниже).

Повторный запуск (или та же команда с бэкенда) обновляет программу и службу тем же способом, что
и в первый раз (агенту пользователя `--rootless` повторять не нужно). Ключ агента, `agent.yaml` и
`agent.env` сохраняются; заново переданные `--token` и `--update-key` заменяют прежние.
Служба, поставленная с `--privileged`, такой и остаётся (сменить — `agent uninstall`, затем
`install`). Новые воркеры из `--worker` дописываются в `workers` готового `agent.yaml` (комментарии
и порядок ключей сохраняются, прежний файл — `agent.yaml.bak`); воркер, у которого уже стоит та же
или более новая сборка (например, после `worker.update`), не переставляется.

Что где лежит:

| Что | Где |
| --- | --- |
| программа | `/opt/agent/bin/agent` (ссылка — `/usr/local/bin/agent`) |
| настройки | `/etc/agent/agent.yaml` |
| токен и ключи сборок | `/etc/agent/agent.env`, доступ только у службы |
| свой сертификат CA | `/etc/agent/ca.pem` (если задан `--ca-file`) |
| данные | `/var/lib/agent` |
| служба | `agent` (`systemctl status agent`) |
| файл службы | `/etc/systemd/system/agent.service` |
| журнал установки | `/etc/agent/install-state` |
| параметры ядра | `/etc/sysctl.d/90-agent.conf` (если задан `--sysctl`) |

В журнал установки записывается, что поставлено: пакеты, которых не было (и какие нужны воркерам),
созданный пользователь службы, параметры ядра с их прежними значениями, — чтобы при удалении точно
вернуть как было.

Флаги `agent install` (список — `agent install -h`):

| Флаг | Что |
| --- | --- |
| `--rootless` | агент пользователя без root (запускать без `sudo`): всё в `~/.agent`, служба пользователя systemd — раздел «Без root» |
| `--instance ИМЯ` | ставить или обновлять экземпляр `ИМЯ` — ещё одного агента на этом узле, со своими путями и службой (раздел «Несколько агентов на одном узле»); без флага — экземпляр по умолчанию |
| `--server URL` | адрес бэкенда; нужен, если `agent.yaml` ещё нет |
| `--token ТОКЕН` | токен регистрации; сохраняется в `agent.env` |
| `--token-file ПУТЬ` | взять токен из файла, а не из командной строки (его не видно в списке процессов); вместо `--token` |
| `--name ИМЯ` | имя агента (по умолчанию — имя машины) |
| `--config ФАЙЛ` | свой `agent.yaml` вместо создаваемого |
| `--ca-file ПУТЬ` | свой корневой сертификат сервера: копируется в `/etc/agent/ca.pem` и прописывается в `server.caFile` |
| `--update-key КЛЮЧ` | открытый ключ проверки подписи сборок (base64); можно несколько раз, подпись принимается, если сходится с любым. Ключ автора агента в сборки из GitHub Release вшит; сюда — ключи проекта (его воркеров). Сохраняется в `agent.env` (`AGENT_UPDATE_PUBLIC_KEYS`). `--public-key` — то же |
| `--worker ИМЯ` | поставить сборку воркера (контрольная сумма сверяется, подпись — если известен хоть один ключ проверки) и прописать его в создаваемый `agent.yaml` с `release: true`; можно несколько раз. Архив `.tar.gz` распаковывается в каталог; что в нём запускать, берётся из `manifest.json` (`command`), иначе — `./run`. `file` сборки в манифесте — имя в каталоге сборок или ссылка `https://` на любой хост (`http://` — только если и `--releases` или сервер `http://`) |
| `--releases URL` | откуда брать сборки воркеров (по умолчанию — `<server>/agent/v1/releases`; без `--server` — адрес из `agent.env` или `agent.yaml` установленного агента); подойдёт и адрес релиза на GitHub: `https://github.com/epifanovmd/agent/releases/download/v<версия>` |
| _(без `--privileged`)_ | служба работает с ограничениями systemd: `/usr`, `/boot`, `/etc` и домашние каталоги — только для чтения, свой `/tmp`, без повышения прав |
| `--privileged` | агент и воркеры — от root и без ограничений. Нужно воркерам, которые настраивают сам узел: сеть, firewall, системные файлы. В Docker — привилегированный контейнер в сети узла. Включайте, только если это действительно нужно |
| `--packages "…"` | поставить системные пакеты для воркеров (apt, dnf, yum, apk, zypper), например `"jq curl"` |
| `--packages-apt`, `--packages-dnf`, `--packages-yum`, `--packages-apk`, `--packages-zypper` `"…"` | свои имена пакетов для этого менеджера — на узле с ним заменяют `--packages` |
| `--sysctl КЛЮЧ=ЗНАЧЕНИЕ` | параметр ядра для воркеров, например `vm.max_map_count=262144` (можно несколько раз) |

**Поменять настройки.** Поправьте `/etc/agent/agent.yaml`, проверьте его и примените без
перезапуска:

```bash
sudo nano /etc/agent/agent.yaml
sudo agent config check          # ошибки — с номером строки; итоговые значения
sudo systemctl reload agent
```

Добавить воркер со сборкой с сервера на уже установленный узел —
`sudo agent install --server https://api.example.com --worker example` (адрес нужен, чтобы
скачать сборку; вместо него можно `--releases URL`): сборка ставится, а если `agent.yaml` уже
был, установщик подскажет, какие строки добавить в `workers`.

### Без root

Если прав root нет (или не нужны), агента ставят для пользователя — без `sudo`:

```bash
./agent install --rootless --server https://api.example.com --token <токен>
curl -fsSL https://github.com/epifanovmd/agent/releases/latest/download/install.sh |
  sh -s -- --rootless --server https://api.example.com --token <токен>
```

Из папки агента и архива — так же: `./agent install --rootless --env prod`. Всё ставится в
домашний каталог (те же пути, что у агента на macOS):

| Что | Где |
| --- | --- |
| программа | `~/.agent/bin/agent` (ссылка — `~/.local/bin/agent`) |
| настройки | `~/.agent/agent.yaml`, токен и ключи — `~/.agent/agent.env` (0600) |
| данные | `~/.agent/data` |
| служба пользователя | `agent` (`systemctl --user status agent`), файл — `~/.config/systemd/user/agent.service` |
| журнал установки | `~/.agent/install-state` |

Служба пользователя (`systemctl --user`) — как обычная служба: сторож и перезапуск при сбое, откат
обновления, `agent status`, `agent logs -f` (`journalctl --user -u agent -f`), применить настройки —
`systemctl --user reload agent`. Чтобы она работала, когда пользователь не вошёл в систему, и
запускалась после перезагрузки, установка включает `loginctl enable-linger`; если система этого не
разрешает, установщик подскажет команду для администратора.

Если служб пользователя нет (нет systemd или сеанса пользователя — например, в контейнере или при
входе через `su`), установка завершается ошибкой и ничего не меняет: войдите этим пользователем по
`ssh` и повторите или запускайте агента сами — `agent run` (`install.sh --run`, раздел ниже);
автозапуск в этом случае настраивается средствами узла. Агента, который уже работает в фоне без
службы (в журнале установки — `mode manual`), установка службой не трогает и просит сначала
остановить его и убрать строку `@reboot` из `crontab`; сам такой агент при запуске пишет об этом
предупреждение.

Без root недоступно то, что меняет систему: `--packages`, `--sysctl`, `--privileged`; то же в разделе
`install` файла настроек пропускается с предупреждением. Воркерам доступно только то, что доступно
пользователю. Команды — без `sudo`: `agent status`, `agent upgrade`, `agent uninstall [--purge]`;
от пользователя они работают с его агентом, если он поставлен (`--purge` удаляет весь `~/.agent`).
Экземпляры — как у службы: `--instance b` → `~/.agent-b`, служба `agent-b`.

### Без установки: `agent run`

Агента можно запускать и без установки — на переднем плане, под чужим менеджером процессов: в
контейнере, в supervisord, в терминале. Установщик `install.sh` делает это флагом `--run`:
скачивает программу (или архив папки агента проекта, `--bundle`) и сразу выполняет `agent run`,
ничего не ставя:

```bash
I=https://github.com/epifanovmd/agent/releases/latest/download/install.sh
# архив папки агента проекта — настройки и воркеры из архива
curl -fsSL $I | sh -s -- --run --bundle 'https://files.example.com/agent-prod-linux-{arch}.tar.gz' --token <токен>
# только программа агента — настройки из окружения
curl -fsSL $I | sh -s -- --run --server https://api.example.com --token <токен>
```

С `--run` — только `--token` (или `--token-file`), `--name` и `--update-key` (ключи проверки —
в `AGENT_UPDATE_PUBLIC_KEYS`); адрес сервера — `--server` (с `--bundle` — из настроек архива),
данные — `AGENT_DATA_DIR` (по умолчанию `/var/lib/agent`; держите его на томе — там ключ агента и
хранилище), агент себя не обновляет (`AGENT_UPDATE_MODE=external`): новая версия — при следующем
запуске. Установщику нужен `curl`. Например, в своём контейнере (образ — с `curl` и тем, что нужно
воркерам):

```bash
docker run -d --restart unless-stopped -v agent-data:/var/lib/agent <образ> \
  sh -c "curl -fsSL https://github.com/epifanovmd/agent/releases/latest/download/install.sh | sh -s -- --run --bundle 'https://files.example.com/agent-prod-linux-{arch}.tar.gz' --token <токен>"
```

Программы, нужные воркерам, должны быть в образе. Тяжёлые зависимости (например, библиотеки
машинного обучения) удобнее держать в своём образе проекта: тот же архив и `agent run` в нём.

### Docker

Образы (`deploy/Dockerfile`):

- `ghcr.io/epifanovmd/agent:<версия>` — минимальный: только агент на Alpine;
- `ghcr.io/epifanovmd/agent:<версия>-python` — агент и Python для воркеров на Python.

В образе уже заданы `AGENT_UPDATE_MODE=external` (обновление — новым образом),
`AGENT_LOG_FORMAT=json` и каталог данных `/var/lib/agent`. Остальное — переменными окружения из
таблицы «Настройки», файл настроек не обязателен:

```bash
docker run -d --name agent --restart unless-stopped \
  -e AGENT_SERVER_URL=https://api.example.com \
  -e AGENT_ENROLL_TOKEN=<токен> \
  -e AGENT_NAME=node-01 \
  -v agent-data:/var/lib/agent \
  ghcr.io/epifanovmd/agent:<версия>
```

То же в Docker Compose:

```yaml
services:
  agent:
    image: ghcr.io/epifanovmd/agent:<версия>
    restart: unless-stopped
    environment:
      AGENT_SERVER_URL: https://api.example.com
      AGENT_ENROLL_TOKEN: ${AGENT_ENROLL_TOKEN}
      AGENT_NAME: node-01
    volumes:
      - agent-data:/var/lib/agent
    stop_grace_period: 1m # не меньше stopTimeout воркеров: в контейнере они останавливаются с агентом
volumes:
  agent-data:
```

Ключ агента и хранилище (очередь, журнал команд, желаемое) — в томе `/var/lib/agent`: без тома
после пересоздания контейнера агент зарегистрируется заново. Агент работает от пользователя с uid
`10001`; если вместо тома подключаете каталог машины (`-v /srv/agent:/var/lib/agent`), отдайте его
этому пользователю: `sudo chown 10001 /srv/agent`.

Проверка живости встроена в образ (`HEALTHCHECK` — `agent status`): контейнер `healthy`, пока
агент работает и отвечает на локальный API (связь с бэкендом не обязательна). Посмотреть состояние
и настройки:

```bash
docker exec agent agent status
docker exec agent agent config check
docker logs -f agent
```

Воркеры проекта добавляют своим образом — `FROM` одного из этих и файл настроек со списком
воркеров (агент найдёт его сам):

```dockerfile
FROM ghcr.io/epifanovmd/agent:<версия>-python
COPY workers/ /app/
COPY agent.yaml /etc/agent/agent.yaml
```

### macOS и разработка

Службой на macOS агент не ставится (`agent install` — только для Linux); его запускают в
терминале из папки агента — каталога с программой и `agent.yaml`:

```yaml
# agent/agent.yaml
server:
  url: http://localhost:8080
  allowInsecure: true # http:// — только на своей машине
enroll:
  token: <токен>
dataDir: .data
update:
  mode: disabled
```

```bash
agent/agent config check
agent/agent run
agent/agent status   # в другом терминале
```

Один файл без папки — `~/.agent/agent.yaml`: агент найдёт его и сам (файл по умолчанию на macOS),
данные — в `~/.agent/data`. Без `server.url` агент работает без бэкенда: желаемое — из
`agent/desired/<воркер>/<ключ>.json`, команды — `agent command`.

Стенд с сервером и воркерами-примерами — [examples/README.md](../examples/README.md). Проверки —
`make check`; сквозные тесты (`test/e2e`, тег `e2e`, `make e2e`) собирают настоящего агента и
воркеры-примеры echo (Python) и sysinfo (Go) и поднимают бэкенд в процессе теста: связь, желаемое,
команды, очередь без связи, длинный опрос, регистрация заново и отзыв, перезапуск агента, работа
без бэкенда.

### Удаление

```bash
sudo agent uninstall           # служба (или контейнер) и программа; настройки и данные остаются
sudo agent uninstall --purge   # всё, что поставила установка
agent uninstall [--purge]      # агент пользователя без root (~/.agent)
```

Тем же установщиком:
`curl -fsSL https://github.com/epifanovmd/agent/releases/latest/download/install.sh | sudo sh -s -- --uninstall [--purge]`
(агента из архива — ещё с `--bundle URL`).
Экземпляр — с `--instance ИМЯ` (раздел «Несколько агентов на одном узле»).

`agent uninstall` останавливает службу и воркеры, оставшиеся работать, и выполняет их `./cleanup`
(`agent stop-workers --cleanup`, от пользователя службы), затем удаляет службу, программу
(`/opt/agent` и ссылку `/usr/local/bin/agent`) и параметры ядра из `--sysctl`, возвращая их
прежние значения. Что воркеры создали на узле, убирает их `cleanup`; без него — остаётся. Без `--purge` настройки и данные
остаются: повторная установка продолжит с тем же ключом агента. С `--purge` удаляются ещё
`/etc/agent`, `/var/lib/agent`, пакеты, которые поставила установка, и созданный ею пользователь
службы; root и пользователей, которые были до установки, не трогает.


### Обновление агента

Обычно агента обновляет бэкенд — командой `agent.update` (раздел «Обновление» ниже). На узле —
`sudo agent upgrade` (у агента пользователя — без `sudo`): новая версия из каталога сборок агента,
служба перезапускается, откат — как у `agent.update`. Или той же установкой с новой сборкой:
`sudo ./agent install` (флаги не нужны, настройки и ключ агента сохраняются), новым архивом
`agent pack` или той же командой `install.sh`. В Docker — новым образом.

### Несколько агентов на одном узле

Один агент связан с одним бэкендом. Если на узле работают воркеры двух разных бэкендов, ставят два
агента — **экземпляра**. Экземпляр получает имя флагом `--instance ИМЯ` (строчная латиница, цифры
и «-», первая — буква, до 32 символов); установка без флага — экземпляр по умолчанию с обычными
путями, так что простая установка не меняется.

```bash
sudo ./agent install --server https://a.example.com --token <токен A>                    # по умолчанию
sudo ./agent install --instance b --server https://b.example.com --token <токен B>       # экземпляр b
curl -fsSL …/install.sh | sudo sh -s -- --instance b --server https://b.example.com --token <токен B>
```

У экземпляра `ИМЯ` все пути — с окончанием `-ИМЯ`, общего с другими экземплярами у него нет:

| Что | По умолчанию | Экземпляр `ИМЯ` |
| --- | --- | --- |
| программа | `/opt/agent/bin/agent` | `/opt/agent-ИМЯ/bin/agent` |
| ссылка в PATH | `/usr/local/bin/agent` | `/usr/local/bin/agent-ИМЯ` |
| настройки | `/etc/agent/agent.yaml`, `agent.env`, `ca.pem`, `install-state` | `/etc/agent-ИМЯ/…` |
| данные (`dataDir`) | `/var/lib/agent` | `/var/lib/agent-ИМЯ` |
| служба | `agent` | `agent-ИМЯ` |
| пользователь службы | `agent` | `agent-ИМЯ` |
| параметры ядра | `/etc/sysctl.d/90-agent.conf` | `/etc/sysctl.d/90-agent-ИМЯ.conf` |

- **Своя программа** — у каждого экземпляра: бэкенд обновляет их по отдельности, версии могут
  различаться, откат неудачного обновления — тоже свой.
- **Свой пользователь** — ключ агента, хранилище и данные воркеров одного экземпляра недоступны
  другому (`--privileged` — root).
- **Воркеры** не пересекаются, даже с одинаковыми именами: сокеты, процессы, блокировка и сборки
  воркеров лежат в `dataDir` своего экземпляра.

Команды работают с экземпляром по флагу `--instance ИМЯ` или через его ссылку `agent-ИМЯ` (программа
узнаёт экземпляр по своему пути):

```bash
sudo agent status --instance b       # то же: sudo agent-b status
sudo agent logs -f --instance b      # journalctl -u agent-b -f
sudo agent config check --instance b
sudo systemctl reload agent-b        # применить настройки
sudo agent restart --instance b      # также stop-workers, command
sudo agent install --instance b      # обновить экземпляр b
sudo agent uninstall --instance b [--purge]
```

Удаление одного экземпляра не трогает остальные. Системные пакеты и параметры ядра, нужные и
другому экземпляру, остаются (параметр ядра сохраняет его значение); запись о них переходит в
журнал установки того экземпляра, и удалит их последний, кому они нужны. То же с пользователем
службы, если экземпляры работают от одного пользователя.

## Работа на узле

**Лог.** Агент пишет лог в поток ошибок (stderr); под systemd его собирает journald:
`agent logs -f` (то же, что `journalctl -u agent -f`; у агента пользователя — `journalctl --user`).
Своих файлов лога агент не ведёт (файлы — только у вывода воркеров, `logs/`, с ротацией по
10 МБ), поэтому и ротация — на стороне journald (`SystemMaxUse=` и `MaxRetentionSec=` в
`/etc/systemd/journald.conf`). В контейнере лог читает `docker logs`, а сколько его хранить,
решают настройки логов Docker. Последние записи воркера из памяти агента — `agent logs --worker ИМЯ`.

**Резервная копия.** Всё, что агент хранит сам, лежит в `/var/lib/agent` (`dataDir`):

| Файл или каталог | Что |
| --- | --- |
| `credentials.json` | ключ агента (и ожидающий секрет при смене): по нему бэкенд узнаёт этот узел |
| `agent.db` | хранилище: очередь итогов и событий, журнал команд, желаемое (настройки воркеров), итоги настроек |
| `workers/` | сборки воркеров с сервера (`current`, `previous`) |
| `state/` | данные воркеров (`WORKER_STATE_DIR`) |
| `run/` | сокеты: `agent.sock` для воркеров, `admin.sock` — локальный API |
| `processes/` | запущенные процессы воркеров: по ним новый запуск агента их подхватывает |
| `logs/` | вывод воркеров: `<имя>.log` (stdout), `<имя>.err.log` (stderr) и копии |
| `agent-update.json` | `agent.update` ждёт запуска новой версии, чтобы отправить итог |
| `update-check.json` | итог последней проверки новой версии агента |
| `agent.lock` | блокировка каталога: один агент на `dataDir` |
| `agent.error` | ошибка, с которой агент завершился в последний раз (`agent status`) |

**Что в каталоге секретно.** `credentials.json` (ключ агента), `agent.db` (значения настроек
воркеров как есть — в них бывают пароли и токены, события и итоги команд), `state/` и `logs/`
(данные и вывод воркеров) не шифруются: защита — права доступа. Каталоги — 0700, файлы — 0600,
доступны только пользователю агента; не открывайте их другим пользователям, держите `dataDir` на
зашифрованном диске или томе, если узел могут унести или снять с него диск, и храните резервные
копии так же, как сам ключ агента.

**Что не попадает в лог агента.** Агент не пишет в свой лог и журнал значения настроек, `args` и
итоги команд, `data` событий и запросов воркеров к бэкенду, токен регистрации, ключ агента и токены
воркеров — только имя воркера, ключ, версию, `id`, тип и код ошибки. Вывод воркера (stdout и
stderr) и текст ошибок, которые воркер присылает сам, агент передаёт в журнал как есть: не
печатайте секреты из настроек и команд.

Копируйте каталог целиком при остановленной службе (`systemctl stop agent`, затем
`agent stop-workers`) или снимком тома. Без копии, если каталог пропал, агент регистрируется
заново по токену регистрации (`--token` при повторной установке или `AGENT_ENROLL_TOKEN` в
`/etc/agent/agent.env`) — для бэкенда это новый агент с новым id, прежнюю запись можно отозвать.
Кроме того, пропадают неотправленные итоги и события; желаемое агент получит от бэкенда снова, а
сборки воркеров ставятся заново (`agent install --worker` или `worker.update`).

## Обновление

**Новые версии агент замечает сам.** Каталог сборок агента — его релизы на GitHub или свой
`update.releases` с тем же устройством (`<адрес>/latest/download/manifest.json` — последняя версия,
`<адрес>/download/v<версия>/…` — сборки версии): ссылка на зеркало или абсолютный путь к папке на
узле — для узлов без доступа к GitHub. Раз в `update.checkInterval` (6 ч; `0s` — не
проверять) агент читает последнюю версию; новее своей — пишет в журнал и сообщает бэкенду в
состоянии (`state.update`). Итог проверки хранится в `dataDir/update-check.json`: `agent status`
показывает его без сети, `agent config check` и `agent upgrade` при устаревшем итоге проверяют
сами (`AGENT_NO_UPDATE_CHECK=1` — не проверять в командах). Сам агент новую версию не ставит:

- `agent upgrade [--check] [--version X] [--force]` на узле — в папке агента программа заменяется на
  месте (прежняя — `agent.prev`), у службы — как по `agent.update`, с откатом, служба
  перезапускается; новую основную версию (`2.x` при `1.x`) — только явно, `--version`;
- `agent.update {version}` от бэкенда — агент сам берёт сборку этой версии под свою платформу из
  каталога сборок, подпись — из его `manifest.json`.

1. **Ключи подписи** — пара Ed25519 в base64: закрытый — seed (32 байта), открытый — 32 байта.
   Создать их можно OpenSSL (1.1.1 и новее):

   ```bash
   openssl genpkey -algorithm ed25519 -outform DER -out signing.der
   echo "AGENT_SIGNING_KEY=$(tail -c 32 signing.der | base64)"
   echo "AGENT_UPDATE_PUBLIC_KEYS=$(openssl pkey -inform DER -in signing.der -pubout -outform DER | tail -c 32 | base64)"
   rm signing.der
   ```

   Закрытый (`AGENT_SIGNING_KEY`) нужен только при подписи сборок — держите его в секретах CI, не
   на бэкенде. Открытый (`AGENT_UPDATE_PUBLIC_KEY`) проверяет подпись. Агенту он вшивается при
   сборке, если при `make release` (или `scripts/go.sh build`) задана переменная
   `AGENT_UPDATE_PUBLIC_KEY` (`-ldflags "-X main.updateKey=<base64>"`). Ключей у агента может быть
   несколько: вшитый и `update.publicKey`, `update.publicKeys` из настроек (`--update-key` при
   установке); подпись принимается, если сходится с любым. Обычно это два ключа: **автора агента**
   (им подписаны сборки агента в GitHub Release, он вшит в эти сборки) и **проекта** (им проект
   подписывает свои воркеры). Подпись — над строкой из имени сборки (`agent` или имя воркера),
   версии, `os`, `arch` и sha256 ([PROTOCOL.md §10](PROTOCOL.md#10-сборки-и-обновление)): подпись
   одной сборки к другой не подходит. `manifest.json` пишет открытый ключ своей подписи в поле
   `publicKey` — справочно, агент ему не доверяет.

2. **Сборка.** `AGENT_SIGNING_KEY=… AGENT_UPDATE_PUBLIC_KEY=… make release` кладёт в
   `dist/<VERSION>/` сборки агента linux/darwin × amd64/arm64, подписанный `manifest.json` и
   `install.sh` (`scripts/release.sh`). CI публикации (`.github/workflows/release.yml`) делает то
   же по тегу `v<VERSION>` и публикует всё в GitHub Release — каталог сборок агента по умолчанию,
   — а ещё в образ `ghcr.io/epifanovmd/agent-dist:<версия>` (каталог `/dist/<версия>/`, основа
   для своего зеркала `update.releases`). Бэкенду ради новой версии агента обновляться не нужно:
   агенты находят её сами.

3. **Сборки воркеров.** Манифест воркеров проекта — `agent manifest DIR VERSION --worker
   NAME=VERSION[,stopTimeout=…][,command=…]…` над каталогом с их сборками (подпись —
   `AGENT_SIGNING_KEY`); сборок агента в нём нет, `artifacts` пуст. Каталог раздаёт бэкенд:
   `worker.update` передаёт агенту `url` сборки (путь от корня бэкенда — запрос с ключом агента —
   или ссылку `https://`), sha256 и подпись. Сборка воркера — один файл
   `<name>-<version>-<os>-<arch>` (например, программа на Go) или архив
   `<name>-<version>-<os>-<arch>.tar.gz` — для воркера, которому нужно несколько файлов. Агент
   распаковывает архив в каталог `current` (пути наружу, ссылки наружу и особые файлы — отказ) и
   запускает в нём `command` воркера; путь `./…` в `command` — от этого каталога. Без `command` в
   настройках запускается файл `run` из архива. `command=bin/report` у `--worker` записывает в
   `manifest.json` (поле `command` сборки), что запускать в архиве, — установщик вписывает это в
   настройки. Например, воркер `report` на Python:

   ```bash
   # каталог воркера: report_worker.py и всё, что он импортирует
   tar -czf release/report-1.0.0-linux-amd64.tar.gz -C workers/report .
   agent manifest release 1.0.0 --worker report=1.0.0
   ```

   ```yaml
   # agent.yaml узла
   workers:
     - name: report
       release: true
       command: ["python3", "./report_worker.py"]
   ```

   Интерпретатор (`python3`) должен быть на узле или в архиве. Архив не зависит от платформы — тот
   же файл кладётся под каждую пару `<os>-<arch>`, где воркер нужен.

4. **Обновление узла.** Бэкенд отправляет агенту `agent.update` с версией. Агент проверяет, что
   после перезапуска прочитает свой файл настроек, берёт сборку этой версии под свою платформу из
   своего каталога сборок, проверяет подпись и контрольную сумму, сохраняет текущую версию как
   запасную (`.prev`), ставит новую, записывает `agent-update.json` в `dataDir` и
   перезапускается; воркеры работают дальше. Итог `{version, previous}` отправляет уже новая
   версия после принятого `hello`. Агент в контейнере (`update.mode: external`) и с
   `update.mode: disabled` себя не обновляет (`UPDATE_NOT_SUPPORTED`), без ключа проверки — тоже
   (`UPDATE_NOT_VERIFIED`). Отметка о новой версии (`agent.update.json`) и запасная копия лежат
   рядом с программой.
5. **Обновление воркеров.** Бэкенд обновляет воркеры с `release: true` командой `worker.update` — с
   той же проверкой подписи (раздел «Воркеры», «Сборка воркера»). Добавить или удалить воркер с
   бэкенда нельзя.
6. **Откат.** Если новая версия за три запуска так и не прошла `hello`, агент возвращает прежнюю,
   а итог `agent.update` — `UPDATE_FAILED`. Под systemd это делает прежняя версия ещё до запуска
   новой (`agent.prev boot-guard`, `AGENT_BOOT_GUARD=external`), поэтому откат срабатывает, даже
   если новая версия падает сразу; без службы — сам `agent run` первым делом.
