# Как устроен агент

Агент — одна программа на узле. Она держит связь с сервером (бэкендом), запускает воркеры и
следит за ними, передаёт им настройки и запросы сервера, собирает метрики узла и обновляет себя.
Своей предметной области у агента нет: всё, что нужно проекту, — в воркерах. Воркер — обычный
HTTP-сервис на unix-сокете на любом языке, без SDK. Формат сообщений и HTTP воркера —
[sdk/spec](../sdk/spec/README.md), как подключить агента к своему бэкенду —
[sdk/docs](../sdk/docs/README.md).

```
cmd/agent/          команды: run | install | uninstall | init | config | status | logs | restart | stop-workers | cleanup | version | boot-guard | sysmetrics
cmd/agent-release/  утилита подписи сборок: ключи, manifest.json (на узлы не ставится)
internal/
├── app/            сборка агента из частей ниже: hello/welcome, метрики, status, лог, watch, действия
├── link/           связь с сервером: WebSocket agent.v2, переподключение, коды закрытия, ping
├── outbox/         важные сообщения на диске — хранятся, пока сервер не подтвердит
├── stream/         сообщения потока (status, metrics, log): нумерация seq, последние 600 в памяти
├── worker/         запуск воркеров, проверка /health, манифест, перезапуск, замена, уборка, сборки воркеров с сервера
├── configs/        настройки воркеров: версии на диске, PUT /config/{key}, итог config.applied
├── fetch/          запросы сервера к воркерам: сверка с манифестом, HTTP по сокету воркера, ответ кусками
├── agentsock/      сокет агента для воркеров: события, запросы к серверу, настройки, контекст
├── requests/       запросы воркеров к серверу: request в текущем соединении, ожидание request.result
├── update/         самообновление: проверка подписи, запасная копия, откат
├── identity/       регистрация по токену, ключ агента, смена ключа
├── config/         настройки агента: YAML (цепочка extends, envFiles), переменные окружения, шаблон файла настроек
├── scaffold/       папка агента: agent init
├── bundle/         архив папки агента для узла (agent pack) и установка из него (agent install)
├── releases/       каталог сборок (manifest.json): сервер, релиз агента, локальная папка; установка сборок воркеров
├── install/        установка службой systemd: agent install и agent uninstall
├── message/        типы сообщений (по sdk/spec)
├── sysmetrics/     встроенный воркер метрик узла (режим agent sysmetrics)
└── logx/, backoff/ лог (журнал и отправка на сервер), паузы между повторами
```

Команды программы:

| Команда                                              | Что делает                                                                                                          |
| ---------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| `agent [run] [-config ФАЙЛ \| --env ИМЯ]`            | работа (по умолчанию); SIGHUP — перечитать настройки, SIGUSR1 — перезапуск, SIGTERM и SIGINT — остановка            |
| `agent install [--env ИМЯ] [флаги]`                  | поставить или обновить службу systemd (Linux, root): из архива, из папки агента или по флагам — раздел «Установка»  |
| `agent pack [--env ИМЯ] [--platform …] [--with-env]` | архив папки агента для узла — раздел «Установка»                                                                    |
| `agent upgrade [--check] [--version X] [--force]`    | поставить новую версию агента из каталога сборок — раздел «Обновление»                                              |
| `agent keygen`                                       | пара ключей подписи сборок воркеров проекта — раздел «Обновление»                                                   |
| `agent worker new ИМЯ [--lang python\|go]`           | воркер из заготовки в папке агента — раздел «Папка агента»                                                          |
| `agent worker sync`                                  | обновить базы воркеров папки до версии этой программы                                                               |
| `agent worker list`                                  | воркеры из настроек: откуда каждый (папка, релиз агента, сборка с сервера, команда), версия, где лежит              |
| `agent uninstall [--purge]`                          | удалить службу (Linux, root); `--purge` — ещё настройки, данные и то, что ставила установка                         |
| `agent init [ПАПКА] [--server URL] [--token ТОКЕН]`  | развернуть папку агента или (`-config ФАЙЛ`) один файл настроек — раздел «Настройки»                                |
| `agent config check [-config ФАЙЛ \| --env ИМЯ]`     | проверить настройки и показать итоговые значения и откуда каждое                                                    |
| `agent status [--json] [-config ФАЙЛ]`               | работает ли агент, связь, воркеры, последняя ошибка (код выхода 0 — работает)                                       |
| `agent logs [-f] [-n N]`                             | лог службы (`journalctl -u agent`): последние `N` записей (по умолчанию 100), `-f` — следить за новыми              |
| `agent restart [-config ФАЙЛ]`                       | перезапустить работающего агента (SIGUSR1; службу запускает systemd снова); воркеры — по `lifecycle.onAgentRestart` |
| `agent stop-workers [-config ФАЙЛ]`                  | остановить воркеры, оставшиеся работать после остановки агента                                                      |
| `agent cleanup [-config ФАЙЛ]`                       | уборка воркеров перед удалением агента с узла (её вызывает `uninstall`)                                             |
| `agent version`                                      | версия                                                                                                              |
| `agent help`                                         | список команд                                                                                                       |
| `agent boot-guard ФАЙЛ`                              | откат версии, которая не вышла на связь (вызывает служба systemd)                                                   |
| `agent sysmetrics`                                   | встроенный воркер метрик узла — агент запускает его сам (ниже)                                                      |

Утилита `agent-release` (`cmd/agent-release`) готовит публикацию самого агента (`scripts/release.sh`, CI); проекту она не нужна — его сборки делает `agent pack`:

| Команда                                          | Что делает                                                            |
| ------------------------------------------------ | --------------------------------------------------------------------- |
| `agent-release keygen`                           | пара ключей подписи сборок                                            |
| `agent-release manifest DIR VERSION [--worker…]` | `manifest.json` для сборок в каталоге (подпись — `AGENT_SIGNING_KEY`) |

## Как это работает

**Связь.** Соединение всегда открывает агент, поэтому входящие порты на узле не нужны: агент
работает за NAT. Связь — WebSocket (`/api/v1/agent-link`, канал `agent.v2`), в том числе через
HTTP-прокси и TLS. Агент раз в 10 с шлёт ping и ждёт ответа 5 с, сервер на SDK — раз в 5 с и
закрывает соединение после двух ping без ответа; соединение закрывается и открывается заново.
Обрыв без закрытия замечается за 10–15 с. Сервер может закрыть соединение с кодом-причиной, и агент поступает по нему:

- `1012` — сервер перезапускается или сменил ключ агента: подключиться сразу;
- `4401` — ключ отозван: зарегистрироваться заново, если есть токен; иначе ждать;
- `4409` — подключилась другая копия этого агента: 30 с не подключаться;
- `4429` (или ответ `429`/`503` с `Retry-After`) — сервер перегружен: подключиться не раньше
  названного срока (не позже 10 минут);
- остальное — переподключение с растущей паузой `server.reconnect` (от 1 с до 1 минуты).

**Виды сообщений.**

- **Важные** — события воркеров, итоги применения настроек (`config.applied`) и действий
  (`action.result`, `action.done`). Они записываются на диск (`<dataDir>/outbox`) и лежат там, пока сервер не
  подтвердит получение. Переживают и обрыв связи, и перезапуск агента. В очереди не больше
  `outbox.maxMessages` (10 000) сообщений: когда она полна, воркер получает отказ на новое событие (`503 OUTBOX_FULL`).
- **Поток** — `status`, `metrics`, `log`. Они нумеруются; без связи агент держит последние `server.streamBuffer` (600) в
  памяти и досылает после подключения.
- **Ответы** на запросы сервера к воркерам — только в том соединении, где пришёл запрос.

После подключения агент сначала досылает важные по порядку, потом поток, потом свежий `status`.

**Воркеры.** Воркер — процесс из списка `workers` в настройках. Агент запускает его с
переменными окружения `AGENT_WORKER` (имя), `AGENT_WORKER_SOCKET` (сокет, на котором воркер
слушает HTTP), `AGENT_SOCKET` (сокет агента), `AGENT_WORKER_TOKEN` (токен для запросов к агенту) и
`AGENT_VERSION`, ждёт, пока сокет начнёт отвечать (`startTimeout`, 1 минута), регистрирует воркер и передаёт ему
сохранённые настройки. Копия воркера всегда одна. Сокет воркера лежит в своём каталоге
(`<dataDir>/run/<имя>/`, права только у пользователя воркера); если путь слишком длинный для
сокета, каталог сокетов — во временном каталоге системы.

Обязательный минимум воркера — `GET /health` (самочувствие) и `GET /manifest` (что воркер умеет,
минимум `{version}`). Остальное необязательно (404 — не поддерживается): `PUT` и
`DELETE /config/{key}` — настройки, `GET /metrics` — свои метрики, `POST /cleanup` — уборка,
маршруты из манифеста — запросы сервера. Через сокет агента воркер шлёт события
(`POST /events`), спрашивает сервер и ждёт ответа (`POST /requests`), читает свои настройки
(`GET /config/{key}`) и сведения об агенте (`GET /context`).

Какие воркеры работают на узле, решают только настройки агента: сервер не может запустить на
узле свою программу, добавить или удалить воркер.

**Жизнь воркера** — блок `lifecycle` его настроек (таблица в «Настройках»; значения по умолчанию
подходят для многочасовой работы).

- **Вышел** — по `lifecycle.restart`: `on-failure` (по умолчанию) — перезапуск, если код выхода не
  0, процесс убит сигналом или завис; `always` — всегда; `never` — нет. Перезапуск — с растущей
  паузой `backoff` (1–30 с, `state: backoff`). Если задан `maxRestarts`, после стольких падений
  подряд воркер остаётся остановленным (`state: stopped`) до `worker.restart` или изменения его
  настроек.
- **Завис** — `GET /health` раз в `health.interval` (5 с); `health.failures` (3) раза подряд нет
  ответа за `health.timeout` (2 с) — процесс завершается и перезапускается как упавший. Выход
  процесса агент видит сразу: новый `state` уходит серверу внеочередным `status`.
- **Занят** — воркер отвечает на `GET /health` `busy: true`, пока идёт долгая работа. Плановая
  замена (`worker.restart`, обновление сборки, изменённые настройки воркера) ждёт её окончания,
  но не дольше `busy.timeout` (24 ч); в `status` — `pending: restart` или `update`. На
  `worker.restart` и `worker.update` агент сразу отвечает, что замена отложена, а её итог
  присылает отдельным важным сообщением `action.done`. `force: true` в действии — заменить
  сразу. От перезапуска зависшего `busy` не защищает.
- **Не зарегистрирован** — после каждого запуска (и подхвата) агент спрашивает `GET /health` и
  `GET /manifest` (срок `probeTimeout`, 2 с). Ответы корректны — `state: running`. Иначе —
  `state: invalid`, причина — в `status.workers[].message`: процесс работает, но настроек и
  запросов сервера не получает (`WORKER_INVALID`); агент пишет предупреждение в лог и повторяет
  проверку с паузой `backoff`, пока ответы не станут корректными.
- **Замена** — сначала уходит прежний процесс, потом запускается новый.
- **Остановка** — SIGTERM; не вышел за `stopTimeout` — SIGKILL. Воркер запускается в своём сеансе
  и группе процессов: сигналы получает вся группа, а потомков, переживших воркер, агент
  завершает. С `keepChildren: true` сигналы получает только сам воркер, и его потомки переживают
  его перезапуск. Остановка ничего на узле не убирает: то, что воркер создал, продолжает работать.

**Воркер переживает агента.** Перезапуск агента (`agent.update`, `agent restart`) и его остановка
(SIGTERM: `systemctl stop`, `systemctl restart`, Ctrl+C) по умолчанию воркер не трогают
(`onAgentRestart: keep`, `onAgentStop: keep`): долгая работа идёт дальше. `systemctl restart` и
`systemctl stop` шлют агенту один и тот же сигнал, поэтому агент их не различает; перезапуск,
который агент различает, — `agent restart` (сигнал SIGUSR1). О каждом запущенном процессе агент
пишет `<dataDir>/processes/<имя>.json` (pid, время запуска процесса по данным системы, сокет,
токен воркера, версия сборки, отпечаток настроек). Запускаясь, агент подхватывает живой процесс:
pid жив, время его запуска то же (pid, выданный системой другому процессу, не подходит), сокет
отвечает. Дальше агент следит за ним как за своим; настройки передаёт заново, только если их
последняя версия не применена; если настройки воркера или сборка с тех пор изменились — плановая
замена. Процесса нет или он чужой — обычный запуск; процесс воркера, которого нет в
настройках, агент останавливает. `stop` и `restart` — воркер останавливается вместе с агентом.
Встроенный `sysmetrics` и воркеры агента в контейнере (`update.mode: external`) всегда
останавливаются вместе с ним. Воркеры, оставшиеся после остановки агента, останавливает
`agent stop-workers`.

**Окружение воркера.** Из окружения агента воркер получает только обычные переменные (`PATH`,
`HOME`, `USER`, `LOGNAME`, `SHELL`, `LANG`, `LANGUAGE`, `LC_*`, `TZ`, `TMPDIR`, `TERM`, переменные
прокси, `SSL_CERT_FILE`, `SSL_CERT_DIR`) и перечисленные в `inheritEnv`; переменные `AGENT_*` агента
(например, токен регистрации) — никогда. С `user` воркер запускается от этого пользователя
(агенту нужен root) и получает его `HOME`, `USER`, `LOGNAME`. `env` воркера важнее всего.

**Вывод воркера.** stdout и stderr воркера — файлы `<dataDir>/logs/<имя>.log` и `<имя>.err.log`
(не каналы агента: воркер переживает его перезапуск). Агент читает их и пишет строки в свой лог и
журнал воркера (stdout — `info`, stderr — `warn`): последние `log.buffer` (5000) записей сервер
получает действием `agent.logs`. Подхватив воркер, агент продолжает чтение с места, где
остановился прежний, — строки, написанные без агента, тоже попадают в журнал. Файл больше
`logs.maxSize` (10 МБ) агент копирует в `.1` (прежние копии — `.2` … до `logs.maxFiles`) и
очищает. Строка длиннее 16 КБ обрезается.

**Настройки воркера.** У воркера может быть несколько ключей настроек (`main`, `limits`, …),
значение — любой JSON с версией от сервера. Агент хранит последнюю версию каждого ключа в
`<dataDir>/configs/<воркер>/<ключ>.json` (права 0600) и передаёт воркеру `PUT /config/{key}`: после
получения, после каждого запуска воркера и после перезапуска агента — так узел работает по
последним настройкам и без связи. Итог (`config.applied`) уходит серверу по одному на каждую пару
«версия + итог»; тело ответа воркера `2xx` (JSON до 64 КБ) — подробный итог в `result`. Не
применилось — повтор через 25 с. Новая версия, пришедшая во время применения,
ждёт его окончания; промежуточные пропускаются.

**Запросы сервера к воркеру** (`fetch`). Агент выполняет HTTP-запрос к сокету воркера и
отправляет ответ кусками до 64 КБ. Срок — из запроса (по умолчанию 30 с, не больше 10 минут),
одновременно — не больше 64 запросов, ответ — до 32 МБ. Служебные пути (`/config/*`, `/metrics`,
`/health`, `/cleanup`) сервер вызвать не может. К воркеру проходят только маршруты из его
манифеста (`routes`; задачи `/jobs*` — у воркера с `jobs`, тип в `POST /jobs` — из `jobs`);
остальное агент завершает сам: `ROUTE_UNDECLARED`, `JOB_UNKNOWN`. Настройка воркера
`routes: open` выключает эту сверку. Обрыв связи прерывает запросы этого соединения.

**Запросы воркера к серверу** (`POST /requests` на сокете агента). Тип — из `requests`
манифеста (иначе `400 REQUEST_UNDECLARED`). Без связи агент сразу отвечает
`503 AGENT_OFFLINE`; иначе шлёт серверу `request` в текущем соединении и ждёт `request.result`
(срок — `timeoutMs` воркера, по умолчанию 30 с, не больше 5 минут; не дождался — `504 TIMEOUT`,
связь оборвалась — `503 DISCONNECTED`). Ответ сервера — воркеру `200 { data }`, отказ —
`422 { code, message }`. Запрос не хранится на диске и не повторяется: одновременно — до 64.

**Метрики узла.** Их собирает встроенный воркер `sysmetrics` — та же программа агента,
запущенная дочерним процессом (`agent sysmetrics`): в процессе агента чтение системы не
выполняется, а сбой или зависание сбора не задевает агента. Это обычный HTTP-воркер: агент
вызывает его `GET /metrics` и кладёт ответ в `metrics.host`. В `agent.yaml` его описывать не
нужно; в статусе он виден с пометкой «встроенный», а сервер его не видит (ни настроек, ни
запросов). Он не запускается, если групп нет (`telemetry.metrics: []`). Группы:

| Группа         | Что                                                                   | По умолчанию |
| -------------- | --------------------------------------------------------------------- | ------------ |
| `cpu`          | загрузка процессора, всего и по ядрам                                 | да           |
| `load`         | средняя нагрузка за 1, 5 и 15 минут                                   | да           |
| `memory`       | память: занято, всего, доступно                                       | да           |
| `swap`         | swap                                                                  | да           |
| `disk`         | корневая файловая система `/` и файловые системы из `telemetry.disks` | да           |
| `diskio`       | чтение и запись дисков: байт/с и операций/с                           |              |
| `network`      | сеть всего: приём, отдача, ошибки, отброшенные пакеты                 | да           |
| `interfaces`   | сеть по каждому интерфейсу                                            | да           |
| `conntrack`    | число отслеживаемых сетевых соединений и предел (Linux)               | да           |
| `sockets`      | TCP-соединения по состояниям                                          |              |
| `processes`    | число процессов и потоков                                             |              |
| `fds`          | открытые файлы и предел (Linux)                                       |              |
| `uptime`       | сколько узел работает                                                 | да           |
| `temperatures` | датчики температуры (где доступны)                                    |              |
| `gpu`          | видеокарты через `nvidia-smi`, если он есть                           |              |

Точные поля — [sdk/spec §9](../sdk/spec/README.md#9-метрики-лог-и-самочувствие).

**Метрики воркеров.** Раз в `metricsIntervalMs` (его задаёт сервер в `welcome`) агент вызывает
`GET /metrics` всех зарегистрированных воркеров (срок `probeTimeout`, 2 с) и кладёт ответы в `metrics.workers`. Без связи
точки копятся вместе с остальным потоком.

**Самочувствие.** Ответ `GET /health` (`{ok, message?, info?}`) виден серверу в
`status.workers[].health`; изменение `ok` — внеочередной `status`.

**Манифест.** После каждого запуска воркера агент спрашивает `GET /manifest` (срок `probeTimeout`, 2 с): версия
воркера, ключи настроек, маршруты, события, задачи и запросы к серверу со схемами. Ответ
хранится в памяти и передаётся в
`hello.workers[].manifest` и `status.workers[].manifest`; изменился — внеочередной `status`.
`version` манифеста — версия воркера в `hello` и `status` (у воркера со сборкой с сервера —
версия сборки). Нет ответа, 404, ответ больше 64 КБ или без `version` — воркер не зарегистрирован
(`state: invalid`, формат и пределы — sdk/spec §12, §16). По манифесту агент отклоняет события,
которых нет в `events` (`400 EVENT_UNDECLARED`), запросы к серверу, которых нет в `requests`
(`400 REQUEST_UNDECLARED`), запросы сервера не по `routes` и `jobs` (`ROUTE_UNDECLARED`,
`JOB_UNKNOWN`) и не передаёт воркеру ключи настроек, которых нет в `configs`
(`CONFIG_KEY_UNKNOWN`). Значения по схемам он не проверяет — это делает сервер (опции SDK
`validateConfigs`, `validateJobs`, `validateRequests`, `validateEvents`). Встроенный
`sysmetrics` тоже отвечает `GET /manifest` — с версией агента.

**`watch`.** Пока на узел смотрят (например, открыта карточка агента в интерфейсе), сервер
присылает `watch`: присылать метрики чаще (не чаще раза в секунду) и лог подробнее — до срока
`untilMs`. Агент снимает его сам в срок или по пустому `watch`.

**Лог на сервер.** Агент отправляет записи своего лога и вывод воркеров пачками до 500 записей не
чаще раза в секунду — от уровня `log.forward` (по умолчанию предупреждения и ошибки) или
подробнее, если так просит `watch`.

**Несколько адресов и прокси.** В `server.urls` можно перечислить несколько адресов одного
бэкенда: агент подключается к первому доступному, а при отказе (сеть, нет ответа, ошибка 5xx)
переходит к следующему. Ключ агента один на все адреса. Запросы агента идут через HTTP-прокси
из `HTTPS_PROXY` / `HTTP_PROXY` (кроме адресов из `NO_PROXY`, localhost и петлевых адресов).

**Один агент на каталог данных.** `agent run`, `agent cleanup` и `agent stop-workers` держат блокировку
`<dataDir>/agent.lock`: второй агент с тем же `dataDir` не запускается («агент с этим dataDir уже
запущен»). Работающий агент раз в 5 с обновляет отметку `<dataDir>/agent.status`: версия, имя,
связь, воркеры с версиями настроек, последняя ошибка связи или регистрации. `agent status`
показывает это человеку (`--json` — для программ) и завершается с кодом 0, если агент с этим
`dataDir` запущен и отмечался не больше минуты назад, — так его использует `HEALTHCHECK` в
Docker. Если агент завершился с ошибкой (например, токен отклонён), `agent status` покажет и её.

**Связь без шифрования.** Если адрес сервера начинается с `http://` и это не localhost, агент
при старте пишет предупреждение: ключ агента и настройки воркеров идут открытым текстом.

**Остановка агента** (SIGTERM, SIGINT). Воркеры с `onAgentStop: stop` агент останавливает
(SIGTERM, через `stopTimeout` — SIGKILL), остальные работают дальше; следующий запуск агента их
подхватывает. Остановка ничего на узле не убирает.

**Удаление агента с узла — уборка.** `agent uninstall` вызывает `agent cleanup`: он по очереди
подхватывает работающий воркер (или запускает его), вызывает `POST /cleanup` (срок —
`stopTimeout`) и останавливает воркер; процессы воркеров, которых нет в настройках, тоже
останавливает. Воркер убирает всё, что создал: интерфейсы, правила, файлы. Связь с сервером
для этого не нужна, и сервер запустить уборку не может.

## Кто чем управляет

**Узел** (`agent.yaml`) решает, что на нём работает: какие воркеры и от какого пользователя,
какие метрики узла собирать, можно ли обновляться. Сервер это поменять не может.

**Сервер** задаёт частоты `status` и метрик, присылает настройки воркеров и `watch`, отправляет
запросы к воркерам и встроенные действия:

| Действие          | Что делает                                                                                                |
| ----------------- | --------------------------------------------------------------------------------------------------------- |
| `worker.restart`  | остановить и запустить воркер заново                                                                      |
| `worker.update`   | обновить сборку воркера с сервера (с возвратом прежней)                                                   |
| `agent.update`    | обновить программу агента (только при `update.mode: self`); без ссылки — сборка из каталога сборок агента |
| `agent.rotateKey` | сменить секрет агента                                                                                     |
| `agent.logs`      | последние записи журнала агента или воркера (по умолчанию 200, не больше 5000)                            |

Аргументы и итоги — [sdk/spec §10](../sdk/spec/README.md#10-встроенные-действия).

## Настройки

Настройки — файл YAML и переменные окружения `AGENT_*`; переменные важнее файла. Обязателен только
адрес сервера (`server.url`), для первого подключения ещё нужен токен регистрации
(`enroll.token`); всё остальное имеет значения по умолчанию. Поэтому агента можно запустить вообще
без файла: `AGENT_SERVER_URL=… AGENT_ENROLL_TOKEN=… agent run`.

Где агент ищет файл:

1. флаг `-config ФАЙЛ`, или `--env ИМЯ` — файл `agent.ИМЯ.yaml` в папке агента (см. ниже);
2. `--instance ИМЯ` — настройки экземпляра на узле (`/etc/agent-ИМЯ/agent.yaml`);
3. переменная `AGENT_CONFIG`;
4. `agent.yaml` в папке агента — рядом с программой, затем в текущем каталоге;
5. файл по умолчанию, если он есть, — `/etc/agent/agent.yaml` на Linux и `~/.agent/agent.yaml`
   на macOS.

Папка агента — каталог, где рядом лежат программа и её настройки. У программы, поставленной
службой (`/opt/agent…/bin/agent`), папки нет: её настройки — в `/etc`. Каталог данных по умолчанию
— `/var/lib/agent` на Linux и `~/.agent/data` на macOS.

- `agent init [ПАПКА] [--server URL] [--token ТОКЕН] [--force]` (то же — `agent config init`)
  разворачивает папку агента (без `ПАПКИ` — в текущем каталоге) — раздел «Папка агента» ниже.
  Готовые файлы не перезаписывает (для этого `--force`).
- `agent init -config ФАЙЛ [--server URL] [--token ТОКЕН] [--name ИМЯ] [--data-dir КАТАЛОГ]` создаёт
  один файл настроек с пояснениями: заданные значения и закомментированные примеры всех разделов со
  значениями по умолчанию. Если указан токен, файл доступен только владельцу.
- `agent config check [-config ФАЙЛ | --env ИМЯ]` проверяет настройки так, как их прочитает агент:
  цепочку файлов (`extends`), файлы переменных (`envFiles`), `agent.env` рядом с файлом (его читает
  служба) и переменные окружения. Ошибки показывает с файлом и номером строки, неизвестные поля
  (опечатки) — замечаниями (о них агент предупреждает и при запуске), а если всё в порядке,
  печатает итоговые значения (токен скрыт) и у каждого — откуда оно: файл и строка или переменная
  окружения; значение без пометки — по умолчанию. Если агент ещё не зарегистрирован, а токена нет,
  — тоже замечание.

В файле можно писать `${ПЕРЕМЕННАЯ}` — подставится из окружения или из файлов переменных.
Длительности пишутся как `30s`, `10m`.

### Папка агента

Папка агента — программа, её настройки и воркеры в одном месте; её можно положить в репозиторий
проекта (программа и секреты в git не попадают). `agent init agent` создаёт:

| Файл                             | Что                                                                                  |
| -------------------------------- | ------------------------------------------------------------------------------------ |
| `agent`                          | программа агента: `init` копирует себя сюда                                          |
| `agent.yaml`                     | настройки для этой машины: `./agent run` читает его без флагов                       |
| `agent.prod.yaml`                | боевые узлы: `extends: agent.yaml`, `update.mode: self`, журнал в JSON               |
| `.env`, `.env.example`           | `AGENT_SERVER_URL`, `AGENT_ENROLL_TOKEN` для этой машины (`.env` — только владельцу) |
| `.env.prod.example`              | образец `.env.prod` для боевых узлов                                                 |
| `.gitignore`                     | программа, `.data/`, `.env`, `.env.prod`, архивы                                     |
| `README.md`, `workers/README.md` | что где лежит и как подключить воркер                                                |

Воркер проекта — папка в `workers/` с исполняемым `run` и файлом `VERSION`, в `agent.yaml` —
`- path: workers/<имя>`. Заготовка — `agent worker new <имя> [--lang python|go]`:

| Файл                                                                                                                                                                                                            | Python                                 | Go                                                                                                                                                                                        |
| --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| база (не правится): сокет, `GET /health` (с `busy`), `GET /manifest` из объявлений, настройки, задачи (ход, отмена, повтор `jobId`, продолжение после перезапуска), события, запросы к бэкенду, метрики, уборка | `agent_worker.py`                      | `agent_worker.go` (стандартная библиотека, Go ≥ 1.22)                                                                                                                                     |
| код воркера: маршруты, задачи, ключи настроек, события                                                                                                                                                          | `worker.py` — класс-наследник `Worker` | `worker.go` — тип со встроенной базой `struct{ *Worker }`; необязательные методы `Health`, `Metrics`, `ValidateConfig`, `OnConfig`, `Cleanup`, `PrepareJob`, `OnStart` база вызывает сама |
| запуск                                                                                                                                                                                                          | `run` — `python3 worker.py`            | `run` — собрать из исходников и запустить (своя машина); `build` — программа под платформу узла для `agent pack`                                                                          |
| версия                                                                                                                                                                                                          | `VERSION`                              | `VERSION`; `go.mod` — если у папки агента нет своего                                                                                                                                      |

База одна и та же у всех воркеров проекта и лежит в папке каждого — воркер самодостаточен. В первой строке базы — её версия (`agent-worker-base: N`);
`agent worker sync` обновляет базы всех воркеров папки до версии этой программы (более новые не
трогает). Продолжение задач после перезапуска (`resumable`) хранит состояние в
`WORKER_STATE_DIR` (переменная воркера в `env`).

### Несколько файлов: `extends` и `envFiles`

Настройки для разных окружений не повторяют друг друга: общий файл и поверх него — файл окружения.

```yaml
# agent.yaml — общее: воркеры, журнал, метрики
workers:
  - name: example
    command: ["./run"]
    dir: workers/example
```

```yaml
# agent.prod.yaml — поверх agent.yaml
extends: agent.yaml
envFiles: [.env.prod] # KEY=VALUE: AGENT_ENROLL_TOKEN=…, AGENT_SERVER_URL=…
server:
  url: ${AGENT_SERVER_URL}
workers:
  - name: example # тот же воркер: env дописывается к общему
    env: { EXAMPLE_MODE: prod }
```

`agent run --env prod` (или `-config agent.prod.yaml`) читает сначала `agent.yaml`, затем
`agent.prod.yaml`:

- словари сливаются по ключам, списки заменяются целиком, воркеры (`workers`) сливаются по имени:
  воркер с тем же `name` дополняется, новый добавляется в конец; цепочка — до 8 файлов;
- `envFiles` — файлы `KEY=VALUE` (как у `agent.env`): из них берутся `${ИМЯ}` и переменные `AGENT_*`;
  окружение процесса важнее их, более поздний файл (в списке и в цепочке) — важнее раннего; файла
  нет — замечание, не ошибка;
- относительные пути — от файла, в котором записаны: `extends`, `envFiles`, `dataDir`,
  `server.caFile`, `server.certFile`, `server.keyFile`, `workers[].dir`.

| `inheritEnv`    | —            | какие ещё переменные окружения агента передать воркеру (`EXAMPLE_*` — все с этим началом); `AGENT_*` нельзя                                                                                                                 |
| `user`          | —            | запустить воркер от другого пользователя (агент должен работать от root)                                                                                                                                                    |
| `release`       | `false`      | `true` — воркер со сборкой с сервера: сборку ведёт агент (`<dataDir>/workers/<name>/current`), сервер обновляет её действием `worker.update`; без `command` запускается сам файл сборки или `run` из архива                 |
| `path`          | —            | папка воркера (путь — от файла настроек): агент запускает в ней `command`, по умолчанию `./run`; имя по умолчанию — имя папки; вместо `dir`, не вместе с `release` и `from`                                                 |
| `from`          | —            | `agent` — сборка из релиза агента той же версии (воркер со сборкой, как `release: true`); если её нет в `<dataDir>/workers/<name>`, агент скачивает её сам (`update.releases`)                                              |
| `lifecycle`     | —            | жизнь воркера — таблица ниже                                                                                                                                                                                                |
| `logs.maxSize`  | `10MB`       | файл вывода воркера больше этого (`512KB`, `10MB`, `1GB`; не меньше `64KB`) копируется в `.1` и очищается                                                                                                                   |
| `logs.maxFiles` | `1`          | сколько копий хранить (`.1` … `.N`, 0–100; `0` — без копий)                                                                                                                                                                 |
| `routes`        | `strict`     | `strict` — сервер вызывает у воркера только маршруты и задачи из его манифеста; `open` — любой путь, кроме служебных, тип задачи не сверяется (для воркера, который ещё не описал маршруты). Применяется без замены воркера |

Жизнь воркера (`workers[].lifecycle`). Её изменение (перечитывание настроек) применяется без
перезапуска воркера.

| Поле                   | По умолчанию | Что                                                                                                                                        |
| ---------------------- | ------------ | ------------------------------------------------------------------------------------------------------------------------------------------ |
| `onAgentRestart`       | `keep`       | перезапуск агента (`agent.update`, `agent restart`): `keep` — воркер работает дальше, новый агент его подхватывает; `restart` — остановить |
| `onAgentStop`          | `keep`       | остановка агента (SIGTERM, SIGINT; в том числе `systemctl restart`): `keep` \| `stop`                                                      |
| `restart`              | `on-failure` | после выхода процесса: `always` — перезапуск; `on-failure` — если код не 0, сигнал или завис; `never` — нет                                |
| `backoff.min`, `.max`  | `1s`, `30s`  | пауза перед перезапуском после падения, растёт от `min` до `max`                                                                           |
| `maxRestarts`          | `0`          | падений подряд не больше (`0` — без предела); превышено — воркер остаётся остановленным до `worker.restart` или изменения его настроек     |
| `startTimeout`         | `1m`         | сколько ждать, пока сокет воркера начнёт отвечать                                                                                          |
| `stopTimeout`          | `30s`        | сколько ждать выхода после SIGTERM; потом — SIGKILL; ещё — срок `POST /cleanup` при уборке                                                 |
| `keepChildren`         | `false`      | `true` — сигналы остановки получает только сам воркер: его дочерние процессы переживают его перезапуск                                     |
| `busy.wait`            | `true`       | плановая замена ждёт, пока `GET /health` отвечает `busy: true`                                                                             |
| `busy.timeout`         | `24h`        | дольше не ждать — заменить                                                                                                                 |
| `health.interval`      | `5s`         | как часто вызывать `GET /health`; `0s` — не проверять; зависший воркер перезапускается через `interval × failures` (15–20 с)               |
| `health.timeout`       | `2s`         | срок ответа на `GET /health` (не больше `interval`)                                                                                        |
| `health.failures`      | `3`          | сколько раз подряд без ответа — завис, перезапуск; `0` — не перезапускать                                                                  |
| `probeTimeout`         | `2s`         | срок `GET /manifest`, `GET /metrics` и проверки `GET /health` при регистрации воркера                                                      |
| `configRetry`          | `25s`        | повтор настроек, которые воркер не применил                                                                                                |
| `updateHealthyTimeout` | `1m`         | сколько новая сборка (`worker.update`) может не отвечать `ok: true`; потом — возврат прежней                                               |

Постоянные (их задаёт формат связи, [sdk/spec §16](../sdk/spec/README.md#16-пределы-и-сроки)):
пределы размеров сообщений, сроки `hello`, `welcome`, ping и pong, срок `PUT` и `DELETE /config`
(30 с), срок `fetch` по умолчанию, частота пачек `log`.

Пример:

```yaml
server:
  url: https://api.example.com
dataDir: /var/lib/agent
labels:
  zone: eu
workers:
  - name: report
    command: ["/opt/workers/report/report-worker"]
    lifecycle:
      stopTimeout: 1m
      busy: { timeout: 6h } # замена ждёт окончания отчёта не дольше 6 ч
  - name: example
    release: true
```

### Изменить настройки, не останавливая агента

Поправьте `agent.yaml` и выполните `systemctl reload agent` (агент получает SIGHUP): он
перечитает файл, не теряя outbox.

- **Сразу, без разрыва связи:** `log.level`, `log.format`, `log.forward`, `telemetry.*` (встроенный
  воркер метрик перезапускается).
- **С переподключением** (новый `hello`): имя, метки, воркеры — новые запускаются, удалённые
  останавливаются, изменённые заменяются (замена ждёт, пока воркер занят); изменённые только
  `lifecycle`, `logs` и `routes` применяются без замены.
- **Только перезапуском** (`agent restart` или `systemctl restart agent`): `server.*`, `dataDir`,
  `update.*`, `enroll.token`, `outbox.maxMessages`, `log.buffer`. Агент напишет в лог, какие ключи требуют перезапуска, а остальное применит.
- Если в файле ошибка, агент пишет её в лог и продолжает работать с прежними настройками.

Сервер `agent.yaml` менять не может: что работает на узле, решает только сам узел.

## Установка

Агента ставят службой systemd на Linux, запускают в контейнере Docker или — для разработки —
просто в терминале. `<версия>` ниже — номер версии без `v`, например `1.0.0`. Адрес сервера и
токен регистрации даёт бэкенд.

На узле после установки всегда одно и то же: программа (`/opt/agent/bin/agent`), один файл
настроек (`/etc/agent/agent.yaml`) и переменные службы (`/etc/agent/agent.env`), каталог данных с
воркерами (`/var/lib/agent`) и служба systemd. Откуда всё это приходит:

| Откуда                   | Команда на узле                                                                              | Настройки                                                    |
| ------------------------ | -------------------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| папка агента             | `sudo ./agent install --env prod` в папке                                                    | `agent.yaml` + `agent.prod.yaml` одним файлом, воркеры папки |
| архив `agent pack`       | `tar xzf agent-prod-….tar.gz && cd agent && sudo ./agent install`                            | то же, из архива                                             |
| бэкенд (`install.sh`)    | `curl -fsSL https://api.example.com/api/v1/agent-link/install.sh \| sudo sh -s -- --token …` | шаблон с адресом бэкенда, воркеры — `--worker`               |
| программа агента и флаги | `sudo ./agent install --server URL --token ТОКЕН [--worker …]`                               | шаблон, воркеры — `--worker` с каталога сборок               |

### Из папки агента и архива

`agent pack --env prod` упаковывает папку агента для узлов — по архиву на платформу
(`--platform`, по умолчанию `linux/amd64,linux/arm64`) в папку агента (`--out` — другой каталог):
`agent-prod-<версия>-linux-amd64.tar.gz`. В архиве — папка `agent/`:

| Что                              | Откуда                                                                                                                                         |
| -------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| `agent`                          | программа под платформу узла: эта же или из каталога сборок агента той же версии (подпись сверяется)                                           |
| `agent.yaml`, `agent.prod.yaml`  | файлы цепочки `extends` как есть                                                                                                               |
| `workers/<имя>/`                 | воркеры из папки (`path`) — для `agent run` прямо из архива                                                                                    |
| `release/manifest.json` и сборки | те же воркеры архивами `<имя>-<VERSION>-<os>-<arch>.tar.gz` (версия — файл `VERSION` воркера) и сборки воркеров `from: agent` из релиза агента |
| `bundle.json`                    | версия агента, файл настроек, окружение, платформа, открытые ключи подписи                                                                     |
| `.env.prod`                      | только с `--with-env`: файлы переменных с секретами                                                                                            |

Воркер с исполняемым `build` (программа под платформу — например, на Go) собирается под каждую
платформу архива: `build` запускается в папке воркера с `GOOS` и `GOARCH` (и `AGENT_OS`,
`AGENT_ARCH`) и `OUT` — каталогом итога, где должен появиться исполняемый `run`; в архив и в
сборку воркера идёт итог сборки (и `VERSION`), а не исходники. У воркера без `build` в архив идёт
папка как есть, кроме служебных файлов (`__pycache__`, `*.pyc`, `.git`) и строк его `.packignore`
— шаблонов путей от папки воркера или имён (`tests/` — только каталоги, `*.tmp`, `#` — пояснение).

`--release-out КАТАЛОГ` — ещё и общий каталог сборок воркеров из папки под все платформы
(`manifest.json` и архивы): его раздаёт бэкенд (опция SDK `releasesDir`), чтобы обновлять воркеры
узлов действием `worker.update`. Файлы настроек и воркеры должны лежать в папке агента. С `AGENT_SIGNING_KEY` в окружении (ключ —
`agent keygen`) сборки воркеров подписаны, открытый ключ — в `bundle.json`; закрытый в архив не
попадает. Без ключа воркеры поставить можно, а обновить с сервера (`worker.update`) — нет.

`agent install` из распакованного архива (рядом с программой — `bundle.json`) или с `--env` в
папке агента (тогда архив собирается тут же, с файлами переменных):

1. сводит цепочку файлов в один `/etc/agent/agent.yaml`: без `extends` и `envFiles`, `dataDir` —
   каталог узла, воркеры из папки — воркеры со сборкой (`release: true`), `instance` и `install`
   убираются; `${ИМЯ}` остаются как есть, а значения из файлов переменных — только те, что
   нужны: из `${ИМЯ}` настроек и `AGENT_*` — уходят в `/etc/agent/agent.env`
   (`AGENT_ENROLL_TOKEN` — токен, `AGENT_UPDATE_PUBLIC_KEYS` — ключи; `--server` — в
   `AGENT_SERVER_URL`, он важнее файла; `AGENT_SIGNING_KEY` на узел не попадает);
2. ставит сборки воркеров из `release/` в `/var/lib/agent/workers/<имя>/current` (подпись
   сверяется ключами агента и ключом из `bundle.json`);
3. берёт `instance` и раздел `install` из настроек, если нет флагов (`--instance`, `--packages`,
   `--sysctl`, …): флаги важнее;
4. дальше — как обычная установка (ниже). Прежний `agent.yaml`, если он отличается, остаётся
   рядом как `agent.yaml.bak`.

Токен — `--token` или `AGENT_ENROLL_TOKEN` в файле переменных архива (`--with-env`). Удалить —
`sudo ./agent uninstall [--purge]` из того же архива: экземпляр берётся из его настроек.

### Linux со systemd

Подходит любой Linux с systemd: Debian и Ubuntu, RHEL и Fedora, SUSE и т. п. Нужны права root. На
узлах без systemd (Alpine и другие) `agent install` сразу завершается с ошибкой и ничего не меняет —
там агента запускают в контейнере.

**Вручную — три команды.** Скачайте сборку из GitHub Release и поставьте ею службу:

```bash
v=<версия>; arch=amd64   # arm64 — для ARM
curl -fLo agent https://github.com/epifanovmd/agent/releases/download/v$v/agent-linux-$arch && chmod +x agent
sudo ./agent install --server https://api.example.com --token <токен>
```

Контрольная сумма сборки — в `manifest.json` той же версии (сравните с `sha256sum agent`). После
установки скачанный файл не нужен: программа лежит в `/opt/agent/bin/agent`, а команда `agent`
доступна из любого каталога. Проверить, что всё работает:

```bash
sudo agent status    # работает ли агент, есть ли связь, воркеры, последняя ошибка
sudo agent logs -f   # лог службы (то же, что journalctl -u agent -f)
```

Если `sudo agent` отвечает «command not found» (так бывает на RHEL, Rocky, Alma: у sudo свой список
каталогов без `/usr/local/bin`), вызывайте программу полным путём: `sudo /opt/agent/bin/agent status`.

Своя сборка ставится так же: `sudo dist/<версия>/agent-linux-amd64 install --server … --token …`
(`make release`).

**С бэкенда — одной командой.** Бэкенд на SDK раздаёт установщик `install.sh`, в который уже
вписаны его адрес и ключи проверки подписи сборок (`DEFAULT_UPDATE_KEYS` — автор агента и проект, уходят
`agent install` флагами `--update-key`), и собирает эту строку сам (`installCommand`, см.
[sdk/docs](../sdk/docs/README.md)):

```bash
curl -fsSL https://api.example.com/api/v1/agent-link/install.sh | sudo sh -s -- --token <токен>
```

`install.sh` скачивает с бэкенда сборку под эту машину (бэкенд может перенаправить загрузку на
GitHub; `file` в `manifest.json` может быть и ссылкой `https://`), сверяет контрольную сумму и запускает
`agent install`, передав ему остальные флаги. Свои флаги у него такие: `--server URL` (в установщик
от бэкенда адрес уже вписан), `--binary ПУТЬ` (поставить сборку из файла), `--releases URL` (откуда
скачать; передаётся и `agent install`), `--ca-file ПУТЬ` (свой корневой сертификат для загрузки;
передаётся и `agent install`), `--instance ИМЯ` (экземпляр, см. «Несколько агентов на одном узле»;
передаётся и `agent install`), `--uninstall [--purge]`.

**Что делает `agent install`:**

1. проверяет, что есть root и systemd;
2. создаёт пользователя службы `agent` (системный, без входа в систему), если его нет;
3. кладёт программу в `/opt/agent/bin/agent` и ссылку на неё в `/usr/local/bin/agent`;
4. создаёт `/etc/agent/agent.yaml` с пояснениями (как `agent init -config`), если файла ещё нет; готовый
   файл не меняет;
5. сохраняет токен в `/etc/agent/agent.env` — читать его может только служба;
6. если заданы флаги — ставит системные пакеты, параметры ядра и сборки воркеров;
7. создаёт службу `agent`, включает её и запускает. Служба сама перезапускается при сбое.

Повторный запуск (или та же команда с бэкенда) обновляет программу и службу. Ключ агента,
`agent.yaml` и `agent.env` сохраняются; заново переданные `--token` и `--update-key` заменяют
прежние.

Что где лежит:

| Что                  | Где                                                      |
| -------------------- | -------------------------------------------------------- |
| программа            | `/opt/agent/bin/agent` (ссылка — `/usr/local/bin/agent`) |
| настройки            | `/etc/agent/agent.yaml`                                  |
| токен и ключи сборок | `/etc/agent/agent.env`, доступ только у службы           |
| свой сертификат CA   | `/etc/agent/ca.pem` (если задан `--ca-file`)             |
| данные               | `/var/lib/agent`                                         |
| служба               | `agent` (`systemctl status agent`)                       |
| файл службы          | `/etc/systemd/system/agent.service`                      |
| журнал установки     | `/etc/agent/install-state`                               |
| параметры ядра       | `/etc/sysctl.d/90-agent.conf` (если задан `--sysctl`)    |

В журнал установки записывается, что поставлено: пакеты, которых не было (и какие нужны воркерам), созданный пользователь
службы, параметры ядра с их прежними значениями, режим остановки, — чтобы при удалении точно
вернуть как было.

Флаги `agent install` (список — `agent install -h`):

| Флаг                                                                                              | Что                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |

Архив `.tar.gz` распаковывается в каталог; что в нём запускать, берётся из `manifest.json` (`command`), иначе — `./run`. `file` сборки в манифесте — имя в каталоге сборок или ссылка `https://` на любой хост (`http://` — только если и `--releases` или сервер `http://`) |

| `--rw-path ПУТЬ`                                                                                  | разрешить службе запись в этот каталог; установка создаёт его и отдаёт пользователю службы (можно несколько раз)                                                                                                                                                                                                                                                                                                                                                                  |
| `--privileged`                                                                                    | агент и воркеры — от root и без ограничений (`--user` не действует). Нужно воркерам, которые настраивают сам узел: сеть, firewall, системные файлы. Включайте, только если это действительно нужно                                                                                                                                                                                                                                                                                |
| `--packages "…"`                                                                                  | поставить системные пакеты для воркеров (apt, dnf, yum, apk, zypper), например `"jq curl"`                                                                                                                                                                                                                                                                                                                                                                                        |
| `--packages-apt`, `--packages-dnf`, `--packages-yum`, `--packages-apk`, `--packages-zypper` `"…"` | свои имена пакетов для этого менеджера — на узле с ним заменяют `--packages`                                                                                                                                                                                                                                                                                                                                                                                                      |
| `--sysctl КЛЮЧ=ЗНАЧЕНИЕ`                                                                          | параметр ядра для воркеров, например `vm.max_map_count=262144` (можно несколько раз)                                                                                                                                                                                                                                                                                                                                                                                              |
| `--kill-mode process\|mixed`                                                                      | `process` (по умолчанию) — systemd останавливает только агента: воркеры работают дальше по `lifecycle.onAgentStop` и переживают перезапуск агента; `mixed` — SIGTERM получает агент, а оставшиеся процессы службы systemd завершает SIGKILL: воркеры не переживают перезапуск агента. Запоминается для повторной установки                                                                                                                                                        |
| `--stop-timeout СРОК`                                                                             | сколько systemd ждёт остановки службы (по умолчанию `15min`)                                                                                                                                                                                                                                                                                                                                                                                                                      |

**Поменять настройки.** Поправьте `/etc/agent/agent.yaml`, проверьте его и примените без
перезапуска:

```bash
sudo nano /etc/agent/agent.yaml
sudo agent config check          # ошибки — с номером строки; итоговые значения
sudo systemctl reload agent
```

Добавить воркер со сборкой с сервера на уже установленный узел —
`sudo agent install --server https://api.example.com --worker example` (адрес нужен, чтобы
скачать сборку; вместо него можно `--releases URL`): сборка ставится, а если `agent.yaml` уже
был, установщик подскажет, какие строки добавить в `workers`.

### Docker

Образы (`deploy/Dockerfile`):

- `ghcr.io/epifanovmd/agent:<версия>` — минимальный: только агент на Alpine;
- `ghcr.io/epifanovmd/agent:<версия>-python` — агент и Python для воркеров на Python.

В образе уже заданы `AGENT_UPDATE_MODE=external` (обновление — новым образом),
`AGENT_LOG_FORMAT=json` и каталог данных `/var/lib/agent`. Остальное — переменными окружения из
таблицы «Настройки», файл настроек не обязателен:

```bash
docker run -d --name agent --restart unless-stopped \
  -e AGENT_SERVER_URL=https://api.example.com \
  -e AGENT_ENROLL_TOKEN=<токен> \
  -e AGENT_NAME=node-01 \
  -v agent-data:/var/lib/agent \
  ghcr.io/epifanovmd/agent:<версия>
```

То же в Docker Compose:

```yaml
services:
  agent:
    image: ghcr.io/epifanovmd/agent:<версия>
    restart: unless-stopped
    environment:
      AGENT_SERVER_URL: https://api.example.com
      AGENT_ENROLL_TOKEN: ${AGENT_ENROLL_TOKEN}
      AGENT_NAME: node-01
    volumes:
      - agent-data:/var/lib/agent
    stop_grace_period: 1m # не меньше stopTimeout воркеров: в контейнере они останавливаются с агентом
volumes:
  agent-data:
```

Ключ агента, outbox и настройки воркеров хранятся в томе `/var/lib/agent`: без тома после пересоздания
контейнера агент зарегистрируется заново. Агент работает от пользователя с uid `10001`; если вместо
тома подключаете каталог машины (`-v /srv/agent:/var/lib/agent`), отдайте его этому пользователю:
`sudo chown 10001 /srv/agent`.

Проверка живости встроена в образ (`HEALTHCHECK` — `agent status`): контейнер `healthy`, пока
агент работает. Посмотреть состояние и настройки:

```bash
docker exec agent agent status
docker exec agent agent config check
docker logs -f agent
```

Воркеры проекта добавляют своим образом — `FROM` одного из этих и файл настроек со списком
воркеров (агент найдёт его сам):

```dockerfile
FROM ghcr.io/epifanovmd/agent:<версия>-python
COPY workers/ /app/
COPY agent.yaml /etc/agent/agent.yaml
```

### macOS и разработка

Службой на macOS агент не ставится (`agent install` — только для Linux); его запускают в
терминале из папки агента:

```bash
./agent init agent --server http://localhost:8080 --token <токен>   # папка agent/ рядом
agent/agent config check
agent/agent run
agent/agent status   # в другом терминале
```

Один файл без папки — `agent init -config ~/.agent/agent.yaml …`: агент найдёт его и сам (файл по
умолчанию на macOS), данные — в `~/.agent/data`.

### Удаление

```bash
sudo agent uninstall           # служба и программа; настройки и данные остаются
sudo agent uninstall --purge   # всё, что поставила установка
```

С бэкенда — тем же установщиком:
`curl -fsSL https://api.example.com/api/v1/agent-link/install.sh | sudo sh -s -- --uninstall [--purge]`.
Экземпляр — с `--instance ИМЯ` (раздел «Несколько агентов на одном узле»).

`agent uninstall` останавливает службу, даёт воркерам убрать за собой (`agent cleanup`, от
пользователя службы: каждый воркер получает `POST /cleanup`), затем удаляет службу, программу
(`/opt/agent` и ссылку `/usr/local/bin/agent`) и параметры ядра из `--sysctl`, возвращая их
прежние значения. Без `--purge` настройки и данные остаются: повторная установка продолжит с тем же
ключом агента. С `--purge` удаляются ещё `/etc/agent`, `/var/lib/agent`, пакеты, которые поставила
установка, и созданный ею пользователь службы; root и пользователей, которые были до установки,
не трогает.

### Обновление агента

Обычно агента обновляет сервер — действием `agent.update` (раздел «Обновление» ниже). На узле —
`sudo agent upgrade`: новая версия из каталога сборок агента, служба перезапускается, откат — как
у `agent.update`. Или той же установкой с новой сборкой: `sudo ./agent install` (флаги не нужны,
настройки и ключ агента сохраняются), новым архивом `agent pack` или командой с бэкенда. В Docker
— новым образом.

### Несколько агентов на одном узле

Один агент связан с одним бэкендом. Если на узле работают воркеры двух разных бэкендов (например,
одного сервиса и другого, у каждого свой сервер), ставят два агента — **экземпляра**. Экземпляр
получает имя флагом `--instance ИМЯ` (строчная латиница, цифры и «-», первая — буква, до 32
символов); установка без флага — экземпляр по умолчанию с обычными путями, так что простая
установка не меняется.

```bash
sudo ./agent install --server https://a.example.com --token <токен A>                    # по умолчанию
sudo ./agent install --instance b --server https://b.example.com --token <токен B>       # экземпляр b
curl -fsSL https://b.example.com/api/v1/agent-link/install.sh | sudo sh -s -- --instance b --token <токен B>
```

У экземпляра `ИМЯ` все пути — с окончанием `-ИМЯ`, общего с другими экземплярами у него нет:

| Что                 | По умолчанию                                                    | Экземпляр `ИМЯ`                   |
| ------------------- | --------------------------------------------------------------- | --------------------------------- |
| программа           | `/opt/agent/bin/agent`                                          | `/opt/agent-ИМЯ/bin/agent`        |
| ссылка в PATH       | `/usr/local/bin/agent`                                          | `/usr/local/bin/agent-ИМЯ`        |
| настройки           | `/etc/agent/agent.yaml`, `agent.env`, `ca.pem`, `install-state` | `/etc/agent-ИМЯ/…`                |
| данные (`dataDir`)  | `/var/lib/agent`                                                | `/var/lib/agent-ИМЯ`              |
| служба              | `agent`                                                         | `agent-ИМЯ`                       |
| пользователь службы | `agent`                                                         | `agent-ИМЯ`                       |
| параметры ядра      | `/etc/sysctl.d/90-agent.conf`                                   | `/etc/sysctl.d/90-agent-ИМЯ.conf` |

- **Своя программа** — у каждого экземпляра: сервер обновляет их по отдельности, версии могут
  различаться, откат неудачного обновления — тоже свой.
- **Свой пользователь** — ключ агента, настройки воркеров и их данные одного экземпляра недоступны
  другому (`--user` задаёт другого, `--privileged` — root).
- **Воркеры** не пересекаются, даже с одинаковыми именами: сокеты, процессы, блокировка и сборки
  воркеров лежат в `dataDir` своего экземпляра.

Команды работают с экземпляром по флагу `--instance ИМЯ` или через его ссылку `agent-ИМЯ` (программа
узнаёт экземпляр по своему пути):

```bash
sudo agent status --instance b       # то же: sudo agent-b status
sudo agent logs -f --instance b      # journalctl -u agent-b -f
sudo agent config check --instance b
sudo systemctl reload agent-b        # применить настройки
sudo agent restart --instance b      # также stop-workers, cleanup
sudo agent install --instance b      # обновить экземпляр b
sudo agent uninstall --instance b [--purge]
```

Удаление одного экземпляра не трогает остальные. Системные пакеты и параметры ядра, нужные и
другому экземпляру, остаются (параметр ядра сохраняет его значение); запись о них переходит в
журнал установки того экземпляра, и удалит их последний, кому они нужны. То же с пользователем
службы, если экземпляры работают от одного пользователя.

## Работа на узле

**Лог.** Агент пишет лог в поток ошибок (stderr); под systemd его собирает journald:
`agent logs -f` (то же, что `journalctl -u agent -f`). Своих файлов лога агент не ведёт (файлы —
только у вывода воркеров, `logs/`, с ротацией по `logs.maxSize`), поэтому и ротация — на стороне
journald (`SystemMaxUse=` и `MaxRetentionSec=` в `/etc/systemd/journald.conf`). В контейнере лог
читает `docker logs`, а сколько его хранить, решают настройки логов Docker.

**Резервная копия.** Всё, что агент хранит сам, лежит в `/var/lib/agent` (`dataDir`):

| Файл или каталог             | Что                                                                      |
| ---------------------------- | ------------------------------------------------------------------------ |
| `credentials.json`           | ключ агента: по нему сервер узнаёт этот узел                             |
| `outbox/`                    | важные сообщения, которые ещё не дошли до сервера                        |
| `configs/`                   | последние настройки воркеров по ключам: воркер получает их и без связи   |
| `workers/`                   | сборки воркеров с сервера                                                |
| `run/`                       | сокеты агента и воркеров                                                 |
| `processes/`                 | запущенные процессы воркеров: по ним новый запуск агента их подхватывает |
| `logs/`                      | вывод воркеров: `<имя>.log` (stdout), `<имя>.err.log` (stderr) и копии   |
| `agent-update.json`          | `agent.update` ждёт запуска новой версии, чтобы отправить итог           |
| `update-check.json`          | итог последней проверки новой версии агента                              |
| `agent.lock`, `agent.status` | блокировка каталога и отметка «агент работает» (`agent status`)          |
| `agent.error`                | ошибка, с которой агент завершился в последний раз (`agent status`)      |

**Что в каталоге секретно.** `credentials.json` (ключ агента), `configs/` (значения настроек как
есть — в них бывают пароли и токены), `outbox/` (события и итоги, в том числе `config.applied`
с ответом воркера) и `logs/` (вывод воркеров) не шифруются: защита — права доступа. Каталог и
файлы в нём доступны только пользователю агента (каталоги 0700, файлы 0600; сам `dataDir` при
воркерах с `user` — 0711: его можно пройти, но не прочитать);
не открывайте их другим пользователям, держите `dataDir` на зашифрованном диске или томе, если
узел могут унести или снять с него диск, и храните резервные копии так же, как сам ключ агента.

**Что не попадает в лог агента.** Агент не пишет в свой лог и журнал (`agent.logs`, записи `log`
серверу) значения настроек, ответы воркера на `PUT /config` (ни итог, ни текст отказа — только
код), тела запросов `fetch` и ответов на них, заголовки запросов, `data` событий и запросов
воркеров к серверу, токен регистрации, ключ агента и токены воркеров — только имя воркера,
ключ, версию, размер и код. Вывод воркера (stdout и stderr) агент передаёт в журнал как есть и
не фильтрует: что воркер печатает сам, он и отвечает — не печатайте секреты из настроек и
запросов.

Копируйте каталог целиком при остановленной службе (`systemctl stop agent`, затем
`agent stop-workers`) или снимком тома.
Без копии, если каталог пропал, агент регистрируется заново по токену регистрации (`--token` при
повторной установке или `AGENT_ENROLL_TOKEN` в `/etc/agent/agent.env`) — для сервера это новый
агент с новым id, прежнюю запись можно отозвать. Кроме того, пропадают сообщения из `outbox/`;
настройки воркеров агент получит от сервера снова, а сборки воркеров с сервера ставятся заново
(`agent install --worker` или `worker.update`).

## Обновление

**Новые версии агент замечает сам.** Каталог сборок агента — его релизы на GitHub или свой адрес
`update.releases` с тем же устройством (`<адрес>/latest/download/manifest.json` — последняя версия,
`<адрес>/download/v<версия>/…` — сборки версии). Раз в `update.checkInterval` (6 ч; `0s` — не
проверять) агент читает последнюю версию; новее своей — пишет в журнал и сообщает серверу
(`hello.agent.update`, `status.update`; в SDK — поле `update` агента). Итог проверки хранится в
`dataDir/update-check.json`: `agent status` показывает его без сети, `agent config check` и
`agent upgrade` при устаревшем итоге проверяют сами (`AGENT_NO_UPDATE_CHECK=1` — не проверять в
командах). Сам агент новую версию не ставит:

- `agent upgrade [--check] [--version X] [--force]` на узле — в папке агента программа заменяется на
  месте (прежняя — `agent.prev`), у службы — как по `agent.update`, с откатом, служба
  перезапускается; новую основную версию (`2.x` при `1.x`) — только явно, `--version`;
- `agent.update` без ссылки (`agents.updateAgent(id, { version })` в SDK) — агент сам берёт сборку
  этой версии под свою платформу из каталога сборок, подпись — из его `manifest.json`.

1. **Ключи.** `agent keygen` (или `agent-release keygen` для публикации самого агента) выдаёт пару ключей. Закрытый (`AGENT_SIGNING_KEY`) нужен только при
   подписи сборок — держите его в секретах CI, не на бэкенде. Открытый
   (`AGENT_UPDATE_PUBLIC_KEY`) проверяет подпись. Агенту он вшивается при сборке, если при
   `make release` (или `scripts/go.sh build`) задана переменная `AGENT_UPDATE_PUBLIC_KEY`
   (`-ldflags "-X main.updateKey=<base64>"`). Ключей у агента может быть несколько: вшитый и
   `update.publicKey`, `update.publicKeys` из настроек (`--update-key` при установке); подпись
   принимается, если сходится с любым. Обычно это два ключа: **автора агента** (им подписаны агент и
   netprobe в GitHub Release, он вшит в эти сборки) и **проекта** (им проект подписывает свои
   воркеры). Подпись — над строкой из имени сборки (`agent` или имя воркера), версии, `os`, `arch` и
   sha256 (спецификация, §11): подпись одной сборки к другой не подходит. `manifest.json` пишет
   открытый ключ своей подписи в поле `publicKey` — справочно, агент ему не доверяет.
2. **Сборка.** `AGENT_SIGNING_KEY=… AGENT_UPDATE_PUBLIC_KEY=… make release` кладёт в
   `dist/<VERSION>/` сборки агента linux/darwin × amd64/arm64, стандартный воркер
   **netprobe** (`examples/workers/netprobe`, файлы `netprobe-<VERSION>-<os>-<arch>`, в манифесте —
   как `--worker netprobe=<VERSION>`), подписанный `manifest.json` и `install.sh`
   (`scripts/release.sh`). CI публикации (`.github/workflows/release.yml`) делает то же по тегу
   `v<VERSION>` и публикует всё в GitHub Release, а ещё в образ
   `ghcr.io/epifanovmd/agent-dist:<версия>` (каталог `/dist/<версия>/`). Бэкенд на SDK берёт сборки
   агента прямо из GitHub Release (опция `agentReleases`: сам следит за новыми версиями, обновлять
   бэкенд ради новой версии агента не нужно) или раздаёт свой каталог (опция `releasesDir`) —
   [sdk/docs/releases.md](../sdk/docs/releases.md).
3. **Сборки воркеров.** Сборки воркеров кладутся в тот же каталог, затем
   `scripts/go.sh release --worker NAME=VERSION[,stopTimeout=…][,command=…]` добавляет их в
   `manifest.json` с подписью. Манифест только для воркеров проекта (без сборок агента: агент — из
   GitHub Release) — `agent-release manifest DIR VERSION --worker NAME=VERSION…` над каталогом со
   сборками воркеров; в манифесте `artifacts` пуст. Сборка воркера — один файл `<name>-<version>-<os>-<arch>` (например,
   программа на Go) или архив `<name>-<version>-<os>-<arch>.tar.gz` — для воркера на Python, Node и
   других языках, которому нужно несколько файлов. Агент распаковывает архив в каталог `current`
   (пути наружу, ссылки наружу и особые файлы — отказ) и запускает в нём `command` воркера; путь
   `./…` в `command` — от этого каталога. Без `command` в настройках запускается файл `run` из
   архива. `command=bin/report` у `--worker` записывает в `manifest.json` (поле `command` сборки),
   что запускать в архиве, — установщик вписывает это в настройки. Например, воркер
   `report` на Python:

   ```bash
   # каталог воркера: report_worker.py и всё, что он импортирует
   tar -czf dist/<VERSION>/report-1.0.0-linux-amd64.tar.gz -C workers/report .
   scripts/go.sh release --worker report=1.0.0
   ```

   ```yaml
   # agent.yaml узла
   workers:
     - name: report
       release: true
       command: ["python3", "./report_worker.py"]
   ```

   Для Node в архив кладут собранный код и `node_modules` (`npm ci --omit=dev`), `command` —
   `["node", "./dist/index.js"]`. Интерпретатор (`python3`, `node`) должен быть на узле или в
   архиве. Архив не зависит от платформы — тот же файл кладётся под каждую пару
   `<os>-<arch>`, где воркер нужен.

4. **Обновление узла.** Бэкенд отправляет агенту действие `agent.update` со ссылкой на сборку.
   Ссылка — путь от корня сервера (агент скачивает с сервера, с которым на связи, со своим ключом;
   сервер может ответить перенаправлением `302`, например на GitHub, — на чужой хост ключ агента не
   передаётся) или абсолютная `https://…` на любой хост (без ключа агента); `http://…` — только
   если и сервер `http://`. Агент проверяет подпись и контрольную сумму, сохраняет текущую версию как запасную (`.prev`),
   ставит новую и перезапускается; итог `{version, previous}` отправляет уже новая версия после
   подключения. Агент в контейнере (`update.mode: external`) и с `update.mode: disabled` себя не
   обновляет (`UPDATE_NOT_SUPPORTED`), без ключа проверки — тоже (`UPDATE_NOT_VERIFIED`). Отметка
   о новой версии (`agent.update.json`) и запасная копия лежат рядом с программой. Без ссылки агент берёт сборку
   версии из своего каталога сборок (выше).
5. **Обновление воркеров.** Если в `manifest.json` есть сборки воркеров, бэкенд обновляет их действием
   `worker.update` — с той же проверкой подписи. Агент ставит новую сборку и заменяет воркер; если
   новая сборка не ответила `ok: true` на `GET /health` за `updateHealthyTimeout` (1 минута), агент
   возвращает прежнюю
   (`UPDATE_FAILED`). Обновить можно только воркер с `release: true` в `agent.yaml`; добавить или
   удалить воркер с сервера нельзя.
6. **Откат.** Если новая версия за три запуска так и не подключилась к серверу, агент возвращает
   прежнюю. Под systemd это делает прежняя версия ещё до запуска новой (`agent.prev boot-guard`),
   поэтому откат срабатывает, даже если новая версия падает сразу.
