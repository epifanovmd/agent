# Настройки воркеров

Настройки — значения, которые бэкенд задаёт воркеру на конкретном агенте: по ключам (`main`,
`limits`, …), любой JSON, с версией. Агент хранит их на диске и передаёт воркеру — после
перезапуска воркера и агента и без связи узел работает по последним настройкам. Формат —
[sdk/spec §8](../spec/README.md#8-настройки-воркера), образцы —
[configs.json](../spec/examples/configs.json).

## Задать, прочитать, удалить

```ts
const rec = await agents.setConfig(agentId, "report", "main", {
  target: "https://example.com/report",
  intervalSec: 60,
});
rec.version; // 42 — растёт с каждым setConfig по этому ключу

await agents.getConfig(agentId, "report", "main"); // { agentId, worker, key, version, data, updatedAt, actor? }
await agents.listConfigs(agentId); // все ключи агента
await agents.deleteConfig(agentId, "report", "limits"); // true — был
await agents.by("admin@example.com").setConfig(agentId, "report", "main", { intervalSec: 30 }); // с автором (actor)
```

Имя воркера и ключа — `^[a-z][a-z0-9-]{0,31}$` (иначе `MESSAGE_INVALID`), значение — до 4 МБ JSON
(`BODY_TOO_LARGE`). Агент должен быть зарегистрирован (`AGENT_NOT_FOUND`) и не отозван
(`AGENT_REVOKED`); на связи ли он — неважно. Каждое изменение попадает в событие `audit`
(`config.set`, `config.delete`); с `by(actor)` — с автором.

## Проверка по схеме

Если воркер описал ключ в манифесте со схемой значения
([workers.md](workers.md#манифест-что-воркер-умеет)), `Agents` может проверить значение сам —
до записи в Store и отправки агенту:

```ts
const agents = new Agents({ enrollToken, validateConfigs: true });

await agents.setConfig(agentId, "echo", "settings", { prefix: 5, extra: 1 });
// AgentsError CONFIG_INVALID (400): "echo/settings: prefix: ожидается строка; extra: лишнее поле"
```

- Опция `validateConfigs` по умолчанию выключена: значение проверяет только воркер (отказ
  придёт как `CONFIG_REJECTED`, см. ниже). Агент значение по схеме не проверяет — он смотрит
  только, есть ли ключ в манифесте ([ниже](#как-доходит-до-воркера)).
- Схема берётся из манифеста воркера в последнем `status` агента (или в `hello`). Нет манифеста или у ключа нет
  схемы — значение уходит без проверки.
- В тексте ошибки — до трёх замечаний вида «поле: что не так». Схему, которую нельзя применить
  (например, со ссылкой `$ref` на внешний документ), SDK пропускает и пишет об этом в журнал
  (опция `log`).
- Схема — JSON Schema версии 2020-12 или той, что указана в `$schema` (draft-04, draft-07,
  2019-09). Проверку делает библиотека `@cfworker/json-schema`: она не создаёт код из схемы, а
  схема приходит с узла.

**Версии.** Целое число, по ключу только растёт — в том числе после удаления. Если у агента
уже есть версия новее, чем помнит Store (например, хранилище очистили), следующая версия будет
выше агентской: агент новую не пропустит.

## Как доходит до воркера

- Агент на связи с этим процессом получает `config.put {worker, key, version, data}` сразу.
- Агент без связи — при подключении: `Agents` сравнивает версии из `hello.configs` со своими и
  присылает новее, а ключи, которых у бэкенда нет, удаляет (`config.delete`). Хранилище бэкенда
  — источник правды: пустой Store удалит все настройки на агенте.
- Агент на связи с другим процессом — после `refresh(agentId)` в том процессе
  ([connection.md](connection.md#несколько-процессов-бэкенда)), иначе — при следующем
  подключении.

Агент сохраняет значение и вызывает у воркера `PUT /config/{key}` с телом `{ version, data }`
([workers.md](workers.md#что-воркер-обслуживает)). `2xx` — применено; иначе — отказ с текстом
ответа воркера (`CONFIG_REJECTED`), агент повторит через 25 с и после перезапуска воркера.
Версия, пришедшая во время применения, ждёт его конца; промежуточные пропускаются.

Перед вызовом агент сверяется с воркером:

- воркер не зарегистрирован (`state: invalid`, [workers.md](workers.md#обязательный-минимум)) —
  ошибка `WORKER_INVALID`; агент передаст значение, как только воркер зарегистрируется;
- ключа нет в манифесте воркера (`manifest.configs`) — ошибка `CONFIG_KEY_UNKNOWN`, воркеру ключ
  не передаётся. Агент проверит ключ снова при следующей регистрации воркера — например, после
  обновления на сборку, которая этот ключ объявляет.

## Статус применения

```ts
const list = await agents.configStatus(agentId); // или (agentId, "report") — только его ключи
// [{ agentId, worker, key, version, delivered, applied, state, error?, updatedAt }]
```

| Поле        | Что это                                                    |
| ----------- | ---------------------------------------------------------- |
| `version`   | желаемая версия; `null` — ключ удалён, агент ещё не удалил |
| `delivered` | версия на диске агента                                     |
| `applied`   | последняя версия, которую воркер применил                  |
| `error`     | `{ code, message }` — почему желаемая версия не применена  |

| `state`    | Значит                                                        |
| ---------- | ------------------------------------------------------------- |
| `pending`  | агенту ещё не доставлено (агент без связи или ещё не ответил) |
| `applying` | доставлено, воркер применяет                                  |
| `applied`  | воркер применил желаемую версию                               |
| `failed`   | не применено: причина — код в `error` (ниже)                  |
| `deleting` | удаляется на агенте                                           |

Коды в `error` при `state: failed`:

| Код                  | Значит                                                        |
| -------------------- | ------------------------------------------------------------- |
| `CONFIG_REJECTED`    | воркер отказал; `message` — текст его ответа                  |
| `CONFIG_KEY_UNKNOWN` | ключа нет в манифесте воркера, воркеру он не передавался      |
| `WORKER_INVALID`     | воркер не зарегистрирован: не ответил на обязательные запросы |
| `WORKER_UNAVAILABLE` | воркер не запущен или не отвечает                             |
| `WORKER_UNKNOWN`     | воркера нет в настройках агента                               |
| `TIMEOUT`            | воркер не ответил за 30 с                                     |

Статус собирается из `config.applied` (итог каждой версии) и `status.workers[].configs` (что
у агента на диске и чем кончилось применение). Желаемое значение хранится в Store как запись
настроек, сообщённое агентом — в записи агента (поле `configs`), поэтому `configStatus`
работает в любом процессе. Изменение статуса — событие `config`:

```ts
agents.on("config", (s) => ui.push(s.agentId, s)); // ConfigStatus
```

Отказ — ещё и проблема `configFailed` ([observe.md](observe.md#проблемы)); заканчивается, когда
воркер применит версию.

## Воркер сам читает свои настройки

Воркер может в любой момент спросить агента `GET /config/{key}` на `AGENT_SOCKET` — ответ
`{ version, data }` или `404` ([workers.md](workers.md#что-агент-обслуживает-для-воркера)).
