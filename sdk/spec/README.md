# Формат связи агента, сервера и воркеров

Агент — программа на узле: держит связь с сервером, запускает воркеры и следит за ними, собирает
метрики узла, обновляется сам. Что делают воркеры, агент не знает: он передаёт запросы,
настройки, события и метрики, не разбирая их. Воркер — обычный HTTP-сервис на unix-сокете на
любом языке, без SDK.

```
сервер (бэкенд на SDK) ──WebSocket──► агент ──HTTP по unix-сокету──► воркер
                       ◄─────────────        ◄──────────────────────
```

Менять формат начинают с этого документа и образцов (§14). Внутри версии формата можно только
добавлять: новые необязательные поля и новые типы сообщений.

## 1. Главные правила

- Сообщения — JSON (UTF-8). Незнакомые поля и типы сообщений получатель пропускает.
- Время — миллисекунды Unix.
- Имена воркеров и ключей настроек: `^[a-z][a-z0-9-]{0,31}$`. Тип события: `^[a-z][a-z0-9._-]{0,63}$`.
  Имя агента — непустая строка до 128 символов; `labels` — до 64 меток, ключ — непустая строка до
  256 символов, значение — строка до 256 символов.
- Всё, что агент получил от воркера (ответ, событие, метрики), он передаёт серверу без изменений.
- Ошибка всегда описывается объектом `{ code, message }`; коды — в §15. Пределы и сроки — в §16.

## 2. Регистрация и подключение

**Регистрация** — один раз, токеном регистрации:

```
POST /api/v1/agent-link/enroll
{ token, name, labels?, host: { os, arch, hostname } }
→ 200 { agentId, secret }
```

Ключ агента (`agentId` и `secret`) хранится в `<dataDir>/credentials.json` (0600). Токен после
регистрации не нужен. Ошибки — тело `{ code, message }`: `400 MESSAGE_INVALID`, `401
ENROLL_DENIED` (токен не принят), `413 BODY_TOO_LARGE`, `429 RATE_LIMITED` с `Retry-After`.

**Подключение** — WebSocket:

```
GET /api/v1/agent-link
Upgrade: websocket
Sec-WebSocket-Protocol: agent.v2
Authorization: Agent <agentId>.<secret>
```

Ключ не принят — `401` до открытия WebSocket (агент поступает так же, как при `4401`); нет канала
`agent.v2` — `426` (агент пишет ошибку в лог и повторяет через наибольшую паузу
`server.reconnect`). Одно текстовое сообщение WebSocket — одно сообщение JSON. Обе стороны шлют
ping; нет pong — соединение закрывается (сроки — §16): так обрыв без закрытия (сеть пропала, узел
выключен) замечается за секунды.

| Код закрытия | Причина                                                                   | Что делает агент                                                                                                      |
| ------------ | ------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| `1012`       | сервер перезапускается или сменил ключ агента                             | подключается сразу (случайная задержка до 1 с)                                                                        |
| `4400`       | неверное сообщение, первое сообщение — не `hello` или нет `hello` за 10 с | подключается с растущей паузой, пишет в лог                                                                           |
| `4401`       | ключ отозван                                                              | пробует другой секрет (§10); его нет — регистрируется заново, если есть токен; иначе повторяет через наибольшую паузу |
| `4409`       | этот агент подключился ещё раз — к этому или другому процессу сервера     | 30 с не подключается, потом — с растущей паузой                                                                       |
| `4429`       | сервер перегружен; в `reason` — секунды до повтора                        | подключается не раньше указанного (не позже 10 мин)                                                                   |

Ответ `429` или `503` с `Retry-After` на подключение — то же, что `4429`. Остальное —
переподключение с растущей паузой (по умолчанию 1–60 с, `server.reconnect`). Сам агент закрывает
соединение кодом `1001`: при остановке и когда изменились его имя, метки или список воркеров — тогда
он сразу подключается заново со свежим `hello`.

## 3. Конверт и доставка

```jsonc
{ "type": "event", "id": "…", "re": "…", "seq": 17, "data": {} }
```

`type` — всегда; `id` — до 64 символов; `re` — `id` сообщения, к которому относится это (ответ,
отмена); `data` — содержимое, если оно есть.

| Класс      | Поле  | Как доставляется                                                                                       | Сообщения                                                                                  |
| ---------- | ----- | ------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------ |
| важное     | `id`  | агент хранит на диске (outbox), пока сервер не пришлёт `ack {ids}`; повтор после разрыва и перезапуска | `event`, `config.applied`, `action.result`, `action.done`                                  |
| поток      | `seq` | без связи агент держит последние (по умолчанию 600) в памяти и досылает                                | `status`, `metrics`, `log`                                                                 |
| ответ      | `re`  | только в текущем соединении; разрыв — ответ теряется                                                   | `fetch.head`, `fetch.chunk`, `fetch.end`; от сервера — `request.result`                    |
| запрос     | `id`  | шлётся в текущем соединении, без повтора после разрыва; получатель отвечает сообщением с `re`          | `fetch`, `action` — от сервера; `request` — от агента (§12)                                |
| управление | —     | действует в текущем соединении; после подключения сервер присылает заново (§4)                         | `hello`, `welcome`, `config.put`, `config.delete`, `watch`, `fetch.cancel`, `ack`, `error` |

- **`seq` нумерует агент**: с 1 при каждом запуске (`hello.agent.bootId`), подряд через все
  соединения запуска. `ack {seq}` подтверждает всё до этого номера включительно. Номер не больше
  уже принятого сервер отбрасывает; новый `bootId` — нумерация с начала.
- **Важное** сервер обрабатывает так, чтобы повтор с тем же `id` ничего не задвоил, и
  подтверждает `ack {ids}` — в том числе повтор и устаревшее (например, `config.applied` старой
  версии), которое он пропустил. Не принято — `error` с `re` = `id` и `retryable`: `true` — агент
  повторит через 30 с, `false` — удалит из outbox и запишет в лог.
- Неверное сообщение потока сервер подтверждает по `seq` и отвечает `error {code: MESSAGE_INVALID}`
  без `re`.
- Незнакомый `type` от агента сервер пропускает и отвечает `error {code: UNKNOWN_TYPE,
retryable: false}` с `re` = `id` сообщения; от сервера — агент пишет в лог и пропускает.

## 4. Начало разговора

Агент → `hello` (первое сообщение; до `welcome` ничего другого не шлёт):

```jsonc
{
  "agent": { "version": "1.0.0", "bootId": "8f2c…", "startedAt": 1791380000000 },
  "host": { "os": "linux", "arch": "amd64", "hostname": "node-01", "kernel": "6.8.0" },
  "labels": { "zone": "eu" },
  // воркеры из настроек агента (встроенного sysmetrics здесь нет); version — у воркера из выпуска
  // версия сборки, у остальных — из манифеста; manifest — как в status (§6, §12)
  "workers": [{ "name": "report", "version": "1.4.0", "release": true, "manifest": { "version": "1.4.0" } }],
  "configs": { "report": { "main": 41, "limits": 7 } }, // версии настроек на диске агента
}
```

Обязательны `agent` и `host` (`host.kernel` — версия ядра, если система её сообщила); `labels`,
`workers` и `configs` пустыми не передаются.

Сервер → `welcome` `{ serverTime, metricsIntervalMs, statusIntervalMs }`; нет `welcome` за 15 с — агент
закрывает соединение. После `welcome` обе стороны работают независимо:

- **агент** досылает outbox по порядку, затем поток с первого неподтверждённого `seq`, затем шлёт
  свежий `status`;
- **сервер** присылает `config.put` для ключей, у которых его версия новее, чем в `hello.configs`
  (или ключа нет у агента), `config.delete` — для ключей, которых у сервера нет, и текущий
  `watch`, если он есть.

## 5. Сообщения сервер → агент

| Тип              | data                                                                 | Что делает агент                                  |
| ---------------- | -------------------------------------------------------------------- | ------------------------------------------------- |
| `welcome`        | `{ serverTime, metricsIntervalMs, statusIntervalMs }`                | §4                                                |
| `config.put`     | `{ worker, key, version, data }`                                     | сохраняет и передаёт воркеру (§8)                 |
| `config.delete`  | `{ worker, key }`                                                    | удаляет у себя и у воркера (§8)                   |
| `fetch`          | `{ worker, method, path, headers?, body?, encoding?, timeoutMs? }`   | HTTP-запрос к воркеру (§7)                        |
| `fetch.cancel`   | — (`re` — id запроса)                                                | прерывает запрос                                  |
| `watch`          | `{ metricsIntervalMs?, logLevel?, untilMs }`; `{}` — снять           | частота метрик и уровень лога (§9)                |
| `action`         | `{ name, args? }`                                                    | встроенное действие (§10), итог — `action.result` |
| `request.result` | `{ ok, data?, error? }`, `re` — id запроса агента                    | ответ на запрос воркера (§12)                     |
| `ack`            | `{ ids?, seq? }`                                                     | подтверждение (§3)                                |
| `error`          | `{ code, message, retryable }`, `re` — id сообщения агента, если был | §3                                                |

## 6. Сообщения агент → сервер

| Тип              | data                                                                                                                                    |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| `status`         | `{ workers: [WorkerStatus], outbox }` — раз в `statusIntervalMs` и при изменении, пока есть связь; `outbox` — сколько важных ждут `ack` |
| `metrics`        | `{ collectedAt, host?, workers?: { "<имя>": <ответ GET /metrics> } }` (§9)                                                              |
| `log`            | `{ entries: [LogEntry] }` (§9)                                                                                                          |
| `event`          | `{ worker, type, data?, at }` (§12)                                                                                                     |
| `config.applied` | `{ worker, key, version, ok, result?, error? }` (§8); `result` — тело ответа воркера при `ok: true`                                     |
| `fetch.head`     | `{ status, headers }` (§7)                                                                                                              |
| `fetch.chunk`    | `{ data, encoding: "utf8" \| "base64" }` (§7)                                                                                           |
| `fetch.end`      | `{ error? }` (§7)                                                                                                                       |
| `action.result`  | `{ ok, result?, error? }`, `re` — id действия (§10)                                                                                     |
| `action.done`    | `{ name, worker, ok, result?, error? }`, `re` — id действия: итог отложенной замены воркера (§10)                                       |
| `request`        | `{ worker, type, data?, timeoutMs }` — запрос воркера к серверу (§12); ответ — `request.result`                                         |

```jsonc
// WorkerStatus
{
  "name": "report",
  "state": "running", // starting | running | invalid | backoff | stopped (§12, §13)
  "message": "…", // причина состояния invalid: чем ответ GET /health или GET /manifest не подошёл
  "version": "1.4.0", // у воркера из выпуска — версия сборки, у остальных — из манифеста
  "release": true, // ставится и обновляется из выпуска (§11)
  "builtin": false, // true — встроенный sysmetrics: часть агента, его версия — версия агента
  "restarts": 0, // сколько раз агент перезапускал воркер после выхода процесса (с запуска агента)
  // последний ответ GET /health (§9); нет — ответа ещё нет, процесс не работает или ответ — 404
  "health": { "ok": true, "busy": false, "message": "…", "info": {} },
  "pending": "restart", // restart | update — замена ждёт, пока воркер занят (§13); нет — не ждёт
  // ответ GET /manifest последней проверки (§12); нет — проверки ещё не было или ответ некорректен
  "manifest": { "version": "1.4.0", "configs": [], "routes": [], "events": [] },
  // по каждому сохранённому ключу: последняя версия и итог её применения; нет ok — ещё применяется
  "configs": {
    "main": { "version": 41, "ok": true },
    "limits": { "version": 7, "ok": false, "error": { "code": "CONFIG_REJECTED", "message": "…" } },
  },
}
```

## 7. Запрос к воркеру (`fetch`)

Агент выполняет HTTP-запрос к сокету воркера и отвечает кусками с `re` = `id` запроса:
`fetch.head`, затем `fetch.chunk` (ноль или больше), затем `fetch.end`. Ошибка до ответа воркера —
сразу `fetch.end` без `fetch.head`.

- `headers` — объект «имя → значение» (несколько значений — через `, `); в `fetch.head` имена —
  строчными. Тело запроса — строка `body`; двоичное — `body` в base64 и `encoding: "base64"`.
- Кусок тела ответа — до 64 КБ: `utf8`, если это целый текст UTF-8, иначе `base64`.
- Срок — `timeoutMs` (по умолчанию 30 с, не больше 10 мин); истёк — `fetch.end {error: TIMEOUT}`.
  Отмена — `fetch.end {error: CANCELLED}`.
- Нет `method` или `path` от `/`, неверный base64 — `MESSAGE_INVALID`. `fetch` без `id` и повтор
  с тем же `id`, пока запрос идёт, агент пропускает.
- Воркер неизвестен (в том числе встроенный `sysmetrics`) — `WORKER_UNKNOWN`; не запущен или не
  отвечает — `WORKER_UNAVAILABLE`; не зарегистрирован (`state: invalid`, §12) — `WORKER_INVALID`.
- Служебные пути `/config` и `/config/*`, `/metrics`, `/health`, `/cleanup` сервер не вызывает:
  `PATH_FORBIDDEN`. Больше 64 запросов сразу — `BUSY`. Тело запроса больше 4 МБ — `BODY_TOO_LARGE`
  сразу; тело ответа больше 32 МБ — `BODY_TOO_LARGE` после уже отправленных кусков.
- **Маршруты — только объявленные.** Агент пропускает к воркеру только запросы, которые описаны в
  его манифесте (§12); остальные завершает `fetch.end` с ошибкой, не обращаясь к воркеру:
  - обычный путь — должен подойти под один из `manifest.routes`: `method` совпадает точно, `path`
    — по сегментам (между `/`); `{name}` — один любой непустой сегмент, кроме `.` и `..`;
    параметры после `?` не учитываются. Сравнивается путь с раскрытыми `%XX`. Не подошёл —
    `ROUTE_UNDECLARED`;
  - задачи `POST /jobs`, `GET /jobs/{id}`, `POST /jobs/{id}/cancel` — только у воркера с непустым
    `jobs`, другие пути `/jobs/*` и задачи у воркера без `jobs` — `ROUTE_UNDECLARED`. В
    `POST /jobs` агент читает из тела только `type`: типа нет в `manifest.jobs` — `JOB_UNKNOWN`,
    тело не JSON-объект с `type` — `MESSAGE_INVALID`;
  - `GET /manifest` пропускается всегда; служебные пути выше — `PATH_FORBIDDEN`; пути `/jobs*`
    и служебные пути, объявленные в `routes`, ничего не меняют.

  Проверку можно выключить для одного воркера — `routes: open` в настройках узла (§13): тогда
  агент передаёт воркеру любой путь, кроме служебных, и не проверяет тип задачи.

- Связь оборвалась — агент прерывает запросы этого соединения и ничего не досылает; сервер сам
  завершает их с ошибкой `DISCONNECTED`.

## 8. Настройки воркера

У воркера может быть несколько ключей настроек (`main`, `limits`, …). Значение ключа — любой
JSON. Версию задаёт сервер: целое число, которое по ключу только растёт.

Агент, получив `config.put`:

1. если воркера нет в его настройках (или это встроенный `sysmetrics`) — `config.applied` с
   ошибкой `WORKER_UNKNOWN`, ничего не сохраняет; имя ключа не по правилу (§1), значение больше
   4 МБ или не JSON — пропускает сообщение и пишет в лог; версия не новее сохранённой — пропускает;
2. пишет `<dataDir>/configs/<worker>/<key>.json` (0600) и вызывает у воркера `PUT /config/{key}`
   с телом `{ version, data }`. Воркер не запущен или соединение не удалось —
   `WORKER_UNAVAILABLE`; не зарегистрирован — `WORKER_INVALID`. Перед вызовом агент сверяется с
   манифестом воркера (§12): ключа нет в `manifest.configs` — ошибка `CONFIG_KEY_UNKNOWN`, воркеру
   ключ не передаётся (проверка повторяется при следующей регистрации воркера, например после
   обновления). Значение по `schema` ключа агент не проверяет: это может делать сервер до отправки
   (опция `validateConfigs` в SDK);
3. ответ 2xx — применено; нет ответа за 30 с — `TIMEOUT`; другой ответ — ошибка `CONFIG_REJECTED`
   с текстом из ответа воркера. Тело ответа 2xx — JSON до 64 КБ — агент передаёт как есть в
   `config.applied.result`: подробный итог, например что из настроек применено. Пустое тело —
   без `result`; тело больше 64 КБ или не JSON — тоже без `result`, агент пишет предупреждение в
   лог (без содержимого);
4. итог отправляет серверу `config.applied` — по одному на каждую пару «версия + итог»: тот же итог
   той же версии при повторе не отправляется (итог — `ok` и код ошибки; другой `result` при
   повторе нового `config.applied` не даёт);
5. при ошибке повторяет через 25 с и после каждой регистрации воркера, пока не придёт новая версия
   (`CONFIG_KEY_UNKNOWN` — только после регистрации);
6. после регистрации воркера (и после перезапуска агента) передаёт ему все сохранённые ключи по
   одному, по алфавиту ключей — узел работает по последним настройкам и без связи.

Новая версия, пришедшая во время применения, ждёт его окончания; промежуточные пропускаются.

`config.delete`: агент удаляет файл ключа и, если воркер запущен, вызывает у него
`DELETE /config/{key}` (404 тоже успех; ошибку пишет в лог, не повторяет). Ключ пропадает из
`status.workers[].configs`; `config.applied` не отправляется. Следующий `config.put` этого ключа принимается с любой версией.

## 9. Метрики, лог и самочувствие

**Метрики узла** собирает встроенный воркер `sysmetrics`; его ответ `GET /metrics` агент кладёт в
`metrics.host` (а не в `metrics.workers`). Какие группы собирать — `telemetry.metrics` в
настройках агента. Все поля необязательные: нет группы или значения на платформе — нет поля.
Скорости — между двумя сборами, в первой точке их нет.

- `cpu` — `cpuPercent`, `cpuCores: [%]`; `load` — `load1`, `load5`, `load15`;
- `memory` — `memUsedBytes`, `memTotalBytes`, `memAvailableBytes`; `swap` — `swapUsedBytes`, `swapTotalBytes`;
- `disk` — `diskUsedBytes`, `diskTotalBytes` (корень), `disks: [{mount, usedBytes, totalBytes, inodesUsed?, inodesTotal?}]`;
- `diskio` — `diskReadBps`, `diskWriteBps`, `diskReadIops`, `diskWriteIops`;
- `network` — `netRxBps`, `netTxBps`, `netErrors`, `netDrops`; `interfaces` — `interfaces: [{name, rxBps, txBps, errors?, drops?}]`;
- `conntrack` — `conntrack`, `conntrackMax`; `sockets` — `tcp: {established, timeWait, closeWait, listen}`;
- `processes` — `processes`, `threads`; `fds` — `fdsOpen`, `fdsMax`; `uptime` — `uptimeSec`;
- `temperatures` — `temperatures: {maxC, sensors: [{name, c}]}`;
- `gpu` — `gpus: [{index, name, utilPercent?, memUsedBytes?, memTotalBytes?, temperatureC?}]`.

**Метрики воркера.** Раз в `metricsIntervalMs` агент вызывает `GET /metrics` каждого
зарегистрированного воркера и кладёт ответ (любой JSON) в `metrics.workers["<имя>"]`. Нет ответа,
не-2xx, не JSON или больше 1 МБ — воркера в этой точке нет; не ответил никто — точки нет. Метрики
собираются и без связи (§3).

**Лог.** `LogEntry` — `{ at, level, source, msg, attrs? }`: `level` — `debug | info | warn | error`,
`source` — `agent` или имя воркера, `attrs` — объект. Агент шлёт пачки до 500 записей не чаще раза
в секунду, с уровня `log.forward` из своих настроек (`off | error | warn | info | debug`, по
умолчанию `warn`) или `watch.logLevel`, если он подробнее. Ждут отправки не больше 1000 записей;
лишние пропускаются, и в пачку добавляется запись `warn` о том, сколько пропущено. Вывод воркера:
stdout — `info`, stderr — `warn` (§12).

**`watch`** — просьба на время присылать чаще и подробнее (например, пока на узел смотрят в
интерфейсе). Зрителей может быть много — сервер сводит их в одно сообщение: `metricsIntervalMs` —
наименьший, `logLevel` — самый подробный, `untilMs` — самый поздний срок. Сводка изменилась
(зритель пришёл, ушёл, истёк) — сервер присылает новый `watch` целиком; зрителей нет — `{}`.
Каждый `watch` заменяет прежний. Агент сам снимает `watch` в `untilMs` (уже прошедший `untilMs` —
то же, что `{}`); незнакомый `logLevel` пропускает. Частота метрик — из `watch`, но не чаще 1 с и
не реже, чем в `welcome`.

**Самочувствие.** Раз в 5 с агент вызывает `GET /health` → `{ ok, busy?, message?, info? }`;
не-2xx или неверное тело — `ok: false`, 404 — `health` нет. Ответ попадает в
`status.workers[].health`, изменение `ok` или `busy` — внеочередной `status`. Нет ответа три раза
подряд — воркер считается зависшим и перезапускается (по умолчанию — через 15–20 с после зависания).
Выход процесса воркера агент видит сразу: `state` меняется, внеочередной `status` уходит в
пределах 0,2 с. `info` — объект со сведениями для сервера
(версии, занятые порты и т. п.); не объект — сервер его пропускает, остальной `status` принимается. `busy: true` — воркер занят долгой работой: плановая замена ждёт
её окончания (§13). Занятый воркер всё равно обязан отвечать на `GET /health`: `busy` не защищает
от перезапуска зависшего. Частоту, срок и число пропусков задают настройки воркера
(`lifecycle.health`, §13).

## 10. Встроенные действия

`action` выполняется один раз: повтор с тем же `id`, пока действие идёт, агент пропускает (`action`
без `id` — тоже). Итог — `action.result` (важное) с `re` = `id` действия; у отложенной замены
воркера — ещё `action.done` (ниже).

| `name`            | args                                                | Итог `result`                                                                                          |
| ----------------- | --------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| `worker.restart`  | `{ name, force? }`                                  | — ; остановить и запустить воркер заново; итог — после запуска; воркер занят — `{ deferred, pending }` |
| `worker.update`   | `{ name, version, url, sha256, signature, force? }` | `{ version, previous }`; обновить воркер из выпуска (§11); воркер занят — `{ deferred, pending }`      |
| `agent.update`    | `{ version, url, sha256, signature }`               | `{ version, previous }` — после запуска новой версии (§11); версия та же — сразу                       |
| `agent.rotateKey` | —                                                   | `{ secretHash }` — sha256 (hex) нового секрета                                                         |
| `agent.logs`      | `{ worker?, lines? }`                               | `{ entries: [LogEntry] }` — последние записи журнала агента или воркера (старые отбрасываются до 4 МБ) |

`worker` в `agent.logs` нет — журнал агента. `url` в `agent.update` и `worker.update` — от корня
(`/api/…`): агент дополняет его адресом сервера, с которым сейчас связь, и скачивает со своим
ключом; или абсолютная ссылка `https://…` на любой хост (например, файл выпуска на GitHub): ключ
агента туда не отправляется. `http://…` принимается, только если и сервер — `http://` (стенд,
локальная сеть); иначе — `UPDATE_FAILED`. Перенаправления (`302`) агент проходит; на другой хост
ключ агента не передаётся.

**Замена занятого воркера.** `worker.restart` и `worker.update` — плановая замена: пока воркер
отвечает `busy: true`, агент её откладывает (§13), в `status.workers[].pending` — `restart` или
`update`. Воркер свободен — замена идёт сразу, `action.result` — её итог, как в таблице. Воркер
занят — агент сразу отвечает `action.result` `{ ok: true, result: { deferred: true, pending:
"restart" | "update" } }` и ждёт окончания работы; фактический итог замены — отдельное важное
сообщение `action.done` с `re` = `id` действия:

```jsonc
{ "name": "worker.restart", "worker": "echo", "ok": true } // result — как у action.result без отсрочки
{ "name": "worker.update", "worker": "report", "ok": false, "error": { "code": "UPDATE_FAILED", "message": "…" } }
```

Замена может ждать часы (`busy.timeout`); `action.done` приходит, когда она закончилась, — в том
числе после переподключения агента к другому процессу сервера. `force: true` — заменить сразу, не
дожидаясь окончания работы (без отсрочки). Агент перезапустился, пока замена ждала, —
`action.done` не будет.

**Смена ключа.** Агент создаёт новый секрет, хранит его как ожидающий и отдаёт только хеш. Сервер
запоминает хеш и закрывает соединение кодом `1012`. Агент подключается с новым секретом;
`401` — возвращается к старому.

## 11. Выпуск и обновление

Выпуск — каталог со сборками агента и воркеров и `manifest.json` с подписью каждой сборки
(`GET /api/v1/agent-link/releases/manifest.json`, сборки — `GET /api/v1/agent-link/releases/<file>`):
`{ version, publicKey?, artifacts: [{ os, arch, file, sha256, signature }], workers?: [{ name,
version, os, arch, file, sha256, signature, stopTimeout?, command? }] }`. `stopTimeout` и `command`
(что запускать в сборке-архиве) берёт установщик для записи воркера в `agent.yaml`. `file` — имя
файла в каталоге выпуска или абсолютная ссылка `https://…` (`http://…` — только если и каталог
выпуска `http://`). `publicKey` — открытый ключ, которым подписан выпуск (base64; справочно: агент
проверяет подписи только своими ключами). `artifacts` может быть пустым — выпуск только воркеров
(воркеры проекта).

Подпись — Ed25519 (base64) над строкой `agent-release/1\n<имя>\n<версия>\n<os>\n<arch>\n<sha256>`
(имя — `agent` или имя воркера, sha256 — hex строчными). В `manifest.json` и аргументах команд
регистр букв sha256 не важен: агент приводит его к строчным. Агент собирает строку сам, поэтому подпись
не подходит к другой сборке. Ключей проверки может быть несколько: вшитый в агента при сборке и
заданные в настройках (`update.publicKey`, `update.publicKeys`); подпись принимается, если сходится
с любым из них (например, автор агента подписывает агента и его воркеры, проект — свои воркеры).
Нет ни одного ключа — `UPDATE_NOT_VERIFIED`. Подпись или sha256 не сходятся —
`UPDATE_FAILED`. Обновления выключены (`update.mode: disabled`) — `UPDATE_NOT_SUPPORTED`.

- **Агент:** проверить подпись, скачать и сверить sha256 (файл уже тот же — не скачивать),
  сохранить текущий файл как `.prev`, заменить, перезапуститься. Новая версия не получила `welcome`
  за три запуска — вернуть `.prev`, итог — `UPDATE_FAILED`. Агент в контейнере
  (`update.mode: external`) себя не обновляет — `UPDATE_NOT_SUPPORTED`.
- **Воркер из выпуска** (`release: true`): сборка — файл или архив `.tar.gz` (если `url`
  оканчивается на `.tar.gz`; распаковывается в каталог) в `<dataDir>/workers/<имя>/current`.
  Обновление — замена воркера (§13) с возвратом прежней сборки, если новая не запустилась или не
  ответила `ok: true` на `GET /health` за минуту (`UPDATE_FAILED`). Воркер не из выпуска —
  `WORKER_NOT_RELEASED`; уже обновляется — `BUSY`.

Добавить или удалить воркер сервер не может: это решают настройки узла.

## 12. Воркер

Агент запускает воркер с переменными окружения: `AGENT_WORKER` — имя воркера;
`AGENT_WORKER_SOCKET` — путь unix-сокета, на котором воркер слушает HTTP; `AGENT_SOCKET` — путь
unix-сокета агента; `AGENT_WORKER_TOKEN` — токен для запросов к агенту (`Authorization: Bearer`);
`AGENT_VERSION` — версия агента на момент запуска воркера (воркер переживает обновление агента,
§13; текущая версия — `GET /context`).

**Что воркер обслуживает.** `GET /health` и `GET /manifest` — обязательный минимум, остальное
необязательно (404 — не поддерживается):

| Запрос                   | Ответ                                                                                                     |
| ------------------------ | --------------------------------------------------------------------------------------------------------- |
| `GET /health`            | обязательно: `{ ok, busy?, message?, info? }` (§9)                                                        |
| `GET /manifest`          | обязательно: манифест — что воркер умеет (ниже), минимум `{ version }`                                    |
| `PUT /config/{key}`      | тело `{ version, data }`; 2xx — применено (тело — JSON-итог или пусто, §8), иначе `{ message }` или текст |
| `DELETE /config/{key}`   | 2xx (404 — тоже успех)                                                                                    |
| `GET /metrics`           | 2xx и любой JSON до 1 МБ                                                                                  |
| `POST /cleanup`          | убрать всё, что воркер создал на узле; 2xx — готово, 404 — убирать нечего                                 |
| `POST /jobs` и `/jobs/*` | задачи воркера (ниже); обязательны, если манифест объявляет `jobs`                                        |
| остальные пути           | маршруты воркера для `fetch` — только из `manifest.routes` (§7)                                           |

**Манифест** — самоописание воркера: по нему сервер и агент узнают, какие ключи настроек,
маршруты, события и задачи воркер поддерживает. Обязательно только `version`:

```jsonc
{
  "version": "1.4.0",
  "description": "Отправка отчётов",
  // Все schema — JSON Schema (по умолчанию 2020-12; другую версию задаёт $schema).
  // schema — значения ключа
  "configs": [{ "key": "main", "description": "Куда и как часто", "schema": { "type": "object" } }],
  // {name} в path — один любой сегмент пути; request — тела запроса, response — тела ответа 2xx
  "routes": [
    {
      "method": "POST",
      "path": "/reports/{id}/send",
      "description": "Отправить отчёт",
      "request": { "type": "object" },
      "response": { "type": "object" },
    },
  ],
  // schema — поля data события
  "events": [{ "type": "report.sent", "description": "Отчёт отправлен", "schema": { "type": "object" } }],
  // типы задач (ниже); schema — поля data
  "jobs": [{ "type": "report.build", "description": "Собрать отчёт", "schema": { "type": "object" } }],
  // запросы воркера к серверу (ниже); schema — поля data запроса, response — data ответа
  "requests": [{ "type": "report.recipients", "description": "Кому слать", "schema": { "type": "object" } }],
}
```

- Манифест хранится в памяти до следующей проверки регистрации и попадает в
  `hello.workers[].manifest` и `status.workers[].manifest`; изменился (например, новая сборка) —
  внеочередной `status`. Незнакомые поля манифеста агент не передаёт.
- `version` манифеста — версия воркера в `hello` и `status`. У воркера из выпуска там версия
  сборки (§11); манифест передаётся как есть, даже если его `version` другая.
- Агент сверяется с манифестом: событие, которого нет в `events`, отклоняет
  (`400 EVENT_UNDECLARED`); ключ настроек, которого нет в `configs`, воркеру не передаёт
  (`CONFIG_KEY_UNKNOWN`, §8); `fetch` пропускает только по `routes` и `jobs` (§7); запрос к
  серверу, которого нет в `requests`, отклоняет (`400 REQUEST_UNDECLARED`). События задач
  `job.progress`, `job.done`, `job.failed`, `job.cancelled` в `events` не объявляются: агент
  принимает их, только если `jobs` непуст; другие типы `job.*` зарезервированы и отклоняются
  (`EVENT_UNDECLARED`), в `events` их объявлять нельзя.
- Схемы (`schema`, `request`, `response`) агент не проверяет: он сверяет только имена, типы и
  пути. Значения может проверять сервер — опции SDK `validateConfigs` (настройки), `validateJobs`
  (`data` задачи), `validateRequests` (тело `fetch` по `routes[].request` и `data` запроса
  воркера по `requests[].schema`), `validateEvents` (`data` события по `events[].schema`).
  `routes[].response` и `requests[].response` — описание для людей и сервера, их никто не
  проверяет.

**Задачи** (`/jobs`) — общий вид работы, которую сервер поручает воркеру: «сделай и сообщи итог».
Необязательны; воркер, объявивший `jobs` в манифесте, обязан обслуживать маршруты ниже. Сервер
вызывает их обычным `fetch` (§7); агент пропускает их только у воркера с `jobs` и сверяет `type`
в `POST /jobs` с манифестом, остальное тело передаёт как есть.

| Запрос                   | Ответ                                                                                                        |
| ------------------------ | ------------------------------------------------------------------------------------------------------------ |
| `POST /jobs`             | тело `{ type, jobId, data?, files? }`; `200 { result? }` — быстрая задача, итог сразу; `202 { id }` — долгая |
| `GET /jobs/{id}`         | `{ id, state, progress?, result?, error? }`; нет задачи — `404 { message }`                                  |
| `POST /jobs/{id}/cancel` | прервать долгую задачу → `{ id, state }`; нет задачи — `404 { message }`                                     |

- `type` — тип из `manifest.jobs` (по правилу типа события, §1); `jobId` — id, который задаёт
  сервер (до 64 символов): повтор `POST /jobs` с тем же `jobId` не должен начинать вторую задачу —
  воркер отвечает тем же `id`. `data` — любой JSON (схема — `jobs[].schema`).
- `files` — `{ inputs?: { "<имя>": "<url>" }, outputs?: { "<имя>": "<url>" } }`: файлы по ссылкам
  (например, подписанные ссылки хранилища). Воркер сам скачивает входные (`GET`) и загружает
  выходные (`PUT`); через агента файлы не идут.
- Отказ — `4xx { message }` (неизвестный `type`, неверные `data`, воркер занят и т. п.).
- `state` — `running | done | failed | cancelled`; `progress` — число от 0 до 1; `error` —
  `{ code, message }`.
- Ход и итог долгой задачи воркер сообщает событиями (`POST /events`, важные сообщения §3):
  `job.progress { jobId, id, progress, message? }`, `job.done { jobId, id, result? }`,
  `job.failed { jobId, id, error: { code, message } }`, `job.cancelled { jobId, id }`. Ровно одно
  из трёх последних завершает задачу.
- Пока долгая задача идёт, `GET /health` отвечает `busy: true` (§9, §13). Воркер, запущенный
  заново, продолжает незаконченные задачи или завершает их `job.failed`, если продолжить нельзя.

**Регистрация воркера.** После каждого запуска воркера (и подхвата, §13) — когда сокет начал отвечать —
агент запрашивает `GET /health` и `GET /manifest` (срок — `lifecycle.probeTimeout`, 2 с).

- Оба ответа корректны — воркер зарегистрирован: `state: running`, агент передаёт ему настройки
  (§8), опрашивает метрики и пропускает к нему `fetch`. Корректный `GET /health` — 2xx и JSON с
  булевым `ok` (`ok: false` — тоже корректный ответ: это самочувствие, а не регистрация);
  корректный `GET /manifest` — 2xx и манифест в пределах §16 с непустым `version`.
- Иначе — `state: invalid`, причина — в `status.workers[].message`. Процесс работает дальше, но
  настроек и `fetch` не получает (`WORKER_INVALID`); агент пишет предупреждение в лог и
  повторяет проверку с растущей паузой (`lifecycle.backoff`). Ответы стали корректными — воркер
  зарегистрирован и получает настройки. Зависание (нет ответа на `GET /health` `failures` раз
  подряд, §9) ведёт к перезапуску и в этом состоянии.
- Событие, присланное до окончания первой проверки, ждёт её итога (не дольше 10 с).

**Что даёт агент** на `AGENT_SOCKET` (без токена или с чужим — `401 UNAUTHORIZED`; другой путь —
`404 NOT_FOUND`; ошибки — `{ code, message }`):

| Запрос              | Что делает                                                                                                                                                                                                                                                                                                  |
| ------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /events`      | `{ type, data? }` → `202` после записи в outbox; агент добавляет `worker` и `at`; не JSON или `type` не по правилу (§1) — `400 MESSAGE_INVALID`; `data` больше 64 КБ — `413 BODY_TOO_LARGE`; `type` нет в `manifest.events` (`job.*` — см. выше) — `400 EVENT_UNDECLARED`; outbox полон — `503 OUTBOX_FULL` |
| `GET /config/{key}` | `{ version, data }` — сохранённые настройки этого воркера; нет ключа — `404 NOT_FOUND`                                                                                                                                                                                                                      |
| `GET /context`      | `{ agent: { id, name, version, labels? }, online }` — `id` пустой, пока агент не зарегистрирован; `online`: есть ли связь с сервером                                                                                                                                                                        |
| `POST /requests`    | `{ type, data?, timeoutMs? }` — запрос к серверу (ниже) → `200 { data? }` — ответ сервера                                                                                                                                                                                                                   |

**Запросы к серверу** (`POST /requests`) — воркеру нужно что-то от бэкенда сейчас (данные,
решение) и он ждёт ответа. Тип запроса объявляется в `manifest.requests`.

- `type` — по правилу типа события (§1), `data` — любой JSON до 1 МБ, `timeoutMs` — срок ответа
  (по умолчанию 30 с, не больше 5 мин).
- Не JSON или `type` не по правилу — `400 MESSAGE_INVALID`; тело больше 1 МБ —
  `413 BODY_TOO_LARGE`; типа нет в `manifest.requests` — `400 REQUEST_UNDECLARED` (запрос сразу
  после запуска ждёт итога регистрации, как событие); нет связи с сервером — сразу
  `503 AGENT_OFFLINE`; больше 64 запросов сразу — `503 BUSY`.
- Иначе агент шлёт серверу `request { worker, type, data?, timeoutMs }` с новым `id` и ждёт
  `request.result` с `re` = этот `id`: `{ ok: true, data? }` → воркеру `200 { data? }`;
  `{ ok: false, error }` → `422 { code, message }` — ошибка сервера как есть. Нет ответа за
  `timeoutMs` — `504 TIMEOUT`; связь оборвалась до ответа — `503 DISCONNECTED`.
- Запрос — не важное сообщение: агент не хранит его в outbox и не повторяет. Повторить после
  `AGENT_OFFLINE`, `DISCONNECTED` или `TIMEOUT` может сам воркер. Воркер закрыл соединение —
  агент перестаёт ждать; ответ, пришедший позже, пропускается.

stdout и stderr воркера — файлы `<dataDir>/logs/<имя>.log` и `<имя>.err.log`, а не каналы агента:
воркер переживает перезапуск агента. Агент читает их, передаёт в лог (§9) и отдаёт по
`agent.logs`; файл больше `logs.maxSize` агент копирует в `<файл>.1` (прежние — `.2`, … до
`logs.maxFiles`) и очищает.

## 13. Жизнь воркера

Настройки воркера в `agent.yaml` (у `lifecycle` и `logs` показаны значения по умолчанию):

```yaml
workers:
  - name: report
    command: ["/usr/local/bin/report"] # у воркера из выпуска — необязательно
    release: true
    user: root # по умолчанию — пользователь агента
    env: { LOG_LEVEL: info }
    lifecycle:
      onAgentRestart: keep # keep — работает дальше, новый агент его подхватит; restart — остановить
      onAgentStop: keep # keep | stop — при остановке агента
      restart: on-failure # always | on-failure | never — после выхода процесса
      backoff: { min: 1s, max: 30s } # пауза перед перезапуском после падения
      maxRestarts: 0 # падений подряд не больше (0 — без предела); дальше — state: stopped
      startTimeout: 60s # сокет должен начать отвечать
      stopTimeout: 30s # ждать выхода после SIGTERM, потом SIGKILL
      keepChildren: false # true — дочерние процессы переживают остановку воркера
      busy: { wait: true, timeout: 24h } # плановая замена ждёт, пока GET /health отвечает busy: true
      health: { interval: 5s, timeout: 2s, failures: 3 } # interval: 0s — не проверять; failures: 0 — не перезапускать
      probeTimeout: 2s # срок GET /manifest, GET /metrics и проверки GET /health при регистрации
      configRetry: 25s # повтор неприменённых настроек
      updateHealthyTimeout: 1m # новая сборка должна ответить ok: true
    logs: { maxSize: 10MB, maxFiles: 1 } # файлы вывода воркера (§12)
    routes: strict # strict — fetch только по манифесту (§7); open — любой путь, кроме служебных
```

Изменение `lifecycle`, `logs` и `routes` (перечитывание настроек по `SIGHUP`) применяется без
перезапуска воркера; изменение остального — плановая замена воркера.

- **Запуск:** агент создаёт каталог сокета, запускает процесс в своём сеансе (`setsid`) с выводом в
  файлы (§12) и ждёт, пока сокет начнёт отвечать (`startTimeout`), затем регистрирует воркер
  (`GET /health` и `GET /manifest`, §12) и передаёт ему сохранённые настройки. О каждом запущенном
  процессе агент пишет файл `<dataDir>/processes/<имя>.json`: pid, время запуска процесса по
  данным системы, сокет, токен, версию сборки и отпечаток настроек.
- **Остановка воркера, его перезапуск и обновление** — `SIGTERM`. Воркер завершается, **не
  убирая** то, что создал на узле: созданное продолжает работать. Не вышел за `stopTimeout` —
  `SIGKILL`. Сигналы получает вся группа процессов воркера, с `keepChildren: true` — только сам
  воркер; без `keepChildren` после выхода воркера его дочерние процессы завершаются.
- **Замена** (перезапуск, обновление) — сначала уходит прежний процесс, потом запускается новый.
  Копия воркера всегда одна.
- **Плановая замена и занятый воркер.** Перед заменой по `worker.restart`, `worker.update` и по
  изменению настроек воркера агент спрашивает `GET /health`. `busy: true` (и `busy.wait: true`) —
  замена ждёт: агент спрашивает раз в секунду, в `status.workers[].pending` — `restart` или
  `update`; на `worker.restart` и `worker.update` агент сразу отвечает `action.result` с
  `deferred: true`, а итог замены присылает `action.done` (§10). Работа закончилась, воркер не
  отвечает или прошло `busy.timeout` — замена идёт. `force: true` в действии — сразу. Зависший воркер (нет ответа на `GET /health` `failures` раз
  подряд) перезапускается, даже если последний ответ был `busy: true`. Пока замена ждала, воркер
  перезапустился сам (упал, завис) — `worker.restart` считается выполненным.
- **Выход процесса** — по `restart`: `always` — перезапуск всегда, `on-failure` — если код выхода
  не 0, процесс убит сигналом или завис (у подхваченного процесса код выхода неизвестен — это
  тоже сбой), `never` — нет. Перезапуск — с растущей паузой (`backoff`), `state: backoff`;
  без перезапуска — `state: stopped` до `worker.restart` или изменения настроек воркера.
- **Перезапуск и остановка агента.** Перезапуск (`onAgentRestart`) — агент выходит сам, чтобы
  менеджер службы запустил его снова: после `agent.update` и по команде `agent restart` (сигнал
  `SIGUSR1`). Остановка (`onAgentStop`) — `SIGTERM` и `SIGINT`: `systemctl stop`, `docker stop`,
  Ctrl+C. `systemctl restart` шлёт тот же `SIGTERM`, что и `systemctl stop`, — агент их не
  различает, поэтому для него это остановка; оба умолчания — `keep`, и долгая работа не
  прерывается ни тем, ни другим: воркер работает дальше, а агент после запуска его подхватывает.
  `stop` (`restart`) — воркер останавливается вместе с агентом, следующий агент запускает его
  заново. Служба агента по умолчанию ставится с `KillMode=process`: systemd останавливает только
  агента. В контейнере (`update.mode: external`) и у встроенного `sysmetrics` воркеры всегда
  останавливаются вместе с агентом: контейнер не переживает свой первый процесс.
- **Подхват.** Запускаясь, агент читает файлы `<dataDir>/processes`. Процесс жив, это тот же
  процесс (pid и время запуска совпадают — повторно выданный системой pid не подходит) и его
  сокет отвечает — агент продолжает следить за ним, как за своим: `GET /health`, метрики,
  запросы, вывод из файлов с места, где остановился прежний агент. Настройки подхваченному
  воркеру передаются заново, только если их последняя версия не применена. Отпечаток настроек
  или версия сборки не совпадает — плановая замена. Процесса нет или он чужой — обычный запуск.
  Процесс воркера, которого больше нет в настройках, агент останавливает.
- **Удаление воркера из настроек** — воркер останавливается сразу.
- **Удаление агента** (`agent uninstall`): агент подхватывает работающие воркеры (остальные
  запускает), вызывает `POST /cleanup` у каждого (срок — `stopTimeout`), останавливает их и
  удаляет себя. Сервер уборку запустить не может. `agent stop-workers` — только остановить
  воркеры, оставшиеся после остановки агента.

## 14. Образцы

Образцы всех сообщений — в [`examples/`](examples), по темам: `connection.json`, `configs.json`,
`fetch.json`, `observe.json`, `actions.json`, `events.json`, `requests.json` — сообщения
WebSocket; `worker.json` — HTTP-запросы между агентом и воркером. Каждый файл — объект «имя образца → образец»; имена
уникальны во всём каталоге. Один тип в нескольких образцах — `тип@отправитель` или `тип.суффикс`.

- сообщение WebSocket — `{ from, to, message }`, `message` — конверт целиком (§3);
- HTTP — `{ from, to, request: { method, path, headers?, body? }, response: { status, headers?, body? } }`;
  тело — JSON (строка — текст).

`from` и `to` — `agent`, `server` или `worker`. Типы сообщений агента и серверный SDK проверяются
на всех образцах (тесты `internal/message` и `sdk/node/test`).

## 15. Коды ошибок

- **`error`:** `MESSAGE_INVALID` — сообщение неверно; `UNKNOWN_TYPE` — незнакомый тип; `INTERNAL`
  — сервер не смог обработать важное сообщение (`retryable: true`).
- **Регистрация:** `MESSAGE_INVALID`, `BODY_TOO_LARGE`, `ENROLL_DENIED` — токен не принят,
  `RATE_LIMITED` — много попыток, ждать `Retry-After`.
- **Сокет агента:** `MESSAGE_INVALID`, `BODY_TOO_LARGE`, `UNAUTHORIZED` — нет токена воркера или он
  чужой, `NOT_FOUND` — нет ключа или пути, `OUTBOX_FULL` — outbox полон (503), `INTERNAL` — событие
  не записано в outbox по другой причине (500), `EVENT_UNDECLARED` — типа события нет в манифесте
  воркера или событие задачи (`job.*`) у воркера без `jobs` (§12). Запросы к серверу:
  `REQUEST_UNDECLARED` — типа нет в `manifest.requests`, `AGENT_OFFLINE` — нет связи с сервером
  (503), `BUSY` — много запросов сразу (503), `TIMEOUT` — сервер не ответил за срок (504),
  `DISCONNECTED` — связь оборвалась до ответа (503); отказ сервера (422) — с его кодом, кроме
  `TIMEOUT` (504) и `DISCONNECTED` (503) от сервера.
- **`request.result`** (ставит сервер, SDK): `REQUEST_UNHANDLED` — на сервере нет обработчика
  запросов, `REQUEST_INVALID` — `data` не по `requests[].schema`, `REQUEST_FAILED` — обработчик
  упал без своего кода, `BODY_TOO_LARGE` — ответ больше 4 МБ, `TIMEOUT` / `DISCONNECTED` — срок
  истёк или связь оборвалась, пока работал обработчик (его итог не передаётся); свой код обработчика —
  как есть.
- **`fetch.end`:** `MESSAGE_INVALID` — неверный запрос, `WORKER_UNKNOWN` — воркера нет в
  настройках агента, `WORKER_UNAVAILABLE` — не запущен или не отвечает, `WORKER_INVALID` — не
  зарегистрирован (§12), `TIMEOUT`, `CANCELLED`, `PATH_FORBIDDEN` — служебный путь,
  `ROUTE_UNDECLARED` — маршрута нет в манифесте воркера (§7), `JOB_UNKNOWN` — типа задачи нет в
  `manifest.jobs`, `BODY_TOO_LARGE`, `BUSY` — много запросов сразу. `DISCONNECTED` — связь
  оборвалась до ответа (ставит сам сервер).
- **`config.applied`:** `WORKER_UNKNOWN`, `WORKER_UNAVAILABLE`, `WORKER_INVALID`, `TIMEOUT`,
  `CONFIG_KEY_UNKNOWN` — ключа нет в `manifest.configs` (§8), `CONFIG_REJECTED` — воркер ответил
  не 2xx (`message` — его текст).
- **`action.result` и `action.done`:** `MESSAGE_INVALID` — неверные `args`, `ACTION_UNKNOWN` — незнакомое
  действие, `WORKER_UNKNOWN`, `BUSY` — воркер уже обновляется, `WORKER_NOT_RELEASED` — воркер не
  из выпуска, `UPDATE_NOT_VERIFIED` — нет ключа проверки подписи, `UPDATE_NOT_SUPPORTED` — агент в
  контейнере или обновления выключены, `UPDATE_FAILED` — загрузка, проверка или запуск не удались
  (прежняя сборка возвращена), `ACTION_FAILED` — другая ошибка (например, воркер не запустился
  после `worker.restart`), причина в `message`.

## 16. Пределы и сроки

- **Размеры:** сообщение WebSocket — до 8 МБ; тело регистрации — 64 КБ; значение настройки —
  4 МБ; `config.applied.result` (тело ответа 2xx на `PUT /config`) — 64 КБ; `data` события —
  64 КБ; ответ `GET /metrics` — 1 МБ, `GET /health` и `GET /manifest` — 64 КБ; тело `fetch` —
  запрос 4 МБ, ответ 32 МБ, кусок 64 КБ; `action.result.result` — 4 МБ;
  запрос воркера к серверу — тело `POST /requests` 1 МБ, `data` ответа сервера 4 МБ; outbox — по умолчанию
  10 000 сообщений (`outbox.maxMessages`; полон — события воркеров отклоняются, итоги настроек и
  действий записываются всегда); поток без связи — по умолчанию последние 600
  (`server.streamBuffer`).
- **Сроки агента к воркеру** (по умолчанию; меняются в `lifecycle` воркера, §13): `GET /metrics`,
  `GET /health` и `GET /manifest` — 2 с; запуск (сокет отвечает) — 60 с; новая сборка здорова —
  1 мин. Постоянные: `PUT` и `DELETE /config` — 30 с; `fetch` — `timeoutMs`, по умолчанию 30 с, не
  больше 10 мин; запрос воркера к серверу — `timeoutMs`, по умолчанию 30 с, не больше 5 мин.
- **Частоты** (по умолчанию, `lifecycle`): `GET /health` — раз в 5 с, три пропуска — перезапуск;
  повтор неприменённых настроек — 25 с. Постоянные: метрики по `watch` — не чаще 1 с; `log` — пачка
  до 500 записей не чаще раза в секунду; переподключение — с паузой 1–60 с (по умолчанию,
  `server.reconnect`).
- **Связь:** `hello` — 10 с, `welcome` — 15 с после открытия. Сервер шлёт ping раз в 5 с (по
  умолчанию, опция SDK `pingIntervalMs`) и закрывает соединение, если на два ping подряд не пришёл
  pong; агент шлёт ping раз в 10 с и ждёт pong 5 с. Обрыв без закрытия замечается за 10–15 с,
  закрытое соединение — сразу.
- **Количество:** `fetch` сразу — 64; запросов воркеров к серверу сразу — 64; `agent.logs.lines` —
  по умолчанию 200, не больше 5000.
- **Манифест:** `configs` — до 64, `routes`, `events`, `jobs` и `requests` — до 256 элементов;
  `version` — обязательно, от 1 до 64 символов, `description` (и у элементов списков) — до 1024;
  `configs[].key` — по правилу имён (§1); `routes[].method` — `^[A-Z]{1,16}$`, `routes[].path` —
  начинается с `/`, до 512 символов, без пробелов; `events[].type` — по правилу типа события (§1),
  не `job.*`; `jobs[].type` и `requests[].type` — по правилу типа события; все схемы
  (`configs[].schema`, `routes[].request` и `response`, `events[].schema`, `jobs[].schema`,
  `requests[].schema` и `response`) — объекты.
