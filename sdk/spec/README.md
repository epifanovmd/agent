# Формат сообщений агента, сервера и воркера

Здесь описано, какими сообщениями агент обменивается с сервером (§2–§9) и с воркерами на
своём узле (§10). Если вы пользуетесь SDK, читать это не обязательно: документ нужен тем, кто
пишет свой SDK или работает с агентом без SDK. Образцы всех сообщений лежат в
[`examples/`](examples) (§9), и каждый SDK проверяется на них.

Менять формат начинают с этого документа и образцов. Внутри одной версии можно только
добавлять (§8).

## 1. Главные правила

1. **Соединение открывает только агент.** Агенту не нужны входящие порты: он работает за NAT
   и прокси.
2. **Без связи — обычный режим.** Агент продолжает работать, складывает важные сообщения на
   диск и досылает их, когда связь вернётся.
3. **Сервер хранит, что должно быть сделано, и присылает это заново после каждого
   подключения.** Это задачи, команды и состояние. Поэтому агент должен спокойно принимать
   повторы: одно и то же он узнаёт по id. Агент же отправляет серверу сообщения одним из трёх
   способов (§4).
4. **WebSocket или HTTP — сообщения одни и те же.** WebSocket основной, HTTP запасной.
5. **Версию формата и возможности стороны согласуют** при подключении (§3).

## 2. Подключение

### 2.1 WebSocket (основной способ)

```
GET /api/v1/agent-link
Upgrade: websocket
Sec-WebSocket-Protocol: agent.v1
Authorization: Agent <agentId>.<secret>
```

- Одно текстовое сообщение WebSocket — одно сообщение JSON (UTF-8).
- Проверка, что соединение живо, — ping/pong WebSocket: каждая сторона шлёт ping раз в 20 с.
  Если pong не пришёл за 10 с, соединение закрывается, и агент подключается снова.
- Если ключ неверный, сервер отвечает обычным HTTP-кодом ещё **до** открытия WebSocket:
  - `401` — ключ неверный или отозван;
  - `403` — агент заблокирован;
  - `426` — агент не предложил канал `agent.v1`.

**Коды закрытия соединения:**

| Код  | Кто закрывает | Причина                                                        | Что делает агент                                                          |
| ---- | ------------- | -------------------------------------------------------------- | ------------------------------------------------------------------------- |
| 1000 | любой         | обычное закрытие                                               | подключается снова (если сам не останавливается)                          |
| 1001 | агент         | агент останавливается                                          | —                                                                         |
| 1012 | сервер        | сервер перезапускается                                         | подключается сразу, со случайной задержкой до 1 с                         |
| 4400 | сервер        | неправильное сообщение или нет `hello` за 10 с                 | подключается снова с растущей паузой, пишет в лог                         |
| 4401 | сервер        | ключ агента отозван                                            | регистрируется заново (§5), если есть токен; иначе ждёт с растущей паузой |
| 4409 | сервер        | нет общей версии формата                                       | ждёт с растущей паузой — нужна новая версия агента или сервера            |
| 4410 | сервер        | подключилась другая копия этого же агента                      | 30 с не подключается, потом — с растущей паузой                           |
| 4429 | сервер        | сервер перегружен; в `reason` — через сколько секунд повторить | подключается не раньше указанного                                         |

### 2.2 HTTP (запасной способ)

Если WebSocket не проходит (прокси не пропускает или сервер отвечает `404`/`400`/`426`), агент
обменивается теми же сообщениями пачками через HTTP:

```
POST /api/v1/agent-link/sync
Authorization: Agent <agentId>.<secret>
{ "sessionId": "…" | null, "messages": [ …сообщения… ], "waitSeconds": 0..25 }
→ 200 { "sessionId": "…", "messages": [ …сообщения… ] }
```

- Первый запрос: `sessionId: null`, первым сообщением — `hello`. В ответе приходит `welcome`.
- Сервер обрабатывает присланное по порядку и отвечает тем, что нужно передать агенту. Если
  передавать нечего, он держит запрос до `waitSeconds` и ждёт новую задачу, команду или
  изменение состояния.
- Если сервер уже забыл это подключение, он отвечает `409` с кодом `AGENT_SESSION_EXPIRED`, и
  агент начинает заново с `hello`.
- Раз в 10 минут агент пробует вернуться на WebSocket.

## 3. Начало разговора

```
агент                                сервер
  │── hello ─────────────────────────▶│  проверяет версию и возможности
  │◀──────────────────────── welcome ─│  или закрывает с кодом 4409
  │◀─ задачи, команды, состояние (job.assign, cmd.run, state.put, job.cancel …)
  │── status / metrics / … ──────────▶│
```

- `hello` — первое сообщение. До `welcome` ничего другого слать нельзя. Нет `hello` за 10 с —
  сервер закрывает соединение (4400). Нет `welcome` за 15 с — агент закрывает сам.
- `hello.versions` — версии формата, которые знает агент. Сервер выбирает наибольшую общую и
  пишет её в `welcome.version`. Общей нет — закрывает с кодом 4409.
- В `hello` агент сообщает свои **возможности** (`capabilities`) и задачи, которые у него есть
  (`jobs`). Сюда входят и выполняющиеся задачи, и **завершённые без связи, чей итог ещё не
  отправлен**. Сервер сверяет этот список (§6.3) раньше, чем получит итоги. Поэтому задачу с
  неотправленным итогом обязательно перечислить, иначе сервер сочтёт её потерянной.
- `welcome.config` — настройки от сервера: как часто слать статус и метрики и текущая сводная
  подписка (§6.9). Позже сервер может поменять их сообщением `config`.

## 4. Конверт и способы доставки

Каждое сообщение — конверт:

```json
{ "type": "job.complete", "id": "0f8c…", "re": "…", "seq": 42, "ts": 1791380000000, "data": { … } }
```

| Поле   | Тип             | Когда нужно                   | Что это                                              |
| ------ | --------------- | ----------------------------- | ---------------------------------------------------- |
| `type` | string          | всегда                        | тип сообщения, `<область>.<действие>`                |
| `id`   | string (≤ 64)   | у важных сообщений и запросов | уникальный id сообщения                              |
| `re`   | string          | у ответов                     | `id` сообщения, на которое это ответ                 |
| `seq`  | integer ≥ 1     | у обычных сообщений агента    | номер по порядку с момента запуска агента (`bootId`) |
| `ts`   | integer, мс UTC | не обязательно                | когда сообщение создано                              |
| `data` | object          | зависит от типа               | содержимое                                           |

Незнакомые поля получатель пропускает. Незнакомый `type` от агента сервер не обрабатывает и
отвечает `error` с кодом `UNKNOWN_TYPE` — соединение при этом не рвётся. Незнакомый `type` от
сервера агент записывает в лог и пропускает.

**Как агент отправляет сообщения серверу — три способа:**

| Способ      | Что гарантировано                                       | Как устроено                                                                                                                                                                                                                      | Сообщения                                                                                                         |
| ----------- | ------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| **обычные** | приходят по порядку и без повторов, но могут потеряться | у каждого номер `seq`. Сервер подтверждает последний полученный номер (`ack{seq}`). Неподтверждённые агент держит в небольшом буфере в памяти и досылает после переподключения. Номера не больше уже принятого сервер отбрасывает | `status`, `metrics`, `inventory`, `capabilities`, `log`, `job.accept`, `job.progress`, `cmd.accept`, `cmd.output` |
| **важные**  | доходят хотя бы раз, даже если агент перезапустился     | у каждого `id`. Агент хранит их на диске, пока сервер не подтвердит (`ack{ids}`). Повтор сервер обрабатывает так, чтобы ничего не задвоилось                                                                                      | `job.event`, `job.complete`, `job.fail`, `job.reject`, `cmd.done`, `state.applied`, `event`                       |
| **запросы** | приходит ответ или ошибка                               | `id` → ответ с `re`. Агент ждёт 30 с, потом спрашивает снова новым запросом                                                                                                                                                       | `job.urls`                                                                                                        |

- Подтверждение сервера: `ack { "ids": [..], "seq": N }`. В `ids` — важные сообщения, которые
  сервер обработал окончательно, **в том числе отклонённые насовсем**. `seq` — последний
  полученный номер обычных сообщений.
- Ошибка обработки — `error{re, code, message, retryable}`:
  - `retryable: false` — агент удаляет сообщение с диска и пишет в лог. Пример: `JOB_LEASE_LOST`
    — задачу уже отдали другому;
  - `retryable: true` — сообщение остаётся на диске, и агент повторит его с растущей паузой.

## 5. Регистрация агента

1. Бэкенд выдаёт **токен регистрации**. Как его выпускать и проверять — дело бэкенда (в SDK —
   опции `enrollToken` или `enroll`).
2. При первом запуске агент регистрируется:
   ```
   POST /api/v1/agent-link/enroll
   { "token": "…", "name": "node-01", "labels": {…}, "host": {…} }
   → 201 { "agentId": "…", "secret": "…" }
   ```
   Слишком много неудачных попыток с одного адреса — ответ `429` с кодом `ENROLL_RATE_LIMITED` и
   заголовком `Retry-After` (через сколько секунд повторить).
3. Ключ `agentId.secret` агент хранит в файле, который может читать только он сам (`0600`).
   Больше токен ему не нужен. Сервер хранит только хеш секрета (sha256).
4. **Смена ключа без новой регистрации.** Бэкенд отправляет агенту команду `agent.rotateKey`.
   Агент сам придумывает новый секрет, сохраняет его у себя как ожидающий и возвращает в итоге
   команды только его хеш: `result: {secretHash}`. Сам секрет никуда не уходит. Сервер запоминает
   хеш как ожидающий и закрывает соединение кодом 1012. Агент подключается снова, сначала с
   новым секретом: сервер его признаёт, а старый забывает. Если новый не подошёл (`401`), агент
   подключается со старым.
5. Если бэкенд отозвал агента, соединение закрывается с кодом 4401. Если у агента ещё есть
   токен, он регистрируется заново. Если токена нет, агент ждёт с растущей паузой и пишет в лог.

## 6. Сообщения

**A→S** — от агента серверу, **S→A** — от сервера агенту.

### 6.1 Подключение

**`hello`** (A→S)

```jsonc
{
  "versions": [1],
  "agent": {
    "name": "node-01",
    "version": "1.0.0",
    "sdk": "go/1.0.0",
    "codeHash": "sha256…", // хеш программы агента (не обязательно)
    "bootId": "a1b2c3d4", // случайный id этого запуска: с него начинается нумерация seq
    "encryptionKey": "base64…", // открытый ключ X25519 агента — для запечатанных значений в состоянии (§6.5)
    "startedAt": 1791380000000,
  },
  "host": {
    "hostname": "node-01",
    "os": "linux",
    "arch": "amd64",
    "platform": "ubuntu 24.04",
    "kernel": "6.8.0",
    "cpus": 16,
    "memoryBytes": 68719476736,
  },
  "labels": { "zone": "eu" },
  "capabilities": {
    "jobs": { "queues": [{ "name": "example.echo", "concurrency": 2 }] },
    "commands": { "names": ["agent.logs", "agent.drain", "agent.update"] },
    "state": { "domains": { "example.kv": 12 } }, // раздел состояния → применённая версия (null — ещё нет)
    "telemetry": { "channels": ["example.kv"] },
    "update": { "mode": "self" }, // self | external | disabled
  },
  "jobs": [{ "jobId": "…", "attempt": 0 }], // задачи агента: выполняются или итог ещё не отправлен
}
```

**`welcome`** (S→A)

```jsonc
{
  "version": 1,
  "agentId": "…",
  "sessionId": "…",
  "serverTime": 1791380000123,
  "config": {
    "statusIntervalMs": 15000, // как часто слать status
    "metricsIntervalMs": 15000, // как часто слать metrics
    "subscription": { "metricsIntervalMs": 1000, "metrics": ["diskio"] }, // сводная подписка (§6.9); нет подписок — поля нет
  },
}
```

**`config`** (S→A) — меняет часть `welcome.config`:

- `statusIntervalMs`, `metricsIntervalMs` — новое значение; поля нет или `0` — не менять;
- `subscription` — новая сводная подписка **целиком** (§6.9); `{}` — подписок нет; поля нет — подписка
  не меняется.

**`ack`** (S→A) — `{ "ids"?: string[], "seq"?: integer }`.

**`error`** (S→A) — `{ "code": "…", "message": "…", "retryable": boolean }`. В `re` — id сообщения
агента, если ошибка про него.

**`capabilities`** (A→S, обычное) — новые возможности, появившиеся после `hello`: например,
запустился воркер и объявил команды, разделы состояния, показатели (§10). В `data` — тот же
объект, что `hello.capabilities`: все возможности на сейчас.

Сервер **добавляет** их к уже известным:

- новые имена дописывает;
- для раздела состояния берёт большую из применённых версий;
- убрать возможности можно только новым `hello`.

После этого сервер отправляет то, что стало можно отправить: состояние новых разделов и
ждущие команды.

### 6.2 Статус и метрики

**`status`** (A→S, обычное) — при каждом изменении и не реже `statusIntervalMs` (или чаще, если
так просит подписка, §6.9). Это ещё и знак «я жив»: по нему сервер продлевает срок всем
перечисленным задачам (§6.3).

```jsonc
{
  "state": "idle", // starting | idle | busy | draining (дорабатывает, новое не берёт) | updating | degraded (что-то не так)
  "message": "…", // почему degraded и т. п.
  "slots": { "example.echo": 1 }, // сколько ещё задач каждой очереди можно взять
  "capacity": { "example.echo": 2 }, // сколько всего (воркеры меняются после hello)
  "jobs": [
    {
      "jobId": "…",
      "attempt": 0,
      "queue": "example.echo",
      "startedAt": 1791380000000,
    },
  ],
  "workers": [
    {
      "name": "report",
      "state": "running", // starting | running | backoff (перезапускается после падения) | stopped
      "instances": 1, // сколько копий работает
      "version": "2.0.0",
      "release": true, // воркер из выпуска: его можно обновить командой worker.update (§7)
      "health": "degraded", // ok | degraded — как оценивает себя сам воркер (worker.health, §10); нет поля — не сообщал
      "message": "example.db недоступна", // причина degraded
      "paused": true, // хоть одна очередь воркера на паузе (от воркера или сервера)
    },
  ],
  "outbox": 0, // сколько важных сообщений ждут подтверждения
}
```

`state: degraded` ставится, если какой-то воркер перезапускается после падения или сам сообщил,
что он не в порядке. В `message` тогда перечислены причины.

**`metrics`** (A→S, обычное) — раз в `metricsIntervalMs` (или чаще, если так просит подписка, §6.9).

```jsonc
{
  "collectedAt": 1791380000000, // когда собрано (часы агента)
  "clockOffsetMs": -120, // насколько часы сервера впереди часов агента (по welcome.serverTime)
  "backfill": true, // собрано без связи и дослано позже
  "host": { "cpuPercent": 12.5, "load1": 0.4, "memUsedBytes": 1073741824, "…": "…" }, // метрики узла — по группам, таблица ниже
  "gpus": [
    { "index": 0, "name": "RTX 4090", "utilPercent": 97, "memUsedBytes": 1, "memTotalBytes": 2, "temperatureC": 71 },
  ],
  "channels": { "example.kv": { "…": "…" } }, // показатели воркеров; что внутри — решает воркер
}
```

**Группы метрик узла.** Поля `host` собираются группами. Какие группы собирать, задаёт настройка
агента `telemetry.metrics`; подписка сервера может на время добавить группы (§6.9). Все поля `host`
необязательные: нет группы или значения на этой платформе — нет поля. Скорости и счётчики «за
интервал» считаются между двумя сборами, поэтому в первой точке после запуска их нет.

| Группа         | Поля в `host`                                                                                                                                                  |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `cpu`          | `cpuPercent` — загрузка процессора, %                                                                                                                          |
| `cpu.cores`    | `cpuCores: [%, …]` — загрузка по ядрам                                                                                                                         |
| `load`         | `load1`, `load5`, `load15` — средняя нагрузка за 1, 5 и 15 минут                                                                                               |
| `memory`       | `memUsedBytes`, `memTotalBytes`, `memAvailableBytes`                                                                                                           |
| `swap`         | `swapUsedBytes`, `swapTotalBytes`                                                                                                                              |
| `disk`         | `diskUsedBytes`, `diskTotalBytes` — корневая файловая система `/`; `disks: [{mount, usedBytes, totalBytes, inodesUsed?, inodesTotal?}]` — по `telemetry.disks` |
| `diskio`       | `diskReadBps`, `diskWriteBps` (байт/с), `diskReadIops`, `diskWriteIops` (операций/с) — сумма по физическим дискам                                              |
| `network`      | `netRxBps`, `netTxBps` (байт/с), `netErrors`, `netDrops` (ошибок и отброшенных пакетов за интервал) — сумма по показываемым интерфейсам                        |
| `interfaces`   | `interfaces: [{name, rxBps, txBps, errors?, drops?}]` — сеть по интерфейсам, кроме исключённых настройкой `telemetry.excludeInterfaces`                        |
| `conntrack`    | `conntrack`, `conntrackMax` — записей в таблице отслеживания соединений и её предел (Linux)                                                                    |
| `sockets`      | `tcp: {established, timeWait, closeWait, listen}` — TCP-соединения по состояниям                                                                               |
| `processes`    | `processes`, `threads` — процессов и потоков на узле                                                                                                           |
| `fds`          | `fdsOpen`, `fdsMax` — открытых файлов на узле и предел (Linux)                                                                                                 |
| `uptime`       | `uptimeSec` — сколько узел работает                                                                                                                            |
| `temperatures` | `temperatures: {maxC, sensors: [{name, c}]}` — самая высокая температура и датчики, °C (где они доступны)                                                      |

Видеокарты — отдельный блок `gpus`, его включает настройка агента `telemetry.gpu`. Полная точка со
всеми группами — образец `metrics` в [`examples/observe.json`](examples/observe.json).

- **Без связи** агент продолжает собирать метрики — до `telemetry.backlog` точек (настройка
  агента, по умолчанию 720). После `welcome` он досылает их по порядку с `backfill: true`.
  Сервер сохраняет их в историю, но не принимает по ним решений «здесь и сейчас».
- **Время точки** по часам сервера — `collectedAt + clockOffsetMs`. Оно верно и для досланных,
  и для отправленных повторно, и для застрявших в очереди точек. Разницу часов агент считает
  при каждом `welcome`: `serverTime` минус своё время получения. Ошибка не больше задержки
  сети в одну сторону. Если `clockOffsetMs` нет, сервер берёт время получения.
- **Частота и состав меняются на ходу** — `config` с новым `metricsIntervalMs` или подпиской
  (§6.9). Агент применяет их сразу.

`channels` — последние показатели от воркеров (`telemetry`, §10), по объекту на каждое имя из
`capabilities.telemetry.channels`. Если воркер остановился, его показатели пропадают из
`metrics`, пока он не пришлёт новые.

**`inventory`** (A→S, обычное) — сведения об узле, которые меняются редко. Агент присылает их
после `welcome` и при изменении; проверяет раз в 10 минут.

```jsonc
{
  "collectedAt": 1791380000000,
  "os": {
    "hostname": "node-01",
    "platform": "ubuntu 24.04",
    "kernel": "6.8.0",
    "arch": "amd64",
```

### 6.3 Задачи (`capabilities.jobs`)

Сервер сам раздаёт задачи агентам, у которых есть свободные места (`status.slots`). Верить
нужно именно `status.slots`: воркеры запускаются и перезапускаются уже после `hello`. А
`hello.capabilities.jobs` лишь говорит, какие очереди были в момент подключения. Когда число
мест меняется, агент сразу присылает `status`.

**Срок задачи.** Задача выполняется под сроком: каждый `status`, где она упомянута, продлевает
его до `сейчас + leaseSeconds`. Пока агента нет на связи, срок не продлевается:

- агент вернулся до конца срока — задача продолжается;
- вернулся позже — задачу уже отдали другому, и итог старой попытки сервер отклонит
  (`JOB_LEASE_LOST`).

Срок задаётся для очереди. Для долгих задач это и есть время, которое агент может пробыть без
связи.

**Сверка после `hello`.** Для каждой задачи, которую сервер считает выполняющейся на агенте:

- агент её перечислил — задача продолжается;
- агент её не перечислил и не подтверждал (`job.accept`) — сервер присылает её снова;
- агент её не перечислил, но подтверждал — задача потеряна (агент перезапустился). Попытка
  проваливается с кодом `AGENT_LOST` и повторяется по правилам очереди.

Если агент перечислил в `hello.jobs` задачу, которая на сервере у него уже не выполняется,
сервер присылает ему `job.cancel`.

| Сообщение      | Направление            | data                                                                                                                                    |
| -------------- | ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| `job.assign`   | S→A                    | `{jobId, attempt, queue, data, leaseSeconds, inputs: {имя: url}, outputs: {имя: {url, contentType?}}, urlsExpireAt?}`                   |
| `job.accept`   | A→S обычное            | `{jobId, attempt}` — задачу взяли в работу                                                                                              |
| `job.reject`   | A→S важное             | `{jobId, attempt, code, message}` — не может выполнить (очередь не обслуживается, нет места); попытка возвращается в очередь            |
| `job.progress` | A→S обычное            | `{jobId, attempt, progress?: 0..1, text?: ≤200, log?: string[] (≤100 строк по ≤1000)}`; частые обновления агент прореживает             |
| `job.event`    | A→S важное             | `{jobId, attempt, seq, type: ≤50, data?}` — событие задачи (например, итог этапа); `seq` с 1 внутри попытки, повторы сервер отбрасывает |
| `job.urls`     | A→S запрос / S→A ответ | запрос `{jobId, attempt, inputs?: string[], outputs?: string[]}` → ответ `{inputs, outputs, expiresAt}` — свежие ссылки на файлы        |
| `job.cancel`   | S→A                    | `{jobId, attempt}` — прервать сразу, итог не отправлять                                                                                 |
| `job.stop`     | S→A                    | `{jobId, attempt}` — закончить пораньше: доделать шаг и отправить `job.complete`                                                        |
| `job.complete` | A→S важное             | `{jobId, attempt, result?}`                                                                                                             |
| `job.fail`     | A→S важное             | `{jobId, attempt, code: ^[A-Z0-9_]+$ ≤64, message: ≤2000, retryable}`                                                                   |

Коды ошибок, которые ставит сам агент:

- `WORKER_ERROR` — ошибка в обработчике;
- `WORKER_CRASHED` — процесс воркера упал;
- `QUEUE_NOT_SERVED` — эту очередь никто не обслуживает;
- `UPLOAD_FAILED` — не удалось загрузить файл-результат.

### 6.4 Команды (`capabilities.commands`)

Агент выполняет только команды из своего списка. Ждущие команды (`pending`) сервер присылает
и после переподключения; повтор агент узнаёт по `commandId`.

| Сообщение    | Направление | data                                                           |
| ------------ | ----------- | -------------------------------------------------------------- |
| `cmd.run`    | S→A         | `{commandId, name, args?, timeoutSec}`                         |
| `cmd.accept` | A→S обычное | `{commandId}`                                                  |
| `cmd.output` | A→S обычное | `{commandId, chunk: ≤64 КБ}` — вывод по мере работы            |
| `cmd.done`   | A→S важное  | `{commandId, ok, exitCode?, result?, error?: {code, message}}` |

Команды самого агента (встроенные). Любую из них можно выключить настройкой агента
`commands.disabled` — тогда агент её не объявляет и не выполняет.

| Имя               | args                                      | Что делает                                                                                                                                  |
| ----------------- | ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| `agent.logs`      | `{lines?: ≤5000}`                         | последние строки лога агента и воркеров (по умолчанию 500)                                                                                  |
| `agent.drain`     | —                                         | не брать новые задачи, доделать текущие (`status.state = draining`)                                                                         |
| `agent.resume`    | —                                         | снова брать задачи                                                                                                                          |
| `agent.restart`   | —                                         | перезапустить агента, когда задачи доделаны                                                                                                 |
| `agent.update`    | `{version, url, sha256, signature}`       | обновить программу агента (§7); только при `update.mode = self`                                                                             |
| `agent.rotateKey` | —                                         | сменить секрет агента (§5); итог — `{secretHash}`                                                                                           |
| `worker.restart`  | `{name?}`                                 | заменить воркер новой копией (§10, «Замена»); без `name` — все воркеры по очереди                                                           |
| `worker.update`   | `{name, version, url, sha256, signature}` | обновить воркер из выпуска (§7); итог — `{name, version, previous}`                                                                         |
| `worker.pause`    | `{name, queues?}`                         | воркер не получает новых задач этих очередей (без `queues` — всех своих), выданные доделываются; итог — `{name, paused}` (§10)              |
| `worker.resume`   | `{name, queues?}`                         | снять паузу, поставленную сервером (без `queues` — со всех очередей); пауза, которую поставил сам воркер, остаётся; итог — `{name, paused}` |

Команд `worker.*` нет, если в настройках агента нет воркеров; `worker.update` — если нет воркеров
из выпуска. Неизвестное имя воркера в `worker.pause` и `worker.resume` — ошибка `WORKER_UNKNOWN`.

### 6.5 Состояние (`capabilities.state`)

Состояние — это то, как всё должно быть на узле. Оно делится на **разделы** (`domain`,
например `example.kv`). Сервер присылает раздел целиком, с номером версии. Агент:

- сохраняет снимок на диск;
- передаёт воркеру — применять его повторно должно быть безопасно;
- при ошибке повторяет;
- после перезапуска применяет снимок с диска, не дожидаясь сервера;
- раз в `state.resyncInterval` (настройка агента, по умолчанию 10 минут) заново отдаёт воркеру
  последний снимок, чтобы исправить ручные изменения на узле. `state.applied` той же версии
  серверу при этом уходит, только если итог изменился.

| Сообщение       | Направление | data                                                                           |
| --------------- | ----------- | ------------------------------------------------------------------------------ |
| `state.put`     | S→A         | `{domain, version, spec}`                                                      |
| `state.applied` | A→S важное  | `{domain, version, ok, error?, report?}` — `report` воркер заполняет как хочет |

**Отчёт при ошибке.** Если состояние не применилось, воркер может приложить отчёт о том, что получилось
(`{ok: false, error, report}`), например «интерфейсы tun0 и tun1 подняты, tun2 — порт занят».

**Секреты в снимке.** Любое значение в `spec` может быть запечатанным — объект ровно с одним полем
`{"$sealed": "v1.<eph>.<nonce>.<ct>"}` (части — base64url без `=`). Его может раскрыть только агент,
которому оно запечатано:

- `eph` — одноразовый открытый ключ X25519 отправителя;
- ключ шифра — HKDF-SHA256 от общего секрета X25519 (`eph` и ключа агента из
  `hello.agent.encryptionKey`), salt пустой, info `agent sealed v1`;
- шифр — AES-256-GCM, `nonce` 12 байт, без дополнительных данных; `ct` — шифротекст с тегом;
- внутри — JSON исходного значения.

Агент хранит снимок на диске запечатанным и раскрывает значения только в памяти, перед передачей
воркеру. Не раскрылось (ключ агента сменился, данные повреждены) — `state.applied {ok: false}` с ошибкой
«секрет не расшифрован», и воркер снимок не получает. Образцы — [`examples/sealed.json`](examples/sealed.json)
(там ТЕСТОВАЯ пара ключей) и `state.put.sealed` в [`examples/state.json`](examples/state.json).

Номер версии раздела только растёт, **в том числе после перезапуска сервера**. Агент помнит
применённую версию на диске и пропускает снимок, если он не новее. Сервер хранит версию в БД.
Сервер без БД берёт номер не меньше текущего времени в миллисекундах.

Сервер присылает `state.put`, только если версия новее той, что применил агент (по
`hello.capabilities.state.domains` и последнему `state.applied`). Если снимки пришли подряд,
агент применит только последний.

Раздел, который обслуживает воркер (§10), появляется в `capabilities` после того, как воркер
запустился. Каждый новый запуск воркера (перезапуск, замена) снова получает последний снимок.
Поэтому сервер может получить `state.applied` одной и той же версии повторно.

### 6.6 События (`event`)

Сообщения агента и воркеров «что-то случилось», не связанные с задачей: переключили маршрут,
заполнился диск, закончилось резервное копирование.

| Сообщение | Направление | data                                                              |
| --------- | ----------- | ----------------------------------------------------------------- |
| `event`   | A→S важное  | `{source, type: ≤50, data?}` — `source` — имя воркера или `agent` |

Повтор сервер узнаёт по `id` конверта.

### 6.7 Имена

- Имена очередей, команд, разделов состояния и показателей: латиница, цифры, `.`, `_`, `-`;
  начинаются с буквы или цифры; не длиннее 64 символов (`^[A-Za-z0-9][A-Za-z0-9._-]{0,63}$`).
  Неверное имя агент не примет (`worker.ready.rejected`), а сервер на SDK откажет с
  `MESSAGE_INVALID`.
- Команды и разделы на `agent.` и `worker.` принадлежат агенту, воркер их объявить не может.
- Каждое имя команды, раздела или показателей принадлежит одному воркеру — тому, кто объявил
  его первым. Другому воркеру с тем же именем агент откажет (`worker.ready.rejected`).

### 6.8 Лог агента и воркеров (`log`)

Агент присылает записи своего лога и вывод воркеров пачками — не чаще раза в секунду, до 500 записей.

| Сообщение | Направление | data                                                                                                                         |
| --------- | ----------- | ---------------------------------------------------------------------------------------------------------------------------- |
| `log`     | A→S обычное | `{entries: [{at, level, source, msg, attrs?}]}` — `level`: debug \| info \| warn \| error; `source`: `agent` или имя воркера |

С какого уровня слать записи, решает агент: берёт более подробный из двух — настройки агента
`log.forward` (`off`, `error`, `warn`, `info`, `debug`; по умолчанию `warn`) и `logLevel` сводной
подписки (§6.9). Подписка может сделать лог только подробнее, но не тише. Без связи записи не
копятся; если буфер (1000 записей) переполнен, лишние отбрасываются, и агент присылает запись
«пропущено N».

### 6.9 Подписка сервера

Подписка — просьба сервера на время присылать чаще или подробнее обычного: например, пока
человек смотрит на узел в интерфейсе. У одного агента может быть много подписок (по одной на
каждого, кто смотрит), у каждой свой срок. Хранит их и следит за сроками сервер, а агенту
присылает одну **сводную подписку** — поле `subscription` в `welcome.config` и `config`:

```jsonc
{
  "statusIntervalMs": 1000, // слать status не реже, мс
  "metricsIntervalMs": 1000, // слать metrics не реже, мс
  "metrics": ["diskio", "sockets"], // группы метрик узла (§6.2) сверх telemetry.metrics агента
  "logLevel": "debug", // слать лог с этого уровня: debug | info | warn | error
  "channels": { "example.app": 1000 }, // канал показателей воркера → частота, мс
}
```

Все поля необязательные: нет поля — подписки этого не касаются.

**Как сервер сводит подписки.** Берутся только действующие (срок не истёк):

- `statusIntervalMs`, `metricsIntervalMs` — наименьшее значение;
- `metrics` — все группы без повторов, в порядке появления;
- `logLevel` — самый подробный (`debug` подробнее `info`, тот — `warn`, тот — `error`);
- `channels` — по каждому каналу наименьшее значение.

**Когда сервер присылает.** В `welcome.config.subscription` — текущая сводная; подписок нет — поля
нет. Когда сводная меняется (подписку добавили, сняли, она истекла), сервер присылает
`config {subscription}` с новой сводной **целиком**. `config {subscription: {}}` — подписок больше
нет. Одинаковую сводную повторно сервер не шлёт.

**Что делает агент.** Подписка только ужесточает настройки агента и сервера, но не ослабляет их:

- статус — не реже меньшего из `statusIntervalMs` сессии и подписки;
- метрики — не реже меньшего из `metricsIntervalMs` сессии, `metricsIntervalMs` подписки и всех
  частот в `channels` (показатели воркеров уходят в `metrics`, поэтому подписка на канал тоже
  ускоряет метрики);
- группы метрик узла — `telemetry.metrics` агента плюс `metrics` подписки; незнакомую группу агент
  пропускает;
- лог — более подробный уровень из `log.forward` и `logLevel` (§6.8);
- воркерам — действующую частоту метрик, уровень лога и подписки на их каналы в `worker.context`
  (§10).

Новая сессия начинается без подписки: агент берёт ту, что пришла в `welcome`.

## 7. Обновление агента

**Программа на сервере** (`update.mode = self`, systemd). По команде `agent.update` агент:

1. скачивает сборку во временный файл;
2. сверяет sha256;
3. проверяет подпись (Ed25519) открытым ключом выпуска — он вшит в агента или задан в
   настройках;
4. сохраняет текущую программу как `.prev`;
5. заменяет программу одним шагом и перезапускается.

Если новая версия за три запуска так и не получила `welcome`, агент возвращает `.prev`.

**Воркеры из выпуска.** Воркер, помеченный в `agent.yaml` как `release: true`, агент ведёт сам:
исполняемый файл лежит в `<dataDir>/workers/<name>/current`. По команде `worker.update` агент:

1. скачивает сборку, сверяет sha256 и подпись тем же ключом, что у агента;
2. откладывает текущую сборку как `previous` и ставит новую;
3. заменяет воркер его способом (`rolling` или `stop-first`) и ждёт регистрации;
4. если новая копия не зарегистрировалась или сообщила другую версию — возвращает `previous`, итог
   команды — ошибка `WORKER_UPDATE_FAILED`.

Поэтому воркер из выпуска должен сообщать в `worker.register` ту же версию, что у его сборки в выпуске
(агент передаёт её в `AGENT_WORKER_RELEASE_VERSION`). Другие ошибки команды: `WORKER_NOT_RELEASED` —
воркер не из выпуска, `UPDATE_NOT_VERIFIED` — у агента нет ключа проверки подписи,
`WORKER_UPDATE_IN_PROGRESS` — этот воркер уже обновляется. Сборки воркеров попадают в выпуск через
`agent release-manifest DIR VERSION --worker NAME=VERSION[,restart=…][,stopTimeout=…]` (файлы
`DIR/<name>-<version>-<os>-<arch>`, подпись тем же ключом).

Сервер может только **обновить** такой воркер. Добавить или удалить воркер сервер не может: это
решают настройки узла. В `status.workers` у таких воркеров есть `release: true`.

**Контейнер** (`update.mode = external`). Агент только сообщает свою версию, а обновляют его
новым образом.

**Раздача выпуска.** Серверная часть SDK делает это сама. Каталог выпуска из `make release`
(сборки `agent-<os>-<arch>`, подписанный `manifest.json`, `install.sh`) раздаётся без
авторизации — сборки подписаны, секретов в них нет:

```
GET /api/v1/agent-link/releases/manifest.json   { version, artifacts: [{ os, arch, file, sha256, signature }],
                                                  workers?: [{ name, version, os, arch, file, sha256, signature, restart?, stopTimeout? }] }
GET /api/v1/agent-link/releases/<file>          сборка агента
GET /api/v1/agent-link/install.sh               установщик (адрес сервера уже вписан)
```

Обновить можно агента с `update.mode = self`, у которого версия (`hello.agent.version`)
отличается от версии в манифесте. Сервер присылает ему `agent.update` со сборкой под его
`hello.host.os` / `arch`. Поставить агента на новый узел — одной командой:

```
curl -fsSL https://api.example.com/api/v1/agent-link/install.sh | sudo sh -s -- --token <токен регистрации>
```

## 8. Совместимость

- Внутри версии формата можно только **добавлять**: необязательные поля, новые типы сообщений,
  новые возможности. Незнакомое получатель пропускает.
- Несовместимое изменение — это новая версия формата. Сервер поддерживает текущую и
  предыдущую, агент перечисляет все, которые знает.
- Новая возможность объявляется в `hello.capabilities`. Сервер не шлёт агенту сообщения о
  возможности, которую тот не объявил.

## 9. Образцы сообщений

Образцы лежат в [`examples/`](examples), по файлу на тему:

| Файл              | Что в нём                                                                                     |
| ----------------- | --------------------------------------------------------------------------------------------- |
| `connection.json` | подключение: `hello`, `welcome`, `config` (с подпиской и без), `capabilities`, `ack`, `error` |
| `observe.json`    | наблюдение: `status`, `metrics`, `inventory`, `log`                                           |
| `jobs.json`       | задачи: `job.*`                                                                               |
| `commands.json`   | команды: `cmd.*`, в том числе встроенные команды агента                                       |
| `state.json`      | состояние: `state.put`, `state.applied` — между сервером и агентом и между агентом и воркером |
| `events.json`     | события `event` и показатели воркера `telemetry`                                              |
| `workers.json`    | связь воркера с агентом: `worker.*` (§10)                                                     |
| `sealed.json`     | ТЕСТОВАЯ пара ключей агента и значения, запечатанные её открытым ключом (§6.5)                |

Каждый файл, кроме `sealed.json`, — объект «имя образца → `{from, to, message}`»:

- `from`, `to` — кто отправляет и кто получает: `agent`, `server` или `worker`;
- `message` — конверт целиком (§4).

Имя образца — тип сообщения (`hello`), вариант — через точку (`hello.minimal`). Если одно и то же
сообщение ходит в разные стороны, к имени добавляется отправитель: `state.put@server` и
`state.put@agent`.

Что проверяется:

- сервер принимает каждое сообщение от агента (`from: agent`, `to: server`);
- агент и каждый SDK читают каждое сообщение и записывают его обратно без потери полей;
- SDK воркера читает сообщения агента воркеру и пишет свои в том же виде, что образцы
  `from: worker`;
- на `sealed.json` каждый SDK проверяет, что раскрывает `$sealed` в исходное значение и не
  раскрывает значение, запечатанное другим ключом.

## 10. Связь воркера с агентом

Воркер — процесс на любом языке. Агент запускает его по своим настройкам и держит с ним
отдельный канал: **unix socketpair, дескриптор из `AGENT_IPC_FD` (3)**, по строке JSON на
конверт (§4).

Сеть, переподключение, хранение важных сообщений, ключ агента, обновление, метрики узла — это
делает агент. Воркер занимается только своим делом. При запуске он сообщает, что умеет:

| Что        | Поле при регистрации | Что это                                                                      |
| ---------- | -------------------- | ---------------------------------------------------------------------------- |
| задачи     | `queues`             | очереди сервера: срок, повтор, прогресс, файлы (§6.3)                        |
| команды    | `commands`           | действие «сделай сейчас» на этом узле (§6.4)                                 |
| состояние  | `domains`            | разделы состояния: снимок целиком с версией; агент хранит и повторяет (§6.5) |
| показатели | `channels`           | данные воркера в `metrics.channels` (§6.2)                                   |
| события    | —                    | события воркера, доходят гарантированно (§6.6)                               |

Переменные окружения воркера: `AGENT_IPC_FD`, `AGENT_WORKER` (имя), `AGENT_VERSION`; воркеру из выпуска
(`release: true`) — ещё `AGENT_WORKER_RELEASE_VERSION` (версия его сборки); со своим корневым сертификатом
сервера — `AGENT_SERVER_CA_FILE`.

| Сообщение         | Направление | data                                                                                                                                               |
| ----------------- | ----------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| `worker.register` | W→A         | `{name, version, sdk, queues: [{name, concurrency}], commands?: [], domains?: [], channels?: []}` — первое сообщение, не позже 120 с после запуска |
| `worker.ready`    | A→W         | `{agentVersion, rejected?: string[]}` — агент принял воркер; `rejected` — имена, которые не достались (§6.7)                                       |
| `worker.context`  | A→W         | контекст агента: режим, сведения об агенте, связь, частоты, уровень лога (ниже, «Контекст»)                                                        |
| `worker.health`   | W→A         | `{ok, message?}` — воркер сам сообщает, в порядке ли он (ниже, «Самоуправление»)                                                                   |
| `worker.pause`    | W→A         | `{queues?: string[]}` — не давать воркеру новых задач этих очередей; без `queues` — всех его очередей                                              |
| `worker.resume`   | W→A         | `{queues?: string[]}` — снять свою паузу с этих очередей; без `queues` — со всех                                                                   |
| `worker.restart`  | W→A         | `{reason?}` — воркер просит заменить его новой копией                                                                                              |
| `worker.drain`    | A→W         | `{}` — не брать новых задач и выйти, когда текущие доделаны                                                                                        |
| `job.assign`      | A→W         | как в §6.3                                                                                                                                         |
| `job.cancel`      | A→W         | как в §6.3 — прервать, итог не отправлять                                                                                                          |
| `job.stop`        | A→W         | как в §6.3 — доделать шаг и отправить `job.complete`                                                                                               |
| `job.progress`    | W→A         | как в §6.3                                                                                                                                         |
| `job.event`       | W→A         | как в §6.3; `seq` считает воркер (с 1 внутри попытки)                                                                                              |
| `job.urls`        | W→A запрос  | как в §6.3, с `id`; агент отвечает `job.urls` или `error` с `re`                                                                                   |
| `job.complete`    | W→A         | как в §6.3                                                                                                                                         |
| `job.fail`        | W→A         | как в §6.3                                                                                                                                         |
| `cmd.run`         | A→W         | как в §6.4 — одна из команд, объявленных воркером                                                                                                  |
| `cmd.cancel`      | A→W         | `{commandId}` — срок команды истёк: прервать, итог уже не нужен                                                                                    |
| `cmd.output`      | W→A         | как в §6.4                                                                                                                                         |
| `cmd.done`        | W→A         | как в §6.4 — итог; агент отправит его серверу как важное сообщение                                                                                 |
| `state.put`       | A→W запрос  | как в §6.5, с `id` — применить снимок (повторно — без вреда)                                                                                       |
| `state.applied`   | W→A ответ   | как в §6.5, `re` — id `state.put`                                                                                                                  |
| `telemetry`       | W→A         | `{channel, data}` — последние показатели; агент добавит их в ближайшие `metrics`                                                                   |
| `event`           | W→A         | `{type, data?}` — агент допишет `source` (имя воркера) и отправит как важное (§6.6)                                                                |
| `worker.cleanup`  | A→W запрос  | `{}`, с `id` — агента удаляют с узла: убрать всё, что воркер создал (интерфейсы, правила, файлы)                                                   |
| `worker.cleaned`  | W→A ответ   | `{ok, error?}`, `re` — id `worker.cleanup`                                                                                                         |

**Контекст.** Сразу после `worker.ready` агент шлёт воркеру `worker.context`, а потом — каждый раз,
когда что-то в нём меняется (не чаще раза в 100 мс; одинаковый повторно не шлёт):

```jsonc
{
  "mode": "run", // run — обычная работа; cleanup — воркер запущен только для уборки
  "agent": {
    "id": "…", // пустая строка, пока агент не зарегистрирован
    "name": "node-01",
    "version": "1.1.0",
    "labels": { "zone": "eu" }, // нет меток — поля нет
  },
  "online": true, // есть ли сейчас связь с сервером
  "metricsIntervalMs": 1000, // действующая частота метрик агента, с учётом подписки (§6.9)
  "channels": { "example.app": 1000 }, // подписки на каналы показателей ЭТОГО воркера: канал → частота, мс; нет — поля нет
  "logLevel": "warn", // с какого уровня агент сейчас отправляет лог серверу (§6.8)
}
```

- По `metricsIntervalMs` и `channels` воркер решает, как часто готовить показатели: если на
  канал есть подписка — с её частотой, иначе — с частотой метрик агента.
- В режиме `cleanup` (команда `agent cleanup`) агент шлёт контекст **до** `worker.cleanup`: воркер
  может пропустить обычную подготовку и сразу убирать.
- Пока контекст не пришёл, воркер считает: `mode: run`, `online: false`, частота неизвестна.

**Самоуправление.** Воркер сам сообщает агенту о себе. Ответа на эти сообщения нет.

- `worker.health {ok, message?}` — в порядке ли воркер. Агент пишет оценку в
  `status.workers[].health` (`ok` или `degraded`) и причину в `message`. Если хоть один воркер не
  в порядке, `status.state` становится `degraded`. У воркера с несколькими копиями оценка — по
  худшей копии. Оценка копии пропадает вместе с ней.
- `worker.pause {queues?}` и `worker.resume {queues?}` — воркер просит не давать ему новых задач
  этих очередей (без `queues` — всех его очередей) и снова давать. Свободных мест у этих
  очередей становится 0 (`status.slots`), уже выданные задачи доделываются. В
  `status.workers[].paused` — `true`, если хоть одна очередь воркера на паузе. Такая пауза
  принадлежит копии воркера: новая копия начинает без неё.
- `worker.restart {reason?}` — воркер просит заменить его. Агент делает то же, что по команде
  `worker.restart` (ниже, «Замена»), но это не сбой: статус не становится `degraded`. Пока
  замена идёт, повторные просьбы не учитываются.

**Пауза с сервера.** Встроенные команды `worker.pause` и `worker.resume` (§6.4) ставят и снимают
паузу на очереди воркера со стороны сервера. Эта пауза хранится в памяти агента: она переживает
перезапуск и замену воркера, но не перезапуск агента. Паузы сервера и самого воркера независимы: очередь берёт задачи, только
когда её не держит на паузе ни тот, ни другой. `worker.resume` с сервера снимает только паузу
сервера, а `worker.resume` от воркера — только его собственную.

**Состояние.**

- Снимки разделов хранит агент: на диске, только новые версии, с повтором после ошибки.
- Воркер получает `state.put` после каждого запуска (и после перезапуска) и при каждой новой
  версии.
- Следующий снимок приходит только после ответа на предыдущий.

**Команды.**

- Агент принимает `cmd.run` от сервера, отвечает `cmd.accept` и передаёт команду воркеру.
- Затем ждёт `cmd.done` не дольше `timeoutSec`. Не дождался — отправляет воркеру `cmd.cancel`, а
  серверу итог `TIMEOUT`.
- Если воркер не запущен, итог — `WORKER_UNAVAILABLE`.

**Остановка.**

- Агент шлёт `SIGTERM`. Воркер перестаёт брать задачи, доделывает текущие и выходит.
- Не вышел за `stopTimeout` — агент завершает его принудительно (`SIGKILL`).
- Всё, что воркер создал на узле (интерфейсы, правила), остаётся — следующий запуск это
  подхватит.

**Замена** — по команде `worker.restart` или по просьбе самого воркера. Способ задаёт `restart`
воркера в настройках агента:

- `rolling` (по умолчанию) — новая копия запускается рядом, а старая перестаёт брать задачи и
  уходит, доделав текущие;
- `stop-first` — сначала уходит старая, потом запускается новая. Это для воркера, который
  держит то, что нельзя делить: порт, сетевой интерфейс.

По `worker.drain` воркер останавливает и свои фоновые циклы.

**Уборка** — только при удалении агента с узла: команда `agent cleanup` (её вызывает
`install.sh --uninstall`) запускает воркер, шлёт `worker.context` с `mode: cleanup`, затем
`worker.cleanup` и ждёт `worker.cleaned` не дольше
`stopTimeout`, затем останавливает воркер. Воркер без обработчика сразу отвечает `ok`. Сервер
уборку запустить не может; перезапуск, замена и остановка её не вызывают.

**Падение** — задачи воркера проваливаются с `WORKER_CRASHED` (сервер их повторит), а агент
перезапускает процесс с растущей паузой.

**Вывод.** Всё, что воркер печатает в stdout/stderr, агент пишет в свой лог с именем воркера.

Образцы сообщений между агентом и воркером — в [`examples/workers.json`](examples/workers.json),
а также образцы с `from: worker` или `to: worker` в остальных файлах [`examples/`](examples) (§9).
