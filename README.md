# agent

**Агент** — программа, которая ставится на каждый сервер (виртуальную машину, контейнер) и
держит связь с вашим бэкендом. **SDK** — библиотека для бэкенда на Node.js (`agent-sdk`),
которая принимает агентов и даёт с ними работать.

Агент один и тот же для всех проектов. Он — труба между бэкендом и программами на узле: передаёт
запросы, настройки, события и метрики, не разбирая их. Сам он умеет только общее:

- подключаться к серверу и переподключаться после обрыва;
- работать без связи, а потом досылать накопленное;
- запускать воркеры, следить за ними и перезапускать;
- хранить настройки воркеров на диске — узел работает по последним и без связи;
- присылать метрики узла (процессор, память, сеть, диск и другое — набор настраивается), чаще и
  подробнее — пока на узел смотрят;
- обновлять себя и воркеры, проверяя подпись, и возвращать прежнюю версию, если новая не
  заработала.

Всё, что нужно конкретному проекту, делают **воркеры** — обычные HTTP-сервисы на unix-сокете на
любом языке, без SDK. Агент ничего не знает о том, что они делают.

```
бэкенд (agent-sdk) ──WebSocket──► агент ──HTTP по unix-сокету──► воркер
                   ◄─────────────        ◄──────────────────────
```

Соединение всегда открывает агент: узлу не нужен открытый порт.

## Словарь

| Слово                   | Что это                                                                                                                                           |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| **узел**                | машина, на которой работает агент                                                                                                                 |
| **воркер**              | программа проекта, которую агент запускает на узле: HTTP-сервис на unix-сокете, одна копия                                                        |
| **манифест воркера**    | самоописание воркера (`GET /manifest`, обязательно): версия, ключи настроек со схемой значения, маршруты, события; агент передаёт его бэкенду     |
| **регистрация воркера** | проверка после запуска: воркер ответил на `GET /health` и `GET /manifest`; иначе — `state: invalid`, настроек и запросов он не получает           |
| **запрос**              | HTTP-запрос бэкенда к воркеру через агента (`fetch`): метод, путь, заголовки, тело; ответ приходит по частям                                      |
| **настройки**           | значения, которые бэкенд задаёт воркеру по ключам (`main`, `limits`, …), с растущей версией; агент хранит их на диске и передаёт воркеру          |
| **событие**             | сообщение воркера бэкенду «что-то случилось»; агент хранит его на диске, пока бэкенд не подтвердит                                                |
| **метрики**             | цифры узла (собирает встроенный воркер `sysmetrics`) и воркеров (их ответ `GET /metrics`)                                                         |
| **группа метрик**       | набор метрик узла, которые собираются вместе: `cpu`, `memory`, `disk`, `diskio`, `sockets` и другие; какие собирать — решает настройка агента     |
| **наблюдение**          | просьба бэкенда «присылай метрики чаще и журнал подробнее, столько времени» (`watch`) — например, пока узел открыт в интерфейсе                   |
| **жизнь воркера**       | как агент запускает, проверяет, заменяет и останавливает воркер — блок `lifecycle` его настроек; по умолчанию воркер переживает перезапуск агента |
| **занят (`busy`)**      | воркер ведёт долгую работу (`GET /health` → `busy: true`): плановая замена ждёт её окончания                                                      |
| **подхват**             | новый запуск агента находит живой процесс воркера, запущенный прежним, и следит за ним дальше, не перезапуская                                    |
| **действие**            | встроенная операция агента по просьбе бэкенда: перезапустить или обновить воркер, обновить агента, сменить ключ, показать журнал                  |
| **выпуск**              | подписанные сборки агента (и при желании воркеров) с `manifest.json`; бэкенд раздаёт их для установки и обновления                                |
| **Agents**              | главный объект SDK — «все подключённые агенты»: принимает агентов, отправляет запросы воркерам, доставляет настройки, хранит события и метрики    |

## Быстрый старт

Весь стенд — сервер на SDK и агент с воркерами-примерами (нужны Node ≥ 24 и python3; Go ставить
не нужно, он запускается в контейнере):

```bash
make demo-build     # собрать агента, воркеры на Go, выпуск агента, SDK
make demo-server    # терминал 1 — API на http://localhost:8080/api
make demo-agent     # терминал 2 — агент с воркерами-примерами
make e2e            # сквозные тесты: свой сервер и настоящий агент на каждый сценарий
```

Подробнее о стенде — [examples/README.md](examples/README.md).

## Как подключить к своему проекту

1. **Бэкенд** создаёт объект `Agents` из `agent-sdk/server` и подключает его к своему HTTP-серверу.
2. **Воркер** — любая программа, которая слушает HTTP на unix-сокете `AGENT_WORKER_SOCKET` и
   обязательно отвечает `GET /health` и `GET /manifest` (без них агент не регистрирует воркер),
   обслуживает свои маршруты (и, если нужно, `PUT /config/{key}`, `GET /metrics`,
   `POST /cleanup`); события она шлёт в сокет агента `AGENT_SOCKET`.
3. **Агент** ставится на узел одной командой, воркеры перечисляются в его настройках.

По шагам, с примерами кода — [sdk/docs/README.md](sdk/docs/README.md); справочник SDK —
[sdk/README.md](sdk/README.md); формат связи и что воркер получает от агента —
[sdk/spec](sdk/spec/README.md).

Поставить агента на свой Linux-сервер (с systemd) — три команды, `<версия>` — номер без `v`:

```bash
curl -fLo agent https://github.com/epifanovmd/agent/releases/download/v<версия>/agent-linux-amd64 && chmod +x agent
sudo ./agent install --server https://api.example.com --token <токен>
sudo agent status
```

Настройки — `/etc/agent/agent.yaml` (проверка — `sudo agent config check`), лог — `sudo agent logs -f`,
удаление — `sudo agent uninstall`. Docker, macOS и все флаги — [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md#установка).

## Команды

Go на машине не нужен: цели `make` запускают его в контейнере `golang` (`scripts/go.sh`; тесты —
в нём же с node). Node ≥ 24 нужен на машине. Список целей — `make help`.

| Команда                | Что делает                                                                                                  |
| ---------------------- | ----------------------------------------------------------------------------------------------------------- |

| `make race`            | то же с поиском гонок                                                                                       |
| `make vet`             | `go vet`                                                                                                    |
| `make fmt`             | отформатировать Go-код (gofmt)                                                                              |
| `make fmt-check`       | проверить форматирование Go-кода, ничего не меняя                                                           |

| `make format-check`    | проверить Prettier, ничего не меняя                                                                         |
| `make tidy`            | `go mod tidy`                                                                                               |
| `make node-sdk`        | собрать `sdk/node` (его берут тесты на Go и стенд)                                                          |
| `make sdk-test`        | тесты SDK, ESLint и проверка типов                                                                          |
| `make examples-test`   | ESLint и проверка типов сервера стенда, синтаксис воркеров-примеров                                         |
| `make e2e`             | сквозные тесты: сервер стенда, настоящий агент и воркеры-примеры — см. [examples](examples/README.md)       |

| `make release`         | выпуск: агент для linux/darwin × amd64/arm64, `manifest.json`, `install.sh` → `dist/<VERSION>/`             |

## Выпуск

Версия одна на агента, SDK и примеры: файл `VERSION`. Записать новую везде — `make version V=1.2.0`;
`make check` (и CI) проверяет, что она совпадает во всех местах.

Тег `v<VERSION>` → CI выкладывает в GitHub Release (тег с «-», например `v1.2.0-rc.1`, —
предварительный выпуск):

- подписанные сборки агента, `manifest.json`, `install.sh`;
- SDK — архив для Node (`agent-sdk-<версия>.tgz`);

и образы `ghcr.io/epifanovmd/agent:<версия>` (минимальный), `ghcr.io/epifanovmd/agent:<версия>-python`
(с python3 для воркеров на Python) и `ghcr.io/epifanovmd/agent-dist:<версия>`. Всё ставится с
GitHub, без npm — команда установки SDK в [sdk/README.md](sdk/README.md#установка).

Воркеры из выпуска (`release: true` в настройках агента) входят в него, если их сборки положить в
каталог выпуска заранее и передать `scripts/release.sh … --worker NAME=VERSION`.

Подпись: `agent-release keygen` (`go run ./cmd/agent-release keygen`) выдаёт пару ключей. Закрытый
(`AGENT_SIGNING_KEY`) — секрет репозитория для CI. Открытый (`AGENT_UPDATE_PUBLIC_KEY`) —
переменная репозитория: CI вшивает его в сборки агента, и они проверяют обновления без
настройки; бэкенду он нужен в опции `publicKey`. Как поставить агента прямо из GitHub Release —
[docs/ARCHITECTURE.md](docs/ARCHITECTURE.md#установка).

Об уязвимостях сообщайте не в открытых issue — см. [SECURITY.md](SECURITY.md).

## Требования

- Агент: Linux или macOS, amd64 или arm64. Установка службой — Linux с systemd (Debian/Ubuntu,
  RHEL/Fedora, SUSE и т. п.); без systemd (Alpine и другие) — в контейнере.
- Воркер: любой язык, который умеет HTTP-сервер на unix-сокете.
- SDK: Node.js ≥ 24.
- Разработка: Docker, Node ≥ 24, python3 (стенд и сквозные тесты).
