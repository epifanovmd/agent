# agent

**Агент для серверов и SDK для бэкенда: запускайте свои программы на узлах и управляйте ими из
своего бэкенда — без открытых портов, SSH и самописной доставки.**

[![CI](https://github.com/epifanovmd/agent/actions/workflows/ci.yml/badge.svg)](https://github.com/epifanovmd/agent/actions/workflows/ci.yml)
[![Release](https://img.shields.io/github/v/release/epifanovmd/agent)](https://github.com/epifanovmd/agent/releases)
[![License: MIT](https://img.shields.io/badge/license-MIT-blue.svg)](LICENSE)

`agent` — одна программа на Go, которая ставится на каждый сервер (виртуальную машину, контейнер),
сама подключается к вашему бэкенду и запускает рядом с собой **воркеры** — небольшие сервисы
вашего проекта на любом языке. Бэкенд на Node.js подключает **`agent-sdk`** и через него
отправляет воркерам запросы и задачи, задаёт им настройки, получает события, метрики и журнал,
обновляет агента и воркеры.

```
ваш бэкенд + agent-sdk ──WebSocket──► agent ──HTTP по unix-сокету──► воркеры проекта
            ▲                           │
            └── события, метрики, ──────┘   соединение открывает агент: узлу не нужен открытый порт
                итоги задач
```

## Зачем

Когда у проекта есть десятки серверов и на каждом нужно что-то делать — проверять сеть, собирать
отчёты, обслуживать сервис, выполнять задачи, — обычно появляются SSH-скрипты, cron, самописные
демоны со своим протоколом и доставкой обновлений. `agent` берёт на себя всю эту «трубу»:

- **связь** — агент сам подключается к бэкенду и переподключается после обрыва; без связи узел
  работает дальше, важные сообщения ждут на диске и уходят, когда связь вернётся;
- **запуск и надзор** — воркеры запускаются, проверяются по `GET /health`, перезапускаются,
  переживают перезапуск агента; долгая работа не прерывается ради плановой замены;
- **доставка** — запросы и задачи бэкенда к воркеру, настройки воркеров с версиями, события и
  метрики узла, журнал агента и воркеров;
- **обновления** — агент и воркеры обновляются по подписанным сборкам с откатом, если новая версия
  не заработала; агент сам замечает свои новые версии;
- **установка** — папка агента с настройками для своей машины и боевых узлов, архив для переноса,
  служба systemd одной командой — вручную или с бэкенда.

Ваш код — только воркеры (что делать на узле) и бэкенд (что и кому поручить). Воркеру не нужна
библиотека: это обычный HTTP-сервис на unix-сокете.

## Возможности

| Что                     | Как                                                                                                                                      |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| Запросы к воркеру       | `agents.fetch(id, worker, path, init)` — как обычный `fetch`, ответ потоком; проходят только объявленные воркером маршруты               |
| Задачи                  | `agents.runJob(...)`: быстрая — итог сразу, долгая — ход и итог событиями `job.*`; отмена, сверка после переподключения                  |
| Настройки воркеров      | `agents.setConfig(...)` — версия, проверка по схеме, хранение на диске узла, статус применения                                           |
| События и запросы       | воркер шлёт события (доставка гарантирована) и спрашивает бэкенд (`POST /requests`)                                                      |
| Метрики и журнал        | метрики узла (CPU, память, диски, сеть, температура, GPU…) и воркеров; журнал агента и воркеров; «смотреть подробнее» на время (`watch`) |
| Надзор за воркерами     | перезапуск, проверка здоровья, отложенная замена занятого воркера, подхват процессов после перезапуска агента                            |
| Обновления              | агента и воркеров — по подписи Ed25519 с откатом; агент сам проверяет новые версии и сообщает о них бэкенду и в командах                 |
| Папка агента            | `agent init` — программа, настройки для этой машины и для прода (`extends`, `envFiles`), воркеры проекта рядом                           |
| Перенос и установка     | `agent pack` — архив для узла; `agent install` — служба systemd из архива, из папки или с бэкенда; несколько экземпляров на узле         |
| Несколько копий бэкенда | общее хранилище и пересылка вызовов в копию, где сейчас соединение агента                                                                |

## Требования

| Часть                | Нужно                                                                                                                                       |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| Агент                | Linux или macOS, amd64 или arm64. Службой — Linux с systemd (Debian/Ubuntu, RHEL/Fedora, SUSE…); без systemd — в контейнере или `agent run` |
| Воркер               | любой язык, который умеет HTTP-сервер на unix-сокете (Python, Node.js, Go…)                                                                 |
| SDK бэкенда          | Node.js ≥ 24 (TypeScript, ESM)                                                                                                              |
| Сборка из исходников | Docker (Go запускается в контейнере), Node.js ≥ 24, python3 — для стенда и сквозных тестов                                                  |

## Быстрый старт

От нуля до агента с воркером на своей машине.

### 1. Скачайте агента

```bash
curl -fLo agent "https://github.com/epifanovmd/agent/releases/latest/download/agent-$(uname -s | tr A-Z a-z)-$(uname -m | sed 's/x86_64/amd64/;s/aarch64/arm64/')"
chmod +x agent
```

Это единственный раз, когда агента скачивают руками: дальше новые версии ставит `agent upgrade`.

### 2. Разверните папку агента

```bash
./agent init agent --server http://localhost:8080 --token <токен регистрации>
```

В проекте появится папка `agent/` — всё, что агент делает здесь и на узлах:

```
agent/
├── agent              программа (в git не хранится)
├── agent.yaml         настройки для этой машины — ./agent run читает его сам
├── agent.prod.yaml    боевые узлы: поверх agent.yaml
├── .env               адрес бэкенда и токен для этой машины (в git не хранится)
├── .env.example, .env.prod.example
├── workers/           воркеры проекта
└── README.md          что где лежит
```

### 3. Добавьте воркер

```bash
agent/agent worker new report            # или --lang go
```

Команда создаёт `agent/workers/report/`: базу `agent_worker.py` (весь протокол агента — здоровье,
манифест, настройки, задачи с ходом и отменой, события, запросы к бэкенду), `worker.py` с
классом-наследником, `run` и `VERSION` — и добавляет воркер в `agent.yaml`. Ваш код — только в
классе:

```python
# agent/workers/report/worker.py
from agent_worker import Config, Worker, job, route

class Report(Worker):
    description = "Отчёты"
    settings = Config("settings", schema={"type": "object"}, default={"limit": 10})
    events = {"report.sent": {"type": "object"}}

    @route("POST", "/reports/{id}/send")
    def send(self, req):
        self.emit("report.sent", {"id": req.params["id"]})
        return {"ok": True}

    @job("report.build")
    def build(self, job):
        job.progress(0.5, "половина")
        return {"rows": self.settings.value["limit"]}

if __name__ == "__main__":
    Report().run()
```

Без заготовки воркер — любая программа: папка с исполняемым `run` и файлом `VERSION`, которая
слушает HTTP на сокете `AGENT_WORKER_SOCKET` и отвечает на `GET /health` и `GET /manifest`:

```python
# agent/workers/hello/main.py — Python ≥ 3.10, только стандартная библиотека
import json, os, socketserver
from http.server import BaseHTTPRequestHandler

class Handler(BaseHTTPRequestHandler):
    def do_GET(self):
        body = {"/health": {"ok": True}, "/manifest": {"version": "1.0.0"}}.get(self.path)
        raw = json.dumps(body).encode()
        self.send_response(200 if body else 404)
        self.send_header("content-length", str(len(raw)))
        self.end_headers()
        self.wfile.write(raw)

path = os.environ["AGENT_WORKER_SOCKET"]
os.path.exists(path) and os.unlink(path)
socketserver.UnixStreamServer(path, Handler).serve_forever()
```

```bash
printf '#!/bin/sh\nexec python3 "$(dirname "$0")/main.py"\n' > agent/workers/hello/run
chmod +x agent/workers/hello/run && echo 1.0.0 > agent/workers/hello/VERSION
```

```yaml
# agent/agent.yaml
workers:
  - path: workers/hello
```

### 4. Запустите

```bash
agent/agent config check   # итоговые настройки и откуда взялось каждое значение
agent/agent run            # Ctrl+C — остановить
agent/agent status         # в другом терминале: связь, воркеры
```

### 5. Подключите бэкенд

```bash
npm install https://github.com/epifanovmd/agent/releases/download/v<версия>/agent-sdk-<версия>.tgz
```

```ts
import { createServer } from "node:http";
import { Agents } from "agent-sdk/server";

const agents = new Agents({ enrollToken: process.env.AGENT_ENROLL_TOKEN });
const server = createServer(async (req, res) => {
  if (await agents.handle(req, res)) return; // регистрация агентов, сборки, install.sh
  res.writeHead(404).end(); // ваше API
});
agents.attach(server); // WebSocket агентов на том же порту
server.listen(8080);

agents.on("agent", (a) => console.log(a.name, a.online ? "на связи" : "без связи"));
```

Дальше — запросы к воркеру, настройки и задачи: [sdk/docs/README.md](sdk/docs/README.md).

### 6. На боевой узел

```bash
agent/agent pack --env prod   # архивы для узлов: программа под linux/amd64 и linux/arm64, настройки, воркеры
scp agent/agent-prod-*-linux-amd64.tar.gz node-01:
ssh node-01 'tar xzf agent-prod-*-linux-amd64.tar.gz && cd agent && sudo ./agent install --env prod --token <токен>'
```

Агент встал службой systemd: `sudo agent status`, `sudo agent logs -f`.

## Установка на узел

Принцип один: на узле — программа агента, один файл настроек, воркеры в каталоге данных агента и
служба systemd. Различается только то, откуда всё это приходит.

| Способ                   | Команда                                                                                                                   | Когда                                                    |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------- |
| Из папки агента          | `sudo ./agent install --env prod` в папке проекта                                                                         | агент ставится на ту же машину, где лежит папка          |
| Из архива                | `agent pack --env prod` → на узле `tar xzf … && cd agent && sudo ./agent install`                                         | перенос вручную; узлу не нужен доступ к бэкенду и GitHub |
| С бэкенда одной командой | `curl -fsSL https://api.example.com/api/v1/agent-link/install.sh \| sudo sh -s -- --token <токен>`                        | бэкенд на `agent-sdk` раздаёт сборки и команду установки |
| Только программа         | `sudo ./agent install --server https://api.example.com --token <токен> [--worker …]`                                      | без папки агента: настройки создаются по шаблону         |
| Docker                   | `docker run -e AGENT_SERVER_URL=… -e AGENT_ENROLL_TOKEN=… -v agent-data:/var/lib/agent ghcr.io/epifanovmd/agent:<версия>` | узел — контейнер                                         |

Повторная установка обновляет программу и службу и сохраняет ключ агента. Несколько агентов на
одном узле (для разных бэкендов) — `--instance ИМЯ` или `instance:` в настройках. Удаление —
`sudo agent uninstall [--purge]`. Подробно, со всеми флагами —
[docs/ARCHITECTURE.md](docs/ARCHITECTURE.md#установка).

## Настройки

Настройки — YAML. Файл окружения ложится поверх общего, секреты — в файлах переменных:

```yaml
# agent.prod.yaml
extends: agent.yaml # сначала agent.yaml, поверх — этот файл
envFiles: [.env.prod] # KEY=VALUE для ${ИМЯ} и AGENT_*; окружение процесса важнее
instance: example # экземпляр на узле для agent install
install: # то же, что флаги agent install
  packages: [python3]
server:
  url: ${AGENT_SERVER_URL}
update:
  mode: self # агент обновляет себя по команде бэкенда
workers:
  - path: workers/report # воркер из папки проекта
    env: { REPORT_MODE: prod }
  - name: netprobe # воркер из релиза агента
    from: agent
```

- `./agent run` без флагов читает `agent.yaml` рядом с программой или в текущем каталоге;
  `--env prod` — `agent.prod.yaml`; `-config ФАЙЛ` — любой файл.
- `agent config check` показывает итоговые значения и у каждого — откуда оно: файл и строка или
  переменная окружения.
- Почти любой ключ можно задать переменной `AGENT_*`: `AGENT_SERVER_URL`, `AGENT_ENROLL_TOKEN`,
  `AGENT_LOG_LEVEL`…

Все ключи и переменные — [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md#настройки).

## Воркеры

Воркер — HTTP-сервис на unix-сокете из `AGENT_WORKER_SOCKET`. Обязательны `GET /health`
(самочувствие) и `GET /manifest` (что воркер умеет: маршруты, задачи, события, ключи настроек — со
схемами). Всё остальное — по желанию:

| Маршрут                     | Зачем                                                     |
| --------------------------- | --------------------------------------------------------- |
| свои маршруты из манифеста  | запросы бэкенда (`agents.fetch`)                          |
| `POST /jobs`, `GET /jobs/…` | задачи (`agents.runJob`)                                  |
| `PUT /config/{key}`         | настройки (`agents.setConfig`)                            |
| `GET /metrics`              | свои метрики — бэкенд получает их вместе с метриками узла |
| `POST /cleanup`             | убрать за собой при удалении агента                       |

В сторону бэкенда воркер пишет в сокет агента `AGENT_SOCKET`: события (`POST /events`) и запросы
(`POST /requests`). Как подключить воркер:

| В `agent.yaml`                     | Откуда воркер                                                       |
| ---------------------------------- | ------------------------------------------------------------------- |
| `- path: workers/report`           | папка проекта: агент запускает `./run` в ней                        |
| `- name: netprobe` + `from: agent` | сборка из релиза агента той же версии (агент скачает её сам)        |
| `- name: report` + `release: true` | сборка с бэкенда: ставит `agent install --worker`, обновляет бэкенд |
| `- name: report` + `command: […]`  | любая программа на узле                                             |

Воркер на Python, Node.js и Go с примерами — [sdk/docs/workers.md](sdk/docs/workers.md).

## Команды агента

| Команда                                  | Что делает                                                                 |
| ---------------------------------------- | -------------------------------------------------------------------------- |
| `agent init [ПАПКА]`                     | развернуть папку агента (`-config ФАЙЛ` — только файл настроек)            |
| `agent run [--env ИМЯ \| -config ФАЙЛ]`  | работать; SIGHUP — перечитать настройки                                    |
| `agent config check [--env ИМЯ]`         | проверить настройки, показать итоговые значения и откуда каждое            |
| `agent status [--json]`                  | работает ли агент, связь, воркеры, последняя ошибка                        |
| `agent pack [--env ИМЯ] [--platform …]`  | архив папки агента для узла                                                |
| `agent install [--env ИМЯ] [флаги]`      | поставить службой systemd: из архива, из папки или по флагам               |
| `agent upgrade [--check] [--version X]`  | поставить новую версию агента (подпись проверяется)                        |
| `agent keygen`                           | ключи подписи сборок воркеров проекта                                      |
| `agent worker new ИМЯ [--lang go]`       | воркер из заготовки (Python или Go): база и наследник, строка в настройках |
| `agent worker sync`, `agent worker list` | обновить базы воркеров; воркеры: откуда каждый, версия                     |
| `agent logs [-f]`, `agent restart`       | журнал службы; перезапуск агента (воркеры работают дальше)                 |
| `agent stop-workers`, `agent cleanup`    | остановить оставшиеся воркеры; уборка воркеров перед удалением             |
| `agent uninstall [--purge]`              | удалить службу (с `--purge` — настройки, данные, пакеты)                   |
| `agent version`, `agent help`            | версия, справка                                                            |

## Обновления и подписи

- **Агент** раз в 6 часов (`update.checkInterval`) смотрит последнюю версию в своих релизах на
  GitHub (`update.releases` — своё зеркало). Новее — сообщает бэкенду (поле `update` агента в SDK)
  и пишет в командах `status` и `config check`. Ставит её `agent upgrade` на узле или
  `agents.updateAgent(id, { version })` с бэкенда; новая версия не вышла на связь — возвращается
  прежняя.
- **Воркеры** со сборкой обновляет бэкенд (`agents.updateWorker`), с проверкой подписи и откатом.
- **Подписи** — Ed25519. Агент и `netprobe` подписаны ключом автора агента, он вшит в программу.
  Свои воркеры проект подписывает своим ключом: `agent keygen` выдаёт пару, закрытый ключ
  (`AGENT_SIGNING_KEY`) нужен только `agent pack`, открытый `pack` кладёт в архив, и установка
  добавляет его к ключам узла.

## Словарь

| Слово                 | Что это                                                                                                                                                        |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **узел**              | машина, на которой работает агент                                                                                                                              |
| **папка агента**      | программа агента, её настройки (`agent.yaml`, `agent.<env>.yaml`) и воркеры проекта в одном месте — обычно в репозитории проекта                               |
| **воркер**            | программа проекта, которую агент запускает на узле: HTTP-сервис на unix-сокете, одна копия                                                                     |
| **манифест воркера**  | самоописание воркера (`GET /manifest`): версия, ключи настроек, маршруты, события, задачи, запросы к бэкенду — со схемами; агент пропускает только объявленное |
| **маршрут**           | метод и путь из манифеста (`{id}` — любой сегмент); необъявленный запрос агент воркеру не передаёт                                                             |
| **схема**             | описание формы JSON-значения ([JSON Schema](https://json-schema.org)) в манифесте; по ней проверяет бэкенд                                                     |
| **запрос**            | HTTP-запрос бэкенда к воркеру через агента (`fetch`); ответ приходит по частям                                                                                 |
| **задача**            | работа, которую бэкенд поручает воркеру (`POST /jobs`): быстрая — итог сразу, долгая — ход и итог событиями `job.*`                                            |
| **настройки воркера** | значения, которые бэкенд задаёт воркеру по ключам, с растущей версией; агент хранит их на диске                                                                |
| **событие**           | сообщение воркера бэкенду «что-то случилось»; агент хранит его на диске, пока бэкенд не подтвердит                                                             |
| **запрос к бэкенду**  | вопрос воркера бэкенду с ожиданием ответа (`POST /requests`); без связи — сразу отказ                                                                          |
| **метрики**           | цифры узла (встроенный воркер `sysmetrics`, группы `cpu`, `memory`, `disk`…) и воркеров (их `GET /metrics`)                                                    |
| **наблюдение**        | просьба бэкенда «присылай метрики чаще и журнал подробнее» на время (`watch`)                                                                                  |
| **жизнь воркера**     | как агент запускает, проверяет, заменяет и останавливает воркер (`lifecycle`); по умолчанию воркер переживает перезапуск агента                                |
| **занят (`busy`)**    | воркер ведёт долгую работу: плановая замена ждёт её окончания                                                                                                  |
| **подхват**           | новый запуск агента находит живой процесс воркера и следит за ним дальше, не перезапуская                                                                      |
| **действие**          | встроенная операция агента по просьбе бэкенда: перезапустить или обновить воркер, обновить агента, сменить ключ, показать журнал                               |
| **сборка**            | подписанный файл агента или воркера под систему; список сборок — `manifest.json` каталога сборок                                                               |
| **архив агента**      | итог `agent pack`: программа под платформу узла, настройки, воркеры и их сборки — для `agent install` на узле                                                  |
| **экземпляр**         | один из нескольких агентов на узле (`--instance ИМЯ`) со своими путями и службой                                                                               |
| **Agents**            | главный объект SDK: принимает агентов, отправляет запросы воркерам, доставляет настройки, хранит события и метрики                                             |
| **копия бэкенда**     | один из процессов бэкенда с общим хранилищем; вызовы к агенту SDK пересылает в копию с его соединением (`relay`)                                               |

## Разработка

Go ставить не нужно: цели `make` запускают его в контейнере `golang`. Список целей — `make help`.

```bash
make demo-build && make demo-server   # стенд: сервер на SDK — http://localhost:8080/api
make demo-agent                       # в другом терминале: агент с воркерами-примерами
make check                            # все проверки перед коммитом
```

| Цель                      | Что делает                                                                             |
| ------------------------- | -------------------------------------------------------------------------------------- |
| `make test`, `make race`  | тесты на Go (агент, образцы сообщений, `test/integration`), с поиском гонок            |
| `make sdk-test`           | тесты SDK, ESLint и проверка типов                                                     |
| `make e2e`                | сквозные тесты: сервер стенда, настоящий агент и воркеры-примеры                       |
| `make fmt`, `make format` | отформатировать Go-код и всё остальное (Prettier)                                      |
| `make build`              | агент под эту машину → `dist/<VERSION>/`                                               |
| `make release`            | сборки агента и netprobe под linux/darwin × amd64/arm64, `manifest.json`, `install.sh` |
| `make images`             | образы `agent:dev`, `agent:dev-python`, `agent-dist:dev`                               |
| `make version V=1.2.0`    | записать версию во все места                                                           |

```
cmd/agent/          программа агента
cmd/agent-release/  подпись сборок для публикации (на узлы не ставится)
internal/           устройство агента — docs/ARCHITECTURE.md
sdk/                SDK бэкенда (node/), документация (docs/), формат сообщений (spec/)
examples/           стенд: сервер на SDK, воркеры-примеры, сквозные тесты
deploy/             образы Docker, install.sh
test/integration/   настоящий агент против сервера на agent-sdk
```

**Публикация.** Версия одна на агента, SDK и примеры — файл `VERSION`. Тег `v<VERSION>` → CI
выкладывает в GitHub Release подписанные сборки агента и `netprobe`, `manifest.json`,
`install.sh`, архив SDK `agent-sdk-<версия>.tgz` и образы `ghcr.io/epifanovmd/agent:<версия>`,
`:<версия>-python`, `ghcr.io/epifanovmd/agent-dist:<версия>`. Ключ подписи — секрет репозитория
`AGENT_SIGNING_KEY`, открытый ключ — переменная `AGENT_UPDATE_PUBLIC_KEY` (CI вшивает его в
агента). Правила разработки — [CONTRIBUTING.md](CONTRIBUTING.md), об уязвимостях —
[SECURITY.md](SECURITY.md).
